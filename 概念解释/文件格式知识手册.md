# 文件格式知识手册

> **这份笔记的底稿**：`文件格式.txt` 的 5 章（常见格式分类 / 为什么用 docx 不用 doc / 为什么至今还留着 doc / PDF 等格式各自的优势 / 怎么选）是这份手册的骨架，**原文的每张表、每个论点都保留在对应章节里**，并逐条展开、补上原文没涉及的部分（编码、魔数、音视频容器与编码、压缩、可执行文件、文件系统层）。

> **这份笔记想解决的问题**：绝大多数人对文件格式的认识停在「后缀名」上——`.jpg` 就是图片，`.docx` 就是 Word。但只要遇到「后缀改了打不开」「中文乱码」「CSV 用 Excel 打开成乱码」「视频改成 mp4 还是不能播」「PDF 复制不出文字」，这套认知就崩了。
>
> 真正的认知是三层：**① 字节怎么排（格式本身）② 字节怎么解释成字符（编码）③ 系统怎么认出它（后缀/MIME/魔数）**。这份笔记按这三层往下拆。

## 30 秒速览

1. **格式不是后缀，是"读取者怎么解释这些字节"的约定**——所以改后缀永远改不了格式。判断真实格式看**魔数**（文件头），不是扩展名，`file` 一条命令就露。
2. **编码是独立的一层**：字节 → 字符。乱码只有三种成因（编错、解错、双重编码），而"锟斤拷"是双重编码的化石、**救不回来**；BOM 给 Excel 吃要加、给程序吃一律不要。
3. **容器 ≠ 编码**：`.mp4` 里可能是 H.264/265/AV1，所以"同后缀能不能播"完全不确定。只换容器用 `-c copy` 秒级无损，重新编码才是有损的几小时。
4. **`.docx` / `.apk` / `.epub` / `.jar` 全是 ZIP**；doc 是历史债务，行业通行策略是**读旧写新**——新文档走 docx，旧文档按需保留，不搞一刀切。
5. **PDF 是"打印结果"，不是"文档"**——它的目标是"所有人看到的都一样"，不是"让你接着改"。所以正确姿势是：**交付 PDF，同时给自己留母版**（docx/md/psd/工程文件）。

> **一句话记住**：**字节怎么排（格式） → 怎么变成字（编码） → 系统怎么认出它（后缀/MIME/魔数）**，三层分开想，绝大多数"打不开、乱码、播不了"当场就能定位。

## 一、文件格式到底是什么

### 1.1 一句话定义

**文件格式 = 一份关于「这些字节怎么排、怎么解释」的约定。**

文件在磁盘上只是一串 0 和 1，没有任何"标签"告诉计算机这是什么。所谓"这是一张 PNG 图片"，是**某个程序按 PNG 的约定去读这串字节，读通了**，于是它说"这是 PNG"。

所以：

- 格式不是文件的**属性**，是**读取者的解释方式**；
- 同一串字节，按不同约定去读，可以得出完全不同的内容；
- **格式由读写双方共同遵守，没有任何强制力**——这就是为什么会有"不标准的 MP4 只有某些播放器能放"。

### 1.2 一个文件的典型结构

绝大多数格式都长这样，从前往后：

```
┌──────────┬──────────────┬──────────────┬──────────────┬──────────┐
│  魔数     │   元数据/头    │    载荷数据    │   索引/目录    │  校验/尾   │
│ Magic    │  Header      │   Payload     │  Index/TOC    │ Checksum  │
└──────────┴──────────────┴──────────────┴──────────────┴──────────┘
   前几个字节    宽高/采样率     真正的像素/音频      zip 的中央目录    CRC32
   用来认身份    编码参数等        压缩后的数据        让随机读取变快    防损坏
```

| 部分 | 作用 | 例子 |
| --- | --- | --- |
| **魔数 Magic Number** | 文件开头的固定字节，用来识别格式 | PNG 开头 `89 50 4E 47` |
| **头 Header** | 描述后面数据怎么解释 | JPEG 里的宽高、色彩空间；WAV 的采样率 |
| **载荷 Payload** | 真正的数据 | 像素、音频采样、文字 |
| **索引 Index / TOC** | 数据块的位置表，支持随机访问 | ZIP 的中央目录、MP4 的 moov box |
| **校验 Checksum** | 检测是否损坏 | PNG/ZIP 的 CRC32、部分格式的 SHA |

> **这个结构解释了很多现象**：为什么文件头损坏整张图就打不开（认不出身份）、为什么大文件"能播但拖进度条很慢"（索引在文件尾部，得先读完）、为什么下载中断的文件往往打不开（尾部的索引/校验没到）。

### 1.3 文本 vs 二进制

| 维度 | 文本格式 | 二进制格式 |
| --- | --- | --- |
| 存储单位 | 字符（经编码变成字节） | 字节/位，按固定结构排 |
| 人能不能直接看 | 能（用记事本打开） | 不能（一堆乱码或空白） |
| 体积 | 大 | 小（通常小很多） |
| 解析速度 | 慢（要解析字符串） | 快（按偏移直接读） |
| 可读性/可 diff | 好，能进 Git、能人工改 | 差，改一个字节可能全废 |
| 典型代表 | txt、csv、json、xml、yaml、md、html、svg | png、jpg、mp4、docx、exe、pdf、sqlite |
| 出错时 | 通常还能打开，只是内容怪 | 通常直接打不开或崩溃 |

> **灰色地带**：PDF 头是文本（`%PDF`）但内部有大量二进制流；SVG 是纯文本的图片；docx 是 ZIP 压缩包（所以"二进制"，但解开后全是 XML 文本）。

### 1.4 扩展名、MIME、魔数：三个"身份"不是一回事

这是全篇最重要的一个区分：

| 身份 | 谁给的 | 例子 | 可信度 | 谁在用 |
| --- | --- | --- | --- | --- |
| **扩展名** | 文件名的一部分，**人随便改** | `.jpg` `.docx` | **最低**，纯约定 | Windows 资源管理器、网站上传校验 |
| **MIME 类型** | 传输时的声明（HTTP 头、邮件头） | `image/jpeg` `application/pdf` | 中等，由发送方声明 | 浏览器、邮件客户端 |
| **魔数** | 文件内容本身的前几个字节 | `FF D8 FF` = JPEG | **最高**，改不了（改了文件就坏了） | `file` 命令、专业软件 |

于是就有了这些经典现象：

- **改了扩展名，格式没变**：把 `a.zip` 改名成 `a.jpg`，图片查看器打不开，但 `file a.jpg` 依然告诉你这是 Zip。
- **扩展名对、内容错**：网站让你传图片，你把 `.exe` 改名成 `.jpg` 传上去——**只看后缀的校验能过，这是真实存在的上传漏洞**。
- **MIME 声明错，浏览器行为怪**：服务器把 `.js` 用 `text/plain` 返回，浏览器就不执行它；把 `.json` 用 `text/html` 返回，可能引发 XSS。

> **安全结论**：任何"用户上传文件"的场景，必须**按魔数判断真实类型**，不能只信扩展名和 MIME。这就是为什么正规系统上传图片后会重新编码一遍（顺便去掉藏在里面的脚本和 EXIF）。

### 1.5 为什么格式这么多

| 原因 | 结果 |
| --- | --- |
| 不同场景的取舍不同 | 无损 vs 有损、体积 vs 质量、随机访问 vs 顺序流 |
| 历史包袱 | 老格式不能废，只能兼容（`.doc` 至今还要能开） |
| 商业与专利 | H.265 专利池复杂，所以有了 AV1；RAR 专有，所以有了 7z |
| 生态锁定 | 厂商用自己的格式绑定用户（PSD、AI、SKETCH） |
| 标准与实现的差距 | "标准 MP4"和"某软件导出的 MP4"可能不兼容 |

### 1.6 常见文件格式分类总表（对应原文第一章）

| 类别 | 常见格式 | 说明（原文） | 判断要点（补） |
| --- | --- | --- | --- |
| 纯文本 | TXT、MD、CSV、LOG | 无格式、通用性最好，是长期保存的"保底格式" | 只需管**编码**和**换行**两件事 |
| 富文本文档 | DOC、DOCX、RTF、ODT、WPS | 可编辑，即"活动文档" | 有"排版状态"，所以要版本兼容 |
| 固定版式 | PDF、PDF/A、XPS | 用于交付、打印和归档 | 只有"画好的结果"，没有可编辑结构 |
| 表格 | XLS、XLSX、ODS、CSV | 用于保存数据和计算模型 | 区分"含公式/样式"（xlsx）与"纯数据"（csv） |
| 演示 | PPT、PPTX、ODP、KEY | — | KEY 是 macOS 专有，导出时注意字体替换 |
| 网页 | HTML、HTM、MHT、XML | 可在浏览器中直接渲染 | MHT 是"网页 + 图片打包成一个文件" |
| 图片 | JPG、PNG、GIF、BMP、TIFF、WebP、AVIF、SVG、HEIC、RAW | 按位图和矢量、有损和无损区分 | 见第五章逐项对比 |
| 音视频 | MP3、AAC、FLAC、WAV；MP4、MOV、MKV、AVI、WebM | 音频和视频 | **容器与编码是两层**，见第六章 |
| 压缩归档 | ZIP、RAR、7z、TAR、GZ | — | 压缩（算法）与归档（打包）是两件事，见第七章 |
| 电子书 | EPUB、MOBI、AZW3 | — | EPUB 本质是 ZIP；MOBI/AZW3 绑 Kindle |
| 结构化数据 | JSON、XML、YAML、TOML、Parquet | — | 给人改的（YAML/TOML）vs 给机器传的（JSON/Parquet） |
| 可执行与安装包 | EXE、MSI、APK、DMG、AppImage、ISO | — | 能不能双击运行看"平台 + 权限 + 签名"，见第九章 |
| 字体 | TTF、OTF、WOFF、WOFF2 | — | TTF/OTF 给系统用，WOFF2 给网页用 |

> **这张表不是按后缀分的，是按「谁生成、谁读取、能不能改」分的。** 所以同一个后缀可能横跨两类——`.csv` 既是纯文本也是表格，`.xml` 既是网页也是结构化数据，`.zip` 既是压缩包也是 docx/apk/epub 的底层容器。先问"我要拿它干什么"，再回头查表，比记后缀有用得多。

## 二、三分钟看穿一个文件

### 2.1 第一步永远是：看魔数，不看后缀

```bash
# Linux / macOS / Git Bash
file 我的文件.jpg

# Windows PowerShell
Format-Hex -Path .\我的文件.jpg | Select-Object -First 2

# 任意平台：直接看前 16 个字节
xxd -l 16 我的文件.jpg
```

`file` 的输出会告诉你真实类型，例如：

```
a.jpg: Zip archive data, at least v2.0 to extract
```

——后缀写着 jpg，实际是 zip。这种情况在"从网上下载的伪装文件""别人发给你的压缩包被改了名"里非常多。

### 2.2 常见魔数速查表

| 格式 | 开头字节（十六进制） | 可读特征 |
| --- | --- | --- |
| **PNG** | `89 50 4E 47 0D 0A 1A 0A` | `‰PNG` |
| **JPEG** | `FF D8 FF` | 结尾是 `FF D9` |
| **GIF** | `47 49 46 38` | `GIF8` |
| **BMP** | `42 4D` | `BM` |
| **TIFF** | `49 49 2A 00` 或 `4D 4D 00 2A` | `II*` / `MM` |
| **WebP** | `52 49 46 46 ... 57 45 42 50` | `RIFF....WEBP` |
| **PDF** | `25 50 44 46` | `%PDF` |
| **ZIP**（含 docx/xlsx/pptx/apk/jar/epub） | `50 4B 03 04` | `PK` |
| **RAR** | `52 61 72 21 1A 07` | `Rar!` |
| **7z** | `37 7A BC AF 27 1C` | — |
| **GZIP** | `1F 8B` | — |
| **BZIP2** | `42 5A 68` | `BZh` |
| **XZ** | `FD 37 7A 58 5A 00` | — |
| **Zstandard** | `28 B5 2F FD` | — |
| **ELF**（Linux 可执行） | `7F 45 4C 46` | `\x7fELF` |
| **PE / EXE / DLL** | `4D 5A` | `MZ` |
| **Java class** | `CA FE BA BE` | 咖啡杯 |
| **SQLite 数据库** | `53 51 4C 69 74 65 20 66 6F 72 6D 61 74 20 33 00` | `SQLite format 3` |
| **MP4 / MOV** | 偏移 4 处为 `66 74 79 70` | `....ftyp` |
| **FLAC** | `66 4C 61 43` | `fLaC` |
| **OGG** | `4F 67 67 53` | `OggS` |
| **WAV** | `52 49 46 46 ... 57 41 56 45` | `RIFF....WAVE` |
| **AVI** | `52 49 46 46 ... 41 56 49 20` | `RIFF....AVI ` |
| **MKV / WebM** | `1A 45 DF A3` | EBML |
| **ISO 镜像** | 偏移 0x8001 处 `43 44 30 30 31` | `CD001` |
| **OLE 复合文档**（老 doc/xls/ppt） | `D0 CF 11 E0 A1 B1 1A E1` | — |
| **字体 TTF** | `00 01 00 00` 或 `74 72 75 65` | `true` |
| **字体 OTF** | `4F 54 54 4F` | `OTTO` |
| **字体 WOFF** | `77 4F 46 46` | `wOFF` |
| **字体 WOFF2** | `77 4F 46 32` | `wOF2` |

> **记不住没关系**，记住三件事：① 用 `file` 命令；② PNG/JPEG/ZIP/PDF 四种的特征要认识（日常 90% 的情况）；③ 头部 `PK` 基本就是压缩包（或 Office 文档）。

### 2.4 编码与内容的进一步探测

```bash
# 猜测文本编码

# 扫描文件里嵌入的其他格式（固件、镜像、伪装文件）
binwalk 固件.bin

# 从二进制里捞可读字符串
strings 程序.bin | head -50
```

## 三、文本格式的根基：编码与换行

> 这一章是「乱码」问题的唯一解药。所有「中文变问号/方块/锟斤拷」的根源都在这。

### 3.1 字符集与编码：两个概念别混

| 概念 | 回答什么问题 | 例子 |
| --- | --- | --- |
| **字符集 Charset** | 有哪些字符、每个字符给个编号（码点） | Unicode：`中` = U+4E2D |
| **编码 Encoding** | 这个编号在文件里存成哪几个字节 | UTF-8：`中` = `E4 B8 AD` |

一句话：**Unicode 是"字符的编号表"，UTF-8 是"编号怎么变成字节"的规则之一。** 同一个 `中`，UTF-8 存 3 字节，GBK 存 2 字节（`D6 D0`），UTF-16 存 2 或 4 字节。

### 3.2 常见编码对照

| 编码 | 字节数 | 兼容 ASCII | 说明 |
| --- | --- | --- | --- |
| **ASCII** | 1 | — | 只有 128 个字符，英文+控制符，**是其他编码的基础** |
| **Latin-1 / ISO-8859-1** | 1 | 是 | 西欧字符，很多老系统默认 |
| **GB2312** | 1~2 | 是 | 简体中文老标准，6763 个汉字 |
| **GBK** | 1~2 | 是 | GB2312 扩展，2 万多汉字，**Windows 中文版默认** |
| **GB18030** | 1/2/4 | 是 | 国标超集，包含所有 Unicode 字符，**强制国标** |
| **Big5** | 1~2 | 是 | 繁体中文（台湾/香港） |
| **UTF-8** | 1~4 | 是 | **互联网事实标准**，全世界通用 |
| **UTF-16** | 2/4 | 否 | Windows 内部、Java 字符串、部分文件格式 |
| **UTF-32** | 4 | 否 | 极少用，占空间 |

> **为什么 UTF-8 赢了**：① 兼容 ASCII（英文文本一字不变）；② 变长，中文 3 字节而 UTF-16 要 2 字节但英文要 2 字节，混合文本总体更省；③ 自同步，从任意位置能找回字符边界，抗截断。**新项目一律 UTF-8，没有例外。**

### 3.3 BOM：一个小东西制造了大量麻烦

**BOM（Byte Order Mark）**：文件开头几个字节，用来标记"这是哪种编码"以及"字节序是哪头"。

| 编码 | BOM 字节 |
| --- | --- |
| UTF-8 | `EF BB BF` |
| UTF-16 LE | `FF FE` |
| UTF-16 BE | `FE FF` |
| UTF-32 LE | `FF FE 00 00` |

麻烦在哪：

| 场景 | 问题 |
| --- | --- |
| **Excel 打开 CSV 中文乱码** | 无 BOM 时 Excel 按本地 ANSI（中文系统就是 GBK）解释，UTF-8 中文就乱了。**加 BOM 就正常**——这是"CSV 乱码"最常见的原因 |
| **程序读 JSON/YAML 报错** | 某些解析器不识别 BOM，第一个字符变成不可见字符，报「Unexpected token」 |
| **Shell 脚本第一行失效** | `#!/bin/bash` 前面带了 BOM，内核认不出 shebang，报 `bad interpreter` |
| **网页多出空白** | BOM 被当成内容输出，页面顶部多一行空白 |
| **代码合并出现怪 diff** | 一方有 BOM 一方没有，git 显示整文件变更 |

> **实践规则**：
> - **给 Excel 吃的 CSV → 要 BOM（UTF-8 with BOM）**；
> - **给程序吃的 JSON/YAML/代码/配置 → 不要 BOM**；
> - Linux 下的 `file` 会把带 BOM 的文本识别成 `UTF-8 Unicode (with BOM) text`，可以据此检查。

### 3.4 乱码的三种成因与排查

| 类型 | 现象 | 原因 | 怎么修 |
| --- | --- | --- | --- |
| **编码错读** | `ä¸­æ–‡`（这是 UTF-8 被当 Latin-1 读）、`涓枃`（UTF-8 被当 GBK 读） | 存的是 A 编码，读的时候用了 B 编码 | 用正确编码重新打开；VS Code 右下角切换编码 |
| **双重编码** | `锟斤拷`、`烫烫烫` | 已经被错读成乱码，又用错编码保存了一次，信息已经**不可逆丢失** | **修不回来**，只能从源头重来 |
| **字体缺字** | 全是方块 `□□□` 或问号 `???` | 编码是对的，但显示用的字体没有这些字形 | 换字体（如思源黑体），数据没坏 |

> **关键判断**：`锟斤拷` 出现 = 已经坏了，别浪费时间尝试"转换编码"。它来自 GBK 编码里 `EF BF BD`（UTF-8 的替换字符）被按 GBK 解释的结果——是两次错误叠加的化石。

**排查顺序**：

1. 先确认**原始字节**：`file -i` 看它猜什么编码。
2. 用 `xxd -l 32` 看开头：有 `EF BB BF` 就是 UTF-8 BOM；中文 GBK 常见 `D6 D0`（中）。
3. 拿一小段做实验：用 `iconv -f GBK -t UTF-8` 试转，看结果是否正常。
4. 判断"能不能救"：如果原文里本来就有大量 `?` 或 `�`，说明信息已丢，救不回来。

```bash
iconv -f GBK -t UTF-8 旧文件.txt -o 新文件.txt
```

### 3.5 换行符：LF / CRLF / CR

| 系统 | 换行 | 字节 | 名字 |
| --- | --- | --- | --- |
| Linux / macOS（现代） | `\n` | `0A` | LF |
| Windows | `\r\n` | `0D 0A` | CRLF |
| 老 Mac（OS 9 及以前） | `\r` | `0D` | CR |

混乱的后果：

| 场景 | 现象 |
| --- | --- |
| Windows 记事本打开 LF 文件 | 新版能正常显示；老版本全挤成一行 |
| Linux 脚本从 Windows 拷过来 | 报 `bad interpreter: /bin/bash^M` —— 就是那个 `\r` |
| Git 跨平台协作 | 每次提交整个文件都"变了"（换行全变） |
| CSV 导入数据库 | 行尾带 `\r`，最后一列的值多一个不可见字符，导致匹配失败 |

**处理办法**：

```bash
# 转换
dos2unix 文件          # CRLF → LF
unix2dos 文件          # LF → CRLF

# 检查
file 文件              # 会显示 "with CRLF line terminators"

# Git 层面统一（推荐）
# .gitattributes
* text=auto
*.sh text eol=lf
*.bat text eol=crlf
```

### 3.6 Unicode 的四个隐藏陷阱

| 陷阱 | 现象 | 例子 |
| --- | --- | --- |
| **NFC / NFD 归一化** | 看起来一样的字符串，比较却不相等 | macOS 文件名用 NFD（`é` = `e` + 组合符），Windows 用 NFC |
| **零宽字符** | 复制来的代码跑不通、密码总是不对 | `\u200B` 零宽空格、`\uFEFF` BOM 混进字符串 |
| **同形字** | 两个"看起来一样"的字符其实不同 | 拉丁 `a` vs 西里尔 `а`；`Ⅰ`（罗马数字）vs `I` |
| **emoji 与代理对** | 长度算错、截断出乱码 | `👨‍👩‍👧` 是一个"字"，但由多个码点组成，`len()` 会给你 8 |

> **实用建议**：处理用户输入的字符串前先做 `normalize('NFC')`；比较域名/用户名时考虑同形字风险；截断字符串按"字素簇"而不是按字节或码点。

### 3.7 纯文本家族对照

| 格式 | 用途 | 优点 | 坑 |
| --- | --- | --- | --- |
| `.txt` | 纯文本 | 最通用，永不失效 | 没有结构，没有样式 |
| `.csv` | 表格数据 | 极简，Excel 能开 | 见 4.5，坑最多 |
| `.tsv` | 制表符分隔 | 不会和逗号冲突 | 字段里含 Tab 就坏 |
| `.json` | 数据交换/接口 | 通用、好解析 | 不能写注释、不能尾逗号 |
| `.xml` | 数据交换/配置 | 严格、可校验、可命名空间 | 冗长，解析慢 |
| `.yaml` | 配置 | 人读友好 | 缩进敏感，隐式类型坑 |
| `.toml` | 配置 | 语义明确、不易歧义 | 嵌套深了啰嗦 |
| `.ini` | 老式配置 | 简单 | 无标准，各家实现不同 |
| `.md` | 文档 | 好写好 diff | 各家扩展语法不同 |
| `.log` | 日志 | 追加写、可 grep | 无结构，量大 |

## 四、结构化数据格式

### 4.1 JSON

```json
{
  "name": "张三",
  "age": 30,
  "tags": ["a", "b"],
  "address": { "city": "杭州" }
}
```

| 特性 | 说明 |
| --- | --- |
| 类型 | 对象、数组、字符串、数字、布尔、null（**只有这 6 种**） |
| 优点 | 通用、几乎所有语言原生支持、可读 |
| 严格限制 | **不能写注释**、**不能有尾逗号**、key 必须双引号、不支持 `NaN`/`Infinity` |

**四个真实踩过的坑**：

| 坑 | 说明 |
| --- | --- |
| **大整数丢精度** | JSON 数字按 IEEE 754 双精度存，超过 2^53 就丢。Twitter 的推文 ID 就得用字符串传，否则末位变 0 |
| **浮点表示** | `0.1 + 0.2` 在 JSON 里就是 `0.30000000000000004`，金额要用字符串或整数分 |
| **不适合大数据** | 整个文件要一次读进内存解析，几百 MB 就开始吃力 |
| **重复 key** | 标准没规定，不同解析器行为不同（取第一个/最后一个/报错） |

> `JSON5`、`JSONC`（VS Code 配置）允许注释和尾逗号，但**它们不是 JSON**，传给标准解析器会失败。

### 4.2 XML

```xml
<book id="1">
  <title>书名</title>
  <author>作者</author>
</book>
```

| 概念 | 作用 |
| --- | --- |
| DTD / XSD | 定义"这个 XML 应该长什么样"，可校验 |
| 命名空间 xmlns | 避免不同来源的标签重名 |
| XPath / XSLT | 查询与转换 |
| CDATA | 包住不想被解析的原始文本 |

**和 JSON 的取舍**：

| 维度 | JSON | XML |
| --- | --- | --- |
| 可读性 | 好 | 一般（标签多） |
| 体积 | 小 | 大（通常 1.5~3 倍） |
| 校验能力 | 弱（需 JSON Schema） | **强（XSD）** |
| 混合内容（文本里夹标签） | 不支持 | **支持** |
| 现状 | 接口主流 | 企业/文档/政府系统仍大量使用 |

### 4.3 YAML

```yaml
server:
  host: 0.0.0.0
  ports:
    - 80
    - 443
```

| 特性 | 说明 |
| --- | --- |
| 优点 | 人读最舒服，支持注释、锚点复用（`&` / `*`）、多文档（`---`） |
| 缺点 | **缩进即语法**，一个空格错就全错；隐式类型转换极其阴险 |

**YAML 的隐式类型坑（务必知道）**：

| 你写的 | YAML 1.1 理解成 | 后果 |
| --- | --- | --- |
| `country: NO` | `false`（挪威的国家代码变成了布尔） | 著名的「挪威问题」 |
| `on` / `off` / `yes` / `no` | 布尔 | 开关配置"看起来是字符串其实是 bool" |
| `22:22` | 六十进制数字 1342 | 时间被算成数字 |
| `1.0` | 浮点，会变成 `1` 输出时 | 版本号被吃掉 `.0` |
| `012` | 八进制 10 | 编号错了 |
| 未加引号的 `*` 或 `&` | 锚点/引用符号 | 解析报错 |

> **实践**：版本号、国家代码、以 0 开头的编号、看起来像布尔的值——**全部加引号**。YAML 1.2 修掉了大部分，但很多解析器还是 1.1 行为。

### 4.4 TOML 与 INI

```toml
[server]
host = "0.0.0.0"
port = 443
tags = ["a", "b"]
```

| 格式 | 适用 | 说明 |
| --- | --- | --- |
| **TOML** | 现代配置 | 类型明确、无隐式转换、层级清晰，Rust/Go 生态常用（`Cargo.toml`、`pyproject.toml`） |
| **INI** | 简单配置 | 无统一标准，`[section] key=value`；Windows 的 `.ini`、Python 的 `configparser` |

> 配置格式选型一句话：**要人频繁改 → TOML 或 YAML；要机器生成/传输 → JSON；已有生态 → 跟随它**。

### 4.5 CSV 的七个坑

CSV 看着最简单，实际是"看起来最无害、出问题最多"的格式。

| 坑 | 现象 | 解法 |
| --- | --- | --- |
| **① 分隔符不一定是逗号** | 欧洲常用 `;`（因为逗号是小数点） | 显式指定分隔符；或用 TSV |
| **② 字段里有逗号** | `"张三, 李四"` 被拆成两列 | 必须用引号包裹，引号内的逗号不拆 |
| **③ 字段里有换行** | 一条记录跨了多行，按行读就错 | 用真正的 CSV 解析器，别 `split('\n')` |
| **④ 引号转义** | 字段里本身有引号，要写成 `""` | 遵循 RFC 4180 |
| **⑤ 编码** | Excel 打开 UTF-8 中文乱码 | 存成 **UTF-8 with BOM**，或让 Excel 走"数据→从文本导入" |
| **⑥ 类型被 Excel 自动改** | `00123` 变 `123`；`1-2` 变日期；长数字变 `1.23E+18` | 导出时给这些列加前缀 `'` 或用文本格式；**用程序读，别用 Excel 存** |
| **⑦ 首行是表头吗** | 有的文件没表头，有的有 | 必须显式声明，不能猜 |

> **一句话**：**永远不要把 CSV 当字符串处理。** 用 `pandas.read_csv`、`csv` 模块、`Miller`（`mlr`）这类工具，它们处理了引号、换行、编码。

### 4.6 列式与二进制结构化格式

数据量大到 CSV/JSON 撑不住时，就该换这些：

| 格式 | 类型 | 特点 | 典型场景 |
| --- | --- | --- | --- |
| **Parquet** | 列式二进制 | 压缩比高、只读需要的列、带 schema | 数据仓库、Spark、Hive |
| **ORC** | 列式二进制 | 类似 Parquet，Hive 生态 | Hadoop |
| **Avro** | 行式二进制 | 带 schema、支持 schema 演进 | Kafka、流式 |
| **Protobuf** | 二进制序列化 | 体积极小、快，但需要 `.proto` 才能读 | gRPC、微服务 |
| **MessagePack** | 二进制 JSON | 兼容 JSON 数据模型，更小更快 | 缓存、RPC |
| **BSON** | 二进制 JSON | MongoDB 内部格式，支持更多类型 | MongoDB |
| **Arrow** | 内存列式 | 零拷贝跨语言交换 | 分析引擎之间 |

> **为什么列式快**：同样是 100 万行，查询「平均年龄」时列式只需读年龄那一列（几百 KB），行式要把整行（几十 MB）都读进来。这是数据仓库性能差距的主因之一。

### 4.7 选型建议

| 需求 | 选 |
| --- | --- |
| 人和程序都要读、要能进 Git | JSON / TOML / YAML |
| 给非技术人员看表格 | CSV（但注意 4.5）或 xlsx |
| 接口传输 | JSON（通用）或 Protobuf（性能敏感） |
| 百万行以上分析 | Parquet |
| 需要强校验、混合内容 | XML |
| 配置文件 | TOML（新）／ YAML（生态已有）／ `.env`（密钥） |

## 五、图片格式

### 5.1 位图 vs 矢量

| 类型 | 原理 | 放大后 | 体积 | 代表 |
| --- | --- | --- | --- | --- |
| **位图（栅格）** | 记录每个像素的颜色 | **模糊/锯齿** | 与分辨率成正比 | JPEG、PNG、WebP、BMP |
| **矢量** | 记录形状的数学描述 | **永远清晰** | 与复杂度成正比 | SVG、AI、EPS、PDF 里的图形 |

> 矢量图适合图标、logo、地图、图表；位图适合照片。**把位图放大不会变清晰**——这是"分辨率"的本质。

### 5.2 常见位图格式对比

| 格式 | 压缩 | 透明 | 动画 | 典型体积 | 适合 |
| --- | --- | --- | --- | --- | --- |
| **JPEG** | 有损 | ❌ | ❌ | 小 | 照片、复杂色彩 |
| **PNG** | 无损 | ✅（alpha） | ❌（APNG 可以） | 中~大 | 截图、图标、需要透明的图 |
| **WebP** | 有损/无损 | ✅ | ✅ | 比 JPEG 小 25~35% | 网页通用，首选 |
| **AVIF** | 有损/无损 | ✅ | ✅ | 比 WebP 再小 20~50% | 现代网页，压缩最强 |
| **GIF** | 无损（256 色） | ✅（1 位） | ✅ | 大 | **已过时**，只用于兼容 |
| **BMP** | **无压缩** | 部分 | ❌ | 极大 | 几乎不用，除非特定工业软件 |
| **TIFF** | 无损（可压缩） | ✅ | ❌ | 大 | 印刷、扫描、存档 |
| **HEIC/HEIF** | 有损 | ✅ | ✅ | 小 | iPhone 默认拍照格式 |

> **HEIC 的坑**：iPhone 默认存 HEIC，Windows 老版本和很多网站不支持，别人打不开。要么在手机上设「最兼容」（存 JPEG），要么导出时转换。另外 HEIC 有专利，开源支持一直不顺。

### 5.3 有损、无损、以及"压缩了什么"

| 类型 | 做什么 | 代价 |
| --- | --- | --- |
| **无损** | 只去除冗余（如重复颜色、可预测像素），解压后**完全一致** | 体积压不下去多少 |
| **有损** | 主动丢弃人眼不敏感的信息（色度细节、高频纹理） | 反复编辑会累积劣化（**"代际损失"**） |
| **无压缩** | 原样存 | 体积最大 |

> **重要实践**：**不要反复保存 JPEG**。每次另存都重新量化一次，十次之后画质肉眼可见地烂。要多次编辑，用 PNG/TIFF 或原始 RAW，最后导出一次 JPEG。
>
> **JPEG 的质量参数不是线性的**：90 → 95 体积翻倍但肉眼差别很小；70 以下开始出现明显块状伪影。

### 5.4 SVG：是图片，也是 XML，也是脚本容器

```xml
<svg xmlns="http://www.w3.org/2000/svg" width="100" height="100">
  <circle cx="50" cy="50" r="40" fill="blue"/>
</svg>
```

| 特点 | 说明 |
| --- | --- |
| 本质 | **文本 + XML**，能用记事本打开改 |
| 优点 | 任意缩放清晰、体积极小、可被 CSS/JS 操作、可被搜索引擎读 |
| 危险 | **可以内嵌 `<script>` 和事件属性**，直接当图片打开可能触发 XSS |

> **安全红线**：用户上传的 SVG **必须消毒**（移除 script、on* 属性、外部引用），或者干脆不允许上传 SVG、改成服务端转成 PNG。这是很多 CMS 的经典漏洞点。

### 5.5 透明、位深与色彩空间

| 概念 | 含义 | 常见值 |
| --- | --- | --- |
| **位深** | 每个通道用几位表示颜色 | 8 位/通道（常见）、10/12 位（HDR）、16 位（专业） |
| **通道** | 颜色分量 | RGB（3）、RGBA（4）、CMYK（印刷 4） |
| **alpha 通道** | 透明度 | PNG/WebP 支持半透明；GIF 只有"全透/全不透" |
| **色彩空间** | 颜色的解释基准 | sRGB（网页标准）、Display P3（苹果屏）、Adobe RGB、CMYK |
| **色度抽样** | 视频里减少色度采样 | 4:2:0（常见）、4:2:2、4:4:4 |

> **经典事故**：设计给的图是 CMYK 的（印刷用），直接传到网页上，颜色发灰发暗，因为浏览器按 sRGB 解释 4 个通道。**网页一律用 sRGB 的 RGB 图**。

### 5.6 EXIF：照片里藏着的隐私

手机拍的照片会写入 EXIF：**GPS 坐标、设备型号、拍摄时间、甚至镜头序列号**。

| 风险 | 场景 |
| --- | --- |
| 泄露家庭住址 | 二手平台发闲置物品照片，图里带着拍摄地坐标 |
| 泄露行程 | 发旅行照，别人能还原你的路线 |
| 身份关联 | 设备序列号 + 多张照片可关联同一人 |

**清除方法**：

```bash
exiftool -all= 照片.jpg          # 删除所有元数据
convert 原图.jpg -strip 新图.jpg  # ImageMagick
```

> 大部分社交平台上传时会自动剥离 EXIF，但**邮件、网盘、论坛原图直传不会**。

### 5.7 图片选型

| 场景 | 选 |
| --- | --- |
| 网页照片 | WebP（兼容性优先用 JPEG，追求体积用 AVIF） |
| 网页截图/图标/需要透明 | PNG 或 WebP |
| logo / 图标 / 图表 | **SVG** |
| 印刷 | TIFF 或高质量 JPEG（CMYK） |
| 手机拍照 | HEIC（但分享时转 JPEG） |
| 存档母版 | PNG / TIFF / RAW，**不要用有损格式当母版** |

## 六、音频与视频格式

### 6.1 容器 vs 编码：最容易混的一对概念

这是全篇第二重要的区分（第一是后缀/魔数/MIME）。

```
┌─────────────────────────────────────┐
│  容器 Container（.mp4 / .mkv）       │  ← 盒子：装音轨、视频轨、字幕、metadata
│  ┌───────────────┬───────────────┐  │
│  │ 视频编码        │ 音频编码        │  │  ← 内容：真正的压缩算法
│  │ H.264 / H.265  │ AAC / Opus    │  │
│  └───────────────┴───────────────┘  │
└─────────────────────────────────────┘
```

| 概念 | 回答什么 | 例子 |
| --- | --- | --- |
| **容器 / 封装** | 文件怎么组织多条轨道 | MP4、MKV、AVI、MOV、WebM、FLV、TS |
| **编码 / 编解码器** | 每条轨道的数据怎么压 | H.264、H.265、VP9、AV1、AAC、Opus、FLAC |

所以：

- **`.mp4` 里可能装 H.264，也可能装 H.265、AV1** —— 后缀相同，能不能播完全不同；
- **`.mkv` 只是个盒子**，里面装什么都有可能；
- **`ffprobe` 才能告诉你真相**：

```bash
ffprobe -v error -show_streams 视频.mp4 | grep -E "codec_name|width|height|bit_rate"
```

### 6.2 常见容器

| 容器 | 扩展名 | 特点 | 适合 |
| --- | --- | --- | --- |
| **MP4** | `.mp4` `.m4v` | 兼容性最好，网络标准 | 网页、手机、分享 |
| **MKV** | `.mkv` | 能装几乎任何编码、多音轨多字幕 | 本地收藏、高清片源 |
| **WebM** | `.webm` | 开源，VP9/AV1 + Opus | 网页（免专利） |
| **MOV** | `.mov` | 苹果 QuickTime，剪辑常用 | 后期制作中间文件 |
| **AVI** | `.avi` | 很老，索引结构差 | 老素材，别再用 |
| **FLV** | `.flv` | 已淘汰（Flash 时代） | 兼容老系统 |
| **TS** | `.ts` | 流式，切片友好 | HLS 直播/点播分片 |

### 6.3 常见视频编码

| 编码 | 别名 | 压缩效率 | 专利/授权 | 现状 |
| --- | --- | --- | --- | --- |
| **H.264** | AVC | 基准 | 有，但普遍已付 | **兼容性之王**，哪都能播 |
| **H.265** | HEVC | 比 H.264 省 40~50% | **复杂专利池**，麻烦 | 4K/监控常用，网页支持差 |
| **VP9** | — | 接近 H.265 | 免费 | YouTube/WebM |
| **AV1** | — | 比 H.265 再好 20~30% | **免专利**（AOM 联盟） | 新设备、流媒体在迁 |
| **ProRes** | — | 体积大、质量高 | 苹果 | 剪辑中间格式 |
| **FFV1** | — | 无损 | 免费 | 归档保存 |

> **实际选择**：要"谁的设备都能播"→ H.264；要"省带宽且设备较新"→ H.265 或 AV1；要"剪辑不损画质"→ ProRes/DNxHD。

### 6.4 常见音频编码

| 编码 | 压缩 | 典型码率 | 说明 |
| --- | --- | --- | --- |
| **PCM** | 无压缩 | 1411 kbps（CD） | WAV 里就是它，最大最准 |
| **AAC** | 有损 | 128~256 kbps | MP4 标配，比 MP3 好 |
| **MP3** | 有损 | 128~320 kbps | 老标准，兼容无敌 |
| **Opus** | 有损 | 64~128 kbps | **低码率最优**，WebRTC/WebM 用 |
| **Vorbis** | 有损 | — | OGG 容器，开源 |
| **FLAC** | **无损压缩** | 约 CD 的 50~60% | 无损存档首选 |
| **ALAC** | 无损压缩 | 类似 FLAC | 苹果生态 |
| **AAC-LC / HE-AAC** | 有损 | 低码率 | 流媒体/播客 |

### 6.5 影响画质的那些参数

| 参数 | 含义 | 经验值 |
| --- | --- | --- |
| **分辨率** | 像素尺寸 | 1080p / 4K |
| **帧率 fps** | 每秒多少帧 | 24（电影）、25/30（常规）、60（游戏/运动） |
| **码率 bitrate** | 每秒多少数据 | 1080p 约 5~8 Mbps，4K 约 20~40 Mbps |
| **CRF / 质量因子** | 恒定质量的档位（x264/x265） | 18~23 常用，数字越小越清晰越大 |
| **GOP / 关键帧间隔** | 多久一个可独立解码的帧 | 越小越好拖进度条，但体积大 |
| **色彩抽样** | 4:2:0 等 | 4:2:0 最省，4:4:4 最准 |
| **封装开销** | 容器本身的开销 | 很小 |

> **"码率越高越清晰"只在同编码内成立**。H.265 用 2 Mbps 可能比 H.264 用 4 Mbps 还清晰——**跨编码比码率是没有意义的**。

### 6.6 为什么"改后缀不能改格式"

很多人以为把 `.mkv` 改成 `.mp4` 就能在手机上播。**不能。** 因为：

- 后缀只是名字，**内容没变**；
- 而且 MKV 和 MP4 的**内部结构完全不同**（MKV 是 EBML，MP4 是 ISO BMFF 的 box 结构），播放器按 MP4 的规则去读 MKV 的字节，必然读不懂。

两种"转换"要分清：

| 操作 | 做什么 | 会损失画质吗 | 快慢 | 命令 |
| --- | --- | --- | --- | --- |
| **转封装 Remux** | 只换盒子，编码不动 | **不会** | 很快（秒级） | `ffmpeg -i in.mkv -c copy out.mp4` |
| **转码 Transcode** | 重新编码 | **会**（有损编码） | 很慢（几分钟~几小时） | `ffmpeg -i in.mkv -c:v libx264 -crf 20 out.mp4` |

> **优先用 `-c copy`**：如果只是"容器不兼容"，转封装就够了，既快又无损。只有当编码本身不被目标设备支持时，才需要真转码。

### 6.7 DASH / HLS：为什么在线视频是"一片一片"的

流媒体不传一个整文件，而是切成小片，边下边播：

| 协议 | 索引文件 | 分片 | 特点 |
| --- | --- | --- | --- |
| **HLS** | `index.m3u8`（文本播放列表） | `.ts` 或 `.m4s` | 苹果主推，兼容性最好 |
| **DASH** | `manifest.mpd`（XML） | `.m4s` | 国际标准，码率自适应更灵活 |

好处：**自动切码率**（网慢就切低清）、**快速起播**（先下前几片）、**CDN 缓存效率高**。这也是为什么上一份笔记里 B 站的视频流走的是另一套域名、按分段拉取。

## 七、压缩与归档

### 7.1 压缩 ≠ 归档：一个必须先分清的概念

| 概念 | 做什么 | 例子 |
| --- | --- | --- |
| **归档 Archive** | 把多个文件打包成**一个** | `.tar`、`.zip`（顺便压缩） |
| **压缩 Compress** | 把数据变小 | `.gz`、`.xz`、`.zst`、`.br` |

所以 `.tar.gz` 是**两层**：`tar` 先打包（不压缩），`gzip` 再压缩。而 `.zip` 一个文件同时做了两件事。

| 后缀 | 拆开看 | 含义 |
| --- | --- | --- |
| `.tar` | tar | 只打包，**体积不变** |
| `.tar.gz` / `.tgz` | tar + gzip | 打包后 gzip 压缩 |
| `.tar.bz2` | tar + bzip2 | 压缩率更高、更慢 |
| `.tar.xz` | tar + xz | 压缩率最高、最慢 |
| `.tar.zst` | tar + zstd | **又快又小**，现代首选 |
| `.zip` | 打包 + deflate | Windows 友好 |
| `.7z` | 打包 + LZMA2 | 压缩率强 |
| `.rar` | 打包 + 专有算法 | 需要 WinRAR，**专有** |

### 7.2 常见压缩格式

| 格式 | 算法 | 压缩率 | 速度 | 跨平台 | 说明 |
| --- | --- | --- | --- | --- | --- |
| **zip** | deflate | 中 | 快 | 极好 | 最通用，Windows 原生支持 |
| **7z** | LZMA2 | **高** | 慢 | 好（需 7-Zip/p7zip） | 压缩率最高之一，支持固实压缩 |
| **rar** | 专有 | 高 | 中 | 需付费工具 | **专利/收费**，不建议分发 |
| **gz** | deflate | 中 | 快 | 极好 | 单文件，常用于日志/web 传输 |
| **bz2** | BWT | 高 | 慢 | 好 | 逐渐被 xz/zst 取代 |
| **xz** | LZMA2 | **很高** | 很慢 | 好 | 发布包常用（体积优先） |
| **zst** | Zstandard | 高 | **很快** | 好 | **现代默认**，压缩比接近 gz 但快数倍 |
| **br** | Brotli | 高 | 中 | 好（浏览器原生） | Web 传输专用，文本压缩优于 gzip |

> **给不同场景的默认选择**：**日常交换 → zip**（谁都能开）；**发布/备份 → tar.zst 或 tar.xz**；**Web 传输 → br 或 gzip**；**要极限压缩率 → 7z**。

### 7.3 固实压缩与分卷

| 概念 | 含义 | 影响 |
| --- | --- | --- |
| **固实压缩 Solid** | 把多个文件当成一个大数据块压 | 压缩率更高，但**改/取其中一个文件要解压整块**，损坏影响面大 |
| **分卷** | 拆成 `part1.rar` `part2.rar` | 便于传输大文件；**少一卷就全废** |
| **加密** | zip 传统加密弱，AES-256 才安全 | 7z/rar 支持 AES-256；zip 的老式 ZipCrypto 可被破解 |

### 7.4 命令行速查

```bash
# tar（Linux/macOS 通用）
tar -czf 归档.tar.gz 目录/        # 打包 + gzip
tar -xzf 归档.tar.gz              # 解包
tar -tzf 归档.tar.gz              # 只看内容，不解
tar -caf 归档.tar.zst 目录/       # 自动按后缀选压缩（新版 tar）

# zip
zip -r 归档.zip 目录/
unzip -l 归档.zip                 # 列表
unzip 归档.zip -d 目标目录

# 7z
7z a 归档.7z 目录/ -mx=9 -p密码
7z l 归档.7z

# zstd
zstd -19 大文件                    # 生成 大文件.zst
zstd -d 大文件.zst

# Windows PowerShell
Compress-Archive -Path .\目录\* -DestinationPath 归档.zip
Expand-Archive -Path 归档.zip -DestinationPath .\解压后\
```

> **Windows 原生解压的限制**：资源管理器对 zip 支持良好，但对 `.7z`/`.rar`/`.tar.xz` 需要装 7-Zip；另外**中文文件名在 zip 里乱码**是老问题（因为 zip 历史上用本地编码存文件名），用 7-Zip 或 Bandizip 打开可指定编码。

### 7.5 压缩的共同前提

- **已经压缩过的数据压不动**：JPEG/MP4/PNG 再 tar.gz 几乎不变小（甚至变大一点）；
- **文本压得最狠**：日志、JSON、SQL、源码，通常能压到 10~20%；
- **压缩率与速度是权衡**：`-19` 可能比 `-3` 小 10% 但慢 20 倍。

## 八、文档格式

### 8.1 Office 的真相：docx 就是一个 ZIP

把 `报告.docx` 改名成 `报告.zip` 再解开，你会看到：

```
[Content_Types].xml        ← 声明各部分是什么类型
_rels/.rels                ← 关系表
word/document.xml          ← 正文内容（XML）
word/styles.xml            ← 样式
word/media/image1.png      ← 内嵌图片原图
word/theme/theme1.xml      ← 主题
docProps/core.xml          ← 作者、创建时间等元数据
```

| 结论 | 说明 |
| --- | --- |
| `.docx` `.xlsx` `.pptx` 都是 **ZIP + XML**（叫 OOXML） | 标准号 ECMA-376 / ISO 29500 |
| 可以用代码直接生成/修改 | Python 的 `python-docx`、`openpyxl` 就是这么干的 |
| 体积会随内嵌图片暴涨 | 因为图片原图在 `word/media/` 里 |
| 可以"抢救"损坏文档 | 解压后拿 `document.xml` 里的文字 |

### 8.2 老格式：二进制复合文档

| 老格式 | 新格式 | 老格式本质 |
| --- | --- | --- |
| `.doc` | `.docx` | OLE 复合文档（`D0 CF 11 E0`） |
| `.xls` | `.xlsx` | 同上，二进制记录流 |
| `.ppt` | `.pptx` | 同上 |

> **为什么老 `.doc` 难解析**：它是"文件里的文件系统"，结构复杂且不公开（靠逆向）。而 `.docx` 是明文 XML，随便就能读。这也是"为什么现代工具都只支持 docx"的原因。

### 8.3 PDF：一个"打印结果"格式

PDF 的设计目标是**排版绝对固定**——你在哪看到的，别人打开就是那样。所以它**天生不是为编辑设计的**。

| 概念 | 说明 |
| --- | --- |
| 结构 | 对象（object）+ 交叉引用表（xref）+ 页树 |
| 字体 | **通常嵌入子集**，所以换机器不会变字（但文件变大） |
| 文本层 | 文字版 PDF 有可复制文本层；**扫描件只有图片**，复制不出字 |
| 表单 | AcroForm，可填不可改版式 |
| 加密 | 有"打开密码"和"权限密码"两种，权限密码很弱 |

**两个高频误解**：

| 误解 | 真相 |
| --- | --- |
| 「PDF 里的字能直接编辑」 | 不能。PDF 存的是"在某个坐标画某个字形"，不是段落。所谓"PDF 编辑"多是叠加文字框 |
| 「扫描的 PDF 能搜到字」 | 不能，除非做过 **OCR** 加上文本层 |

> **OCR 的价值**：给扫描件加一层不可见的文本层，就能搜索、复制。工具：Tesseract、Adobe Acrobat、各类在线服务。
>
> **PDF/A** 是长期归档专用子标准（禁止外部依赖、强制嵌字体），档案/合同归档常用。

### 8.4 OFD：国内的 PDF 替代

| 对比 | PDF | OFD |
| --- | --- | --- |
| 来源 | Adobe，国际标准 | 中国国家标准（GB/T 33190） |
| 本质 | 二进制对象结构 | **ZIP + XML**（类 docx 思路） |
| 场景 | 全球通用 | 国内电子发票、电子公文、政务 |

> 收到 `.ofd` 打不开是正常的，需要专用阅读器（如"IloveOFD"、税务/政务 App）。**电子发票多为 OFD 或 PDF 双份**。

### 8.5 电子书

| 格式 | 本质 | 特点 |
| --- | --- | --- |
| **EPUB** | ZIP + XHTML + OPF | **开放标准**，可重排（reflow），最推荐 |
| **MOBI** | 亚马逊私有（老） | 已被 AZW3 取代 |
| **AZW3 / KFX** | 亚马逊私有 | Kindle 专用，有 DRM |
| **PDF** | 固定版式 | 适合图文混排，不适合小屏重排 |
| **TXT** | 纯文本 | 最通用，无排版 |

> EPUB 和 docx 一样是 ZIP：改后缀解压就能看到每一章的 XHTML。**没有 DRM 的 EPUB 可以直接用代码处理。**

### 8.6 源格式 vs 呈现格式

| 类型 | 例子 | 特点 |
| --- | --- | --- |
| **源格式（可编辑）** | `.md`、`.tex`、`.rst`、`.docx`、`.odt` | 人类编辑，可 diff，可版本控制 |
| **呈现格式（交付）** | `.pdf`、`.html`、`.epub` | 排版固定，跨平台一致 |

> **工作流建议**：写作用 Markdown / LaTeX，交付时导出 PDF/HTML。**不要用 Word 当"源"再反复转**，样式会越转越乱。

### 8.7 转换工具

| 转换 | 工具 |
| --- | --- |
| 任意文档互转 | **Pandoc**（md/docx/html/latex/epub 全能） |
| Office 转 PDF | LibreOffice `soffice --headless --convert-to pdf` |
| PDF 提文字 | `pdftotext`（poppler）、`PyMuPDF` |
| 扫描件 OCR | Tesseract、PaddleOCR |
| 图片批量处理 | ImageMagick `convert`/`magick` |
| 音视频转换 | ffmpeg |

```bash
pandoc 输入.md -o 输出.docx
pandoc 输入.docx -o 输出.pdf --pdf-engine=xelatex
soffice --headless --convert-to pdf 报告.docx
pdftotext -layout 文档.pdf -
```

### 8.8 为什么是 docx 而不是 doc（原文第二章展开）

原文给了 doc 的四个结构缺陷和 docx 的八条优势。这里先把两者放在同一张表里对照，再逐条展开。

| 维度 | doc（OLE 复合文档） | docx（OPC / Office Open XML） |
| --- | --- | --- |
| 本质 | 私有二进制"小型文件系统" | ZIP 包 + 一堆 XML 部件 |
| 内部结构 | 扇区（sector）+ FAT + 目录项，靠指针偏移跳转 | 部件（part）+ 关系（rels），按名字寻址 |
| 内容与样式 | 正文、样式、图片、修订混在同一条流里 | 各自独立成部件，`word/document.xml` 只是其中一个 |
| 宏 | 与正文混在一起，不分离 | 默认不含宏；含宏另存 `.docm`，后缀就能看出风险 |
| 损坏后的处境 | 一处拷坏，整份打不开，基本只能靠专用恢复工具 | ZIP 可部分修复，XML 是纯文本可读可手改，图片能从包里直接取出 |
| 规范状态 | 从未完整公开，各家实现靠逆向工程 | ECMA-376 / ISO-IEC 29500 公开标准 |
| 体积 | 大 | 同样内容通常小 **50%~75%**（XML 再被 ZIP 压一层，图片还额外压一次） |
| 程序可处理性 | 二进制黑盒 | `python-docx`、OpenXML SDK、XSLT、正则、diff、全文检索都能上 |

**逐条展开原文的八点优势：**

1. **部件化打包（OPC）**——正文在 `word/document.xml`，样式、编号、页眉页脚、媒体各自成件。程序读一份 300 页文档的标题列表，理论上只需要读一个小部件，不必把整份文件解码。这是"按需读取"的前提，doc 做不到。
2. **体积更小**——因为 XML 是文本，而文本的压缩率极高（重复标签多），再叠一层 ZIP；doc 的二进制流本身已经是紧凑排布，压不动。
3. **打开保存快、内存占用低**——因为不需要先把整条流反序列化成内存对象图，可以流式写部件。文档越大、图越多，差距越明显。
4. **损坏可恢复**——这条在真实事故里最值钱：ZIP 的中央目录坏了还能扫本地文件头抢救部件；XML 坏了肉眼能看出是哪个标签没闭合；而 doc 的 FAT 一旦错位，剩下的字节基本等于随机数。
5. **开放标准、多厂商可实现**——WPS、LibreOffice、Google Docs、Apple Pages 都能读写 docx，兼容性问题主要在"高级排版"和"域/宏"；doc 则是每家的逆向结果各不相同。
6. **安全与合规**——后缀即风险等级（`.docx` 无宏 / `.docm` 有宏），配合容器级签名与加密，DLP、内容审查、元数据清除、脱敏都能做在包结构上。
7. **便于自动化**——服务端生成报表、批量校验、内容 diff、入库检索，在 docx 上都是常规操作；doc 上要先过一层专用库，出错还难定位。
8. **易扩展、向前兼容**——遇到不认识的部件直接忽略（不会崩），命名空间让新特性（图表、SmartArt、主题、OMML 公式、无障碍替代文本、批注与协作）可以平滑加入。

> **一句话**：docx 把"文档"从**读不懂的二进制黑盒**，变成了**可压缩、可拆分、可校验、可编程的开放容器**。这是它取代 doc 的根本原因——不是因为"新"，而是因为它把文档变成了**软件能处理的东西**。

**补：后缀矩阵（看后缀就能判断风险）**

| 后缀 | 含义 | 有无宏 |
| --- | --- | --- |
| `.docx` / `.xlsx` / `.pptx` | 普通文档 | 无 |
| `.docm` / `.xlsm` / `.pptm` | 含宏文档 | **有** |
| `.dotx` / `.xltx` / `.potx` | 模板 | 无 |
| `.dotm` / `.xltm` / `.potm` | 含宏模板 | **有** |

> 所以"收到一个 `.docm`"和"收到一个 `.docx`"，风险等级完全不同——**后缀本身就是一道安检**。这也是 doc 时代做不到的：`.doc` 里有没有宏，不看内容根本不知道。

### 8.9 为什么至今不彻底舍弃 doc（原文第三章展开）

原文六条原因，这里补上"什么时候这条原因才可能被打破"：

| 原因 | 为什么成立 | 什么条件下才会松动 |
| --- | --- | --- |
| **历史存量极大** | 二三十年积累的合同、档案、病历、公文，且不少法规要求"以原始格式长期保存" | 法规明确接受"转换后的等效副本"并给出验证方法 |
| **转换是有损的** | 排版位移、分页变化、域代码失效、OLE 对象丢失、宏被改、修订痕迹异常 | 出现能通过"逐页像素比对"验证的转换工具 |
| **老环境仍在** | Office 2003、老 ERP、行业专用软件、老打印机驱动只认 doc | 这些系统被替换（往往比换 Office 还慢） |
| **遗留自动化依赖** | 大量 VBA、邮件合并模板、OA 流程模板绑死 doc 结构和字段 | 业务流程重做（成本极高） |
| **保真确定性** | 同版本 Word 打开 doc，渲染结果稳定可预期；批量转换后每个模板都要重新验证 | 模板数量可控、且能全量回归 |
| **迁移成本高且无法 100% 保真** | 还要重新测试、重新签章、重新归档 | 通常是"新文档走新格式"而不是"存量全转" |

> **"页码一变，法律文书和标书就可能出问题"**——这句话是整章的核心。合同里的"见第 3 页第 2 条"、标书里的"第 47 页"，一旦重新分页就全部失效。所以这类文档宁可保留原件，也不冒险转格式。

**行业通行策略：读旧写新**

- 新文档**一律 docx**（或 ODF），从源头断掉新增存量
- 旧文档**按需保留**，不搞运动式全量转换
- 必须转换的，用**兼容模式**打开、逐份抽检
- 转换前后留**原件 + 校验清单**，可回退

**批量迁移的验收清单：**

- [ ] 抽样覆盖所有模板类型（不只是正文，还有页眉页脚、目录、脚注、批注、修订）
- [ ] 逐页比对页码与总页数（法律/标书类必须 100% 一致）
- [ ] 检查域代码（目录、交叉引用、页码、日期）是否仍可更新
- [ ] 检查 OLE 嵌入对象（Excel 表、Visio 图、公式编辑器）是否还在
- [ ] 检查宏是否被剥离、数字签章是否失效
- [ ] 打印一份 PDF 抽查（屏幕看着对、打印跑版的情况很常见）

### 8.10 PDF 为什么是交付标准（原文第四章展开）

| 优势 | 具体含义 | 代价 |
| --- | --- | --- |
| **渲染结果一致** | 字体可嵌入、图像可压缩，任何设备任何系统显示和打印都一样 | 文件变大（字体整份塞进去） |
| **适合最终交付** | 合同、发票、简历、论文、标书、说明书、图纸，对方不用装 Office，不怕缺字体跑版 | 对方想改就得有工具，且改了容易露痕迹 |
| **防篡改与法律效力** | 加密、打开/打印密码、权限限制、数字签名（PAdES）、可信时间戳 | 权限是"君子协定"，专业工具能绕 |
| **长期归档** | **PDF/A（ISO 19005）** 专为长期保存设计，要求自包含（嵌字体、不依赖外部资源） | 生成时要专门"另存为 PDF/A"，普通导出不算 |
| **功能丰富** | 表单（AcroForm）、标签化无障碍（PDF/UA）、OCR 扫描件、书签目录、附件 | 这些能力要用对工具才做得出来 |

> **PDF 是"打印结果"，不是"文档"**——原文这句"PDF 是输出和归档格式，并非编辑格式"是整章的题眼。它的设计目标是"让所有人看到的都一样"，而不是"让你接着改"。所以"PDF 改不了"不是缺陷，是它的定位。

**补：PDF 的三种字体状态（决定"能不能复制、会不会跑版"）**

| 状态 | 表现 | 后果 |
| --- | --- | --- |
| 字体**子集嵌入** | 只嵌入用到的字符 | 正常。文件小，显示正确 |
| 字体**完整嵌入** | 整个字体文件塞进去 | 正常，但文件可能几十 MB |
| 字体**未嵌入** | 只记录字体名 | 对方没这个字体就**替换字体 → 跑版**；打印店最容易出这事 |

**补：PDF 常见的五个坑**

| 现象 | 原因 | 怎么判断 |
| --- | --- | --- |
| 复制出来是乱码或空 | 扫描件只有图像层，没有文字层 | 用鼠标能框选吗？框不住就是图像 |
| 打印出来字体变了 | 字体未嵌入 | `pdffonts` 看是否有 emb=no |
| 打开要密码 / 不能打印 | 权限加密（owner password） | 用 `qpdf --show-encryption` 看限制项 |
| 表单填不了 | 是"扁平化"后的表单，或用了 XFA（旧式动态表单） | Acrobat 里看表单域是否存在 |
| 体积巨大 | 图片没压缩（扫描件常见） | `qpdf --optimize-images` 或重新导出 |

**补：数字签名的关键性质**——PDF 签名签的是"**当时那份字节**"。所以**签完之后哪怕只改一个标点，签名立即失效**（会显示"文档已被修改"）。这正是它有法律效力的原因，也意味着"签完还要改"必须走"撤回重签"，不能偷偷改。

### 8.11 其他格式的不可替代之处（原文表格 + 补五行）

| 格式 | 优势场景 |
| --- | --- |
| TXT、MD | 零依赖、体积小、百年可读、天然支持 diff 和 git 版本管理、适合写作与文档站（Markdown 转 HTML/PDF） |
| RTF | 跨平台富文本的老牌通用格式，Word、WPS、macOS 文本编辑都能打开 |
| HTML、XML | Web 原生，可交互、可搜索、可无障碍、可响应式排版 |
| ODT、ODS、ODP（ODF，ISO 26300） | 完全开放、无专利顾虑，LibreOffice 原生，政府采购常用 |
| CSV | 表格数据交换最通用的"最小公约数"，任何工具都能读 |
| JSON、YAML、XML | 机器与机器之间的结构化数据交换，便于程序解析 |
| EPUB | 流式重排，自适应屏幕字号，是电子书行业标准 |
| ZIP、7z | 打包归档、压缩传输，也是 docx、odt、epub、apk 的底层容器 |
| JPG、PNG、SVG、WebP | JPG 适合照片并做有损压缩；PNG 无损并支持透明；SVG 是矢量可缩放；WebP/AVIF 用于现代 Web 压缩 |
| **`.tex`（LaTeX）** | 数学公式、论文排版的事实标准；公式质量任何"所见即所得"都追不上 |
| **`.ofd`** | 国内电子发票、公文、档案的法定格式（自主版式标准），报账/归档绕不开 |
| **`.jsonl`（JSON Lines）** | 一行一条记录，可流式读写、可追加、可并行；大日志和数据集首选，比一个大 JSON 数组健壮 |
| **`.mht` / `.mhtml`** | 把网页连同图片打包成一个文件，法律取证、邮件归档常用 |
| **`.psd` / `.ai` / `.indd`** | 设计源文件（图层、蒙版、专色），导出图永远无法替代源文件 |
| **`.sqlite`** | 单文件数据库，零部署、可整份拷贝，桌面/移动端事实标准 |

> **共同结论**：格式没有"最好"，只有"在这份文件的生命周期里，谁需要读、谁需要改、要保存多久"三点对应的最优选择。docx 解决"可编辑文档的现代化"，PDF 解决"交付与归档的不变性"，而 doc 是历史债务，只能用兼容和渐进迁移处理，不能靠简单删除。

## 九、可执行文件与安装包

### 9.1 各平台的可执行格式

| 平台 | 格式 | 魔数/特征 | 说明 |
| --- | --- | --- | --- |
| Windows | **PE**（`.exe` `.dll` `.sys`） | `MZ` | 从 DOS 头开始，后面是 PE 头 |
| Linux | **ELF**（无后缀也行） | `7F 45 4C 46` | 是否可执行看**权限位**，不看后缀 |
| macOS | **Mach-O** | `FE ED FA CE` 等 | 通用二进制（universal）可含多架构 |
| Android | **APK** | `PK`（是 ZIP） | 内含 `classes.dex` + `AndroidManifest.xml` |
| Java | **JAR** | `PK`（是 ZIP） | 内含 `.class` 字节码 |
| Windows 安装包 | **MSI** | OLE 复合文档 | 走 Windows Installer 服务 |
| Debian/Ubuntu | **.deb** | `!<arch>` | 是 `ar` 归档，内含 control + data.tar |
| RHEL/CentOS | **.rpm** | `ED AB EE DB` | 带元数据库 |
| 通用 Linux | **AppImage** | ELF + 内嵌 squashfs | 免安装，双击即跑 |
| macOS 安装 | **.dmg** / `.pkg` | — | dmg 是磁盘镜像，pkg 是安装包 |

> **注意**：`.apk`、`.jar`、`.docx`、`.epub` **全都是 ZIP**。所以 `file` 只会告诉你"这是 Zip"，要判断具体是什么（比如"这是不是 APK"），得解开看里面有没有 `AndroidManifest.xml`。这就是 `binwalk`、`apktool` 这类工具存在的原因。

### 9.2 "能不能双击运行"取决于什么

不是后缀，而是三件事：

| 条件 | 说明 |
| --- | --- |
| **① 系统认识这个格式** | Linux 上 `.exe` 双击不会跑（除非装了 Wine） |
| **② 有执行权限** | Linux 上 `chmod +x` 才行；Windows 看是否在"允许执行"的位置 |
| **③ 架构匹配** | x86 程序不能直接跑在 ARM 上；32 位程序在纯 64 位系统上可能跑不了 |

> **Linux 的"无后缀可执行"** 是很多人第一次见的困惑：`./myprogram` 能跑，因为它有 `x` 权限且是 ELF，跟名字无关。反过来，把一个脚本改名成 `.exe` 在 Linux 上照样能跑（只要有 shebang 和 x 权限）。

### 9.3 安全上必须知道的四件事

| 风险 | 表现 | 防护 |
| --- | --- | --- |
| **双扩展名伪装** | `照片.jpg.exe`（Windows 默认隐藏已知扩展名，只显示 `照片.jpg`） | **关掉"隐藏已知文件类型的扩展名"** |
| **宏文档** | `.docm` `.xlsm` 里带 VBA 宏，打开就执行 | 禁用宏；不要点"启用内容" |
| **伪装成文档的可执行** | `.pdf.exe`、`.scr`（屏幕保护程序其实也是 exe） | 看真实类型 |
| **脚本后缀** | `.vbs` `.js` `.hta` `.wsf` 双击即执行 | 关联到编辑器而不是运行 |

> **最有效的一条习惯**：在 Windows 资源管理器里关掉「隐藏已知文件类型的扩展名」。这一步能挡掉一大半钓鱼附件。

## 十、镜像、字体与其他

### 10.1 磁盘与光盘镜像

| 格式 | 是什么 | 特点 |
| --- | --- | --- |
| **ISO** | 光盘镜像（ISO 9660 / UDF） | 系统安装盘标准格式，可挂载 |
| **IMG** | 原始磁盘镜像 | 就是逐字节拷贝，简单但大 |
| **VMDK** | VMware 虚拟磁盘 | 支持稀疏、快照 |
| **VHD / VHDX** | Hyper-V / 微软 | Windows 原生挂载 |
| **qcow2** | QEMU/KVM | **写时复制**，快照，占用随实际使用增长 |
| **DMG** | macOS 磁盘镜像 | 苹果生态 |

> 云服务器的"自定义镜像"通常就是这些格式之一。**qcow2 和 VMDK 的稀疏特性意味着「文件大小」和「虚拟磁盘容量」不是一回事**——一个 100 GB 的虚拟盘，文件可能只有 2 GB。

### 10.2 字体格式

| 格式 | 全称 | 曲线类型 | 说明 |
| --- | --- | --- | --- |
| **TTF** | TrueType Font | 二次贝塞尔 | 最通用 |
| **OTF** | OpenType Font | 可为三次（CFF） | 功能更强，支持更多排版特性 |
| **WOFF** | Web Open Font Format | 同 TTF/OTF 但压缩 | 网页用，比 TTF 小约 40% |
| **WOFF2** | WOFF 2.0 | Brotli 压缩 | **网页首选**，再小 30% |
| **TTC / OTC** | 字体集合 | — | 一个文件装多个字体（如"思源黑体"的多字重） |
| **可变字体 Variable** | — | — | 一个文件包含整个字重/字宽轴，可无级调节 |

> **中文字体为什么动辄十几 MB**：汉字数量多（GB18030 有 7 万多字），每个字形都要存轮廓。网页用中文字体要做**子集化**（只保留页面用到的字），否则加载极慢。

### 10.3 单文件数据库与日志

| 格式 | 说明 |
| --- | --- |
| **SQLite**（`.db` `.sqlite`） | 整个数据库就是一个文件，魔数 `SQLite format 3`。手机 App、桌面软件、浏览器都用它 |
| **MDB / ACCDB** | Access 数据库，Windows 生态 |
| **`.log`** | 纯文本，通常按行、可 grep、可轮转 |
| **`.ndjson` / `.jsonl`** | 每行一个 JSON，**流式处理友好**（比一个大 JSON 数组好） |
| **PCAP / PCAPNG** | 抓包文件，Wireshark 用 |
| **`.sql` dump** | 数据库导出脚本，纯文本可 diff |

> **`.jsonl` 值得特别记住**：日志、机器学习数据集、流式输出都用它。因为它是"一行一条"，可以边读边处理，不用把整个文件载入内存。

### 10.4 遇到不认识的格式怎么办

| 步骤 | 做法 |
| --- | --- |
| ① 看真实类型 | `file`、`binwalk`、`xxd -l 64` |
| ② 查魔数 | 对照 [[#附录：魔数速查与术语]] 或网上魔数库 |
| ③ 看里面有什么 | `strings` 捞文本；`binwalk -e` 尝试提取嵌入格式 |
| ④ 判断是不是容器 | 如果是 ZIP/7z/TAR，解开可能就真相大白 |
| ⑤ 找官方工具 | 专有格式（PSD、SKETCH、AI）只能靠原厂或逆向工具 |

## 十一、文件本身：大小、权限、链接、校验

> 这一章不是"格式"，但每天都在坑人，而且和格式问题经常混在一起。

### 11.1 文件大小：为什么 ls 和 du 对不上

| 命令 | 显示什么 | 可能不同的原因 |
| --- | --- | --- |
| `ls -l` | **逻辑大小**（字节数） | — |
| `du -h` | **占用磁盘空间**（按块算） | 块对齐、稀疏文件、压缩文件系统 |

```
ls -lh  sparse.img   →  10G      ← 看起来 10 GB
du -h   sparse.img   →  1.2G     ← 实际只占 1.2 GB（稀疏文件）
```

| 概念 | 说明 |
| --- | --- |
| **块大小** | ext4 默认 4 KB，一个 1 字节的文件也占 4 KB |
| **稀疏文件 Sparse** | 空洞不占空间（虚拟机磁盘常见） |
| **硬链接** | 多个文件名指向同一 inode，`du` 只算一次 |
| **压缩文件系统** | ZFS/Btrfs 开启压缩后，占用小于逻辑大小 |

**单位陷阱**：

| 写法 | 换算 | 谁在用 |
| --- | --- | --- |
| KB / MB / GB | 1000 进制 | 硬盘厂商、网络带宽 |
| KiB / MiB / GiB | 1024 进制 | 操作系统、内存 |

> 所以"1 TB 硬盘只有 931 GB"不是被坑了，是两种进制。**报存储容量时先说清是哪套单位**。

### 11.2 权限：rwx 与数字

```
-rwxr-xr--  1 user group  4096 Jan 1 12:00 文件
 │└┬┘└┬┘└┬┘
 │ │  │  └─ 其他人：r--（只读）
 │ │  └──── 所属组：r-x（读+执行）
 │ └─────── 所有者：rwx（读+写+执行）
 └───────── 类型：- 普通文件，d 目录，l 链接
```

| 数字 | 权限 | 对文件 | 对目录 |
| --- | --- | --- | --- |
| 4 | r | 读内容 | 列出文件名 |
| 2 | w | 改内容 | 增删文件 |
| 1 | x | 执行 | **进入目录**（没有 x 就 cd 不进去） |

常用组合：`644`（普通文件）、`755`（可执行/目录）、`600`（私钥）、`777`（**别用**）。

> **目录的 `x` 权限最容易误解**：有 `r` 没 `x`，你能看到文件名但打不开；有 `x` 没 `r`，你知道路径就能进去但列不出目录。SSH 的 `~/.ssh` 必须是 `700`，`authorized_keys` 是 `600`，否则 sshd 直接拒绝。

### 11.3 硬链接 vs 软链接

| 类型 | 命令 | 本质 | 删原文件后 | 跨分区 | 对目录 |
| --- | --- | --- | --- | --- | --- |
| **硬链接** | `ln 原 新` | 同一 inode 的另一个名字 | **仍能访问** | ❌ 不行 | ❌ 不行 |
| **软链接/符号链接** | `ln -s 原 新` | 存的是路径字符串 | **断链（失效）** | ✅ 可以 | ✅ 可以 |

> Windows 的"快捷方式"类似软链接但更弱（是 `.lnk` 文件，由资源管理器解释）；NTFS 也支持真正的符号链接和目录联接（junction）。

### 11.4 文件名的坑

| 平台 | 限制 |
| --- | --- |
| **Windows** | 非法字符 \ / : * ? " < > 和竖线；保留名 `CON` `PRN` `AUX` `NUL` `COM1~9` `LPT1~9`；传统路径上限 260 字符 |
| **Linux** | 只有 `/` 和 `\0` 非法；长度 255 字节（**注意是字节**，中文占 3 字节） |
| **macOS** | 默认**大小写不敏感**（但保留大小写）；用 NFD 存文件名 |

三个典型事故：

- **中文文件名在 zip 里乱码**：zip 历史用本地编码，跨系统就乱。
- **Windows 拷到 Linux 文件名大小写冲突**：`File.txt` 和 `file.txt` 在 Windows 是同一个，在 Linux 是两个。
- **中文文件名在服务器上是乱码**：上传时用了 GBK，服务器按 UTF-8 解释。

### 11.5 时间戳

| 时间 | 含义 | 什么时候变 |
| --- | --- | --- |
| **mtime** | 修改时间（内容） | 写内容时 |
| **ctime** | 状态变更时间（**不是创建时间**） | 改权限、改属主、改内容都算 |
| **atime** | 访问时间 | 读文件时（很多系统已关闭以省 IO） |
| **创建时间** | birth time | Linux 老文件系统没有；NTFS/APFS 有 |

> 拷文件时用 `cp -p` 或 `rsync -a` 保留时间戳，否则 `mtime` 会变成"现在"，让增量备份/构建缓存全部失效。

### 11.6 校验：怎么确认文件没坏

```bash
sha256sum 文件              # Linux
shasum -a 256 文件          # macOS
certutil -hashfile 文件 SHA256   # Windows
```

| 算法 | 状态 | 用途 |
| --- | --- | --- |
| MD5 | **已不安全**（2004 年即被攻破碰撞） | 只能用于"非恶意"的完整性检查，别用于安全 |
| SHA-1 | **已不安全**（2017 年 SHAttered 实证碰撞） | 同上，逐步淘汰 |
| **SHA-256** | 安全 | 校验、签名、区块链 |
| SHA-512 | 安全 | 更长的 SHA-256 |

> **为什么下载站还提供 MD5**：习惯 + 防"传输损坏"够用。但如果你在验证"这个安装包有没有被换过"，**必须用 SHA-256 或签名**，MD5 可以被构造出碰撞。

### 11.7 文件损坏的常见原因

| 原因 | 表现 | 能否修 |
| --- | --- | --- |
| 传输中断 | 尾部不全，打不开 | 重下；部分格式可修复 |
| 存储介质坏道 | 局部乱码/花屏 | 部分可救（`ddrescue`） |
| 编码/换行被错误转换 | 乱码但结构完整 | 能救（转回编码） |
| 用文本编辑器保存了二进制 | 文件被破坏（编辑器插入了处理） | **不能救** |
| 解压时用了错误密码/算法 | 解压失败 | 换工具 |
| 格式化/误删 | 文件没了 | 停止写入，用恢复工具 |

> **一条铁律**：**绝不要用文本编辑器打开并保存二进制文件**（jpg/mp4/zip/exe）。有些编辑器会自动转换换行或编码，保存的瞬间文件就废了。

## 十二、怎么选格式：决策表

| 我要存/传的东西 | 首选 | 备选 | 别用 |
| --- | --- | --- | --- |
| 纯文字笔记 | `.md` | `.txt` | `.docx`（过度） |
| 要给别人看的正式文档 | `.pdf`（交付）+ `.docx`/`.md`（源） | `.odt` | 只给 docx（排版会变） |
| 表格数据（给人看） | `.xlsx` | `.csv`（带 BOM） | 截图 |
| 表格数据（给程序读） | `.csv` / `.parquet` | `.jsonl` | `.xlsx` |
| 接口数据 | `.json` | protobuf | XML（新项目） |
| 配置 | `.toml` / `.yaml` | `.json`、`.env` | 自创格式 |
| 网页图片 | `.webp` / `.avif` | `.jpg`、`.png` | `.bmp`、`.gif` |
| logo / 图标 | `.svg` | `.png`（多倍图） | 位图放大 |
| 照片存档 | 原始 RAW / `.tif` | `.png` | 反复存 `.jpg` |
| 截图 | `.png` | `.webp` | `.jpg`（文字发虚） |
| 视频分享 | `.mp4`（H.264 + AAC） | `.webm` | `.avi`、`.flv` |
| 视频收藏 | `.mkv`（原编码） | `.mp4` | 转码降质 |
| 音频无损 | `.flac` | `.wav` | `.mp3` 转来转去 |
| 音频通用 | `.mp3` / `.m4a` | `.opus`（网页） | — |
| 打包传输 | `.zip` | `.tar.zst` | `.rar`（收费） |
| 大文件压缩 | `.tar.zst` | `.7z`、`.tar.xz` | `.tar`（不压） |
| 长期归档 | 开放格式 + 校验清单 | PDF/A、FLAC、PNG | 专有格式 |
| 电子书 | `.epub` | `.pdf` | `.mobi` |

### 按场景的一句话原则（对应原文第五章）

| 你的情况 | 选 | 理由 |
| --- | --- | --- |
| 需要反复编辑、要协作 | **DOCX**（协作加批注，或直接上在线文档） | 可编辑是它唯一的存在意义 |
| 要发给别人且版式不能变、要盖章签字、要归档 | **PDF**（归档用 **PDF/A**） | 交付物不承担编辑职责 |
| 纯文字写作、要版本管理 | **Markdown / TXT** | 天然 diff、可 git、百年可读 |
| 数据交换 | **CSV / JSON / XLSX** | 谁都能读，成本最低 |
| 压缩打包 | **ZIP** | 通用性压倒压缩率 |
| 结构性数据长期保存、怕被厂商锁死 | **ODF 或开放标准** | 规范公开，谁都能实现 |

> 再补一条原文没写但同样重要的：**"给我自己留一份源文件"**。任何交付（PDF、图片、视频、网页）都要保留可编辑的母版（docx/md/psd/工程文件）+ 原始素材。交付物是"结果"，母版才是"资产"——只交结果不存母版，三年后想改一个字都得重做。

### 长期归档的四条原则

1. **优先开放、无专利、有公开规范的格式**（PNG、FLAC、PDF/A、EPUB、CSV、JSON）。
2. **保留一份"原始/无损"母版**，衍生文件可以随便压。
3. **附一份校验清单**（`sha256sum` 输出），定期验证没腐烂。
4. **格式会过时**：十年后可能没有能读它的软件。重要资料每 5 年做一次"格式迁移"检查。

## 十三、常见误解与坑

| 误解 | 真相 |
| --- | --- |
| 「改后缀就改了格式」 | 只改了名字，内容一点没变；魔数会揭穿它 |
| 「`.docx` 是二进制所以没法读」 | 它是 ZIP + XML，解压就能读明文 |
| 「`.mp4` 就是 H.264」 | 容器和编码是两回事，同一个 mp4 里可能是 H.265/AV1 |
| 「`.mkv` 改成 `.mp4` 就能播」 | 内部结构不同，必须转封装或转码 |
| 「视频码率越高越清晰」 | 只在**同编码内**成立，跨编码比码率无意义 |
| 「PNG 一定比 JPEG 大」 | 截图/纯色图 PNG 更小；照片才是 JPEG 更小 |
| 「GIF 压缩好」 | 256 色 + 老旧算法，同画质下 WebP/AVIF 小得多 |
| 「CSV 是纯文本所以简单」 | 引号、换行、编码、类型推断，坑最多 |
| 「Excel 打开 CSV 乱码是文件坏了」 | 通常是缺 BOM，Excel 按本地 ANSI 解释了 UTF-8 |
| 「UTF-8 是 Unicode」 | UTF-8 是 Unicode 的一种**编码方式**，还有 UTF-16/32 |
| 「乱码都能转回来」 | 双重编码（`锟斤拷`）后信息已丢，不可逆 |
| 「PDF 能直接编辑文字」 | PDF 存的是坐标上的字形，不是段落 |
| 「扫描版 PDF 能复制文字」 | 没有文本层，除非做过 OCR |
| 「压缩包越大说明压缩率越低」 | 也可能是里面本来就是压缩过的媒体文件 |
| 「MD5 能验证文件安全」 | 能验证完整性，**不能验证安全性**（可构造碰撞） |
| 「Linux 没有后缀所以没格式」 | 有格式，只是不靠后缀判断，靠魔数和权限 |
| 「文件扩展名隐藏很正常」 | 这正是双扩展名钓鱼能成功的原因，建议关掉 |
| 「SVG 是图片所以安全」 | 它是 XML，能内嵌脚本，是 XSS 载体 |
| 「EXIF 无所谓」 | 里面可能有你家 GPS 坐标和设备序列号 |
| 「`ls` 显示 10G 就占了 10G」 | 稀疏文件、块对齐、硬链接都会让 `du` 不一样 |

## 十四、全链路：一个文件的一生

以「你在网页上传一张手机照片，最终被别人看到」为例：

```
① 拍摄
   手机存成 HEIC（HEVC 编码），附带 EXIF：GPS、机型、时间
   ↓
② 上传
   浏览器读文件 → 按 MIME 声明 image/heic → multipart 表单发送
   ↓
③ 服务端校验（关键一步）
   ❌ 只信后缀 .heic        → 可被伪装文件绕过
   ❌ 只信 MIME 头          → 客户端可伪造
   ✔ 读魔数 + 用图像库真正解码一次 → 最可靠
   ↓
④ 处理与转换
   - 剥离 EXIF（保护隐私）
   - 转成 JPEG/WebP/AVIF 多档
   - 生成缩略图
   - 重命名成 hash（避免同名覆盖、避免路径穿越）
   ↓
⑤ 存储
   对象存储（如 OSS/S3），Content-Type 显式设为 image/webp
   ↓
⑥ 分发
   CDN 缓存，按 Accept 头返回 WebP/AVIF 或 JPEG 回退
   ↓
⑦ 展示
   浏览器解码 → 渲染。如果 Content-Type 错成 text/html，
   浏览器不会当图片显示，甚至可能执行里面的脚本
   ↓
⑧ 归档
   原图 + 衍生图 + 校验清单，定期验证 sha256
```

**这条链上每一环都可能出错**，而且现象各不相同：

| 出错环节 | 现象 |
| --- | --- |
| 上传校验只看后缀 | 服务器上出现伪装成图片的脚本（安全事件） |
| 没剥 EXIF | 用户住址泄露 |
| 编码转换失败 | 图片显示为破图 |
| Content-Type 设错 | 浏览器下载而不是显示，或引发 XSS |
| 文件名未重命名 | 同名覆盖、路径穿越（`../../etc/passwd`） |
| 没做多档尺寸 | 手机上加载 5 MB 原图，慢 |
