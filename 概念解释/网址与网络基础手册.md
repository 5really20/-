## 30 秒速览

1. **IP 是逻辑地址，不是设备的身份**——换个网络就变；MAC 才是硬件地址，而 MAC 也能伪造。
2. **域名只是一个名字，DNS 才是控制权**——登记簿上改了指向，门牌号没动，人却全被导走了。所以域名账号要按最高敏感资产对待。
3. **一次访问 = DNS → TCP → TLS → HTTP → 并发子资源**，而且**每换一个域名就把前三步重来一遍**（HTTP/2 多路复用只在同域内省）。B 站把资源拆到 6 类域名，图的就是并发、Cookie 隔离、故障隔离和 CDN 分工。
4. **NAT 省地址，不负责安全；IPv6 更需要防火墙**——没有 NAT 挡着，规则必须显式配，否则内网设备直接裸露在公网。
5. **排障靠顺序，不靠背命令**：先分层定位（能通吗 → 通到哪 → 端口开吗 → 应用回什么），再挑命令。跳过定位直接清缓存、重启，基本是白忙。

> **一句话记住**：**名字（域名）→ 登记簿（DNS）→ 门牌（IP）→ 房子（服务器）**，四层各管各的，出问题时先想是哪一层断了，而不是猜哪个软件坏了。

## 一、先建立全局感：一次访问发生了什么

### 1.1 分层：数据是怎么被包起来的

网络之所以难学，是因为它一层套一层。你写的是「网址」，网卡发的是「电信号」，中间隔着四层翻译。

| 层 | 名字 | 管什么 | 典型代表 | 地址长什么样 |
| --- | --- | --- | --- | --- |
| 应用层 | Application | 你和程序打交道的那层 | HTTP、HTTPS、DNS、SSH | 网址、域名 |
| 传输层 | Transport | 端到端、端口、可靠与否 | TCP、UDP、QUIC | 端口号（0~65535） |
| 网络层 | Network | **寻址与路由转发** | **IP**（IPv4 / IPv6）、ICMP | IP 地址 |
| 链路层 | Link | 同一根网线/同一个局域网内送达 | 以太网、Wi-Fi、ARP | MAC 地址 |

一句话记住分工：**IP 负责「跨网络找到那台机器」，端口负责「找到那台机器上的哪个程序」，域名负责「让人能记住」。**

> IP 是**无连接、不可靠、尽力而为**的：它不保证送达、不保证顺序、不重发。可靠性是 TCP 在传输层补的。所以「网络层丢了包」是正常现象，不是故障。

### 1.2 全链路（先看全景，后面逐段拆）

```
你敲 https://www.bilibili.com/video/BV1xx
   │
   ├─1 浏览器拆 URL：协议 https、主机 www.bilibili.com、路径 /video/BV1xx
   ├─2 查缓存（浏览器 → 系统 → 路由器），没有就发 DNS 查询
   ├─3 DNS 递归解析：根 → .com → bilibili.com 的 NS → 拿到 A 记录 IP
   ├─4 建 TCP 连接（三次握手）到 IP:443
   ├─5 TLS 握手：校验证书、协商密钥（SNI 里带域名）
   ├─6 发 HTTP 请求，服务器返回 HTML
   ├─7 浏览器解析 HTML，再对 JS/CSS/图片重复 2~6
   └─8 渲染出页面
```

后面每一章，就是把这条链上的一个环节拆开。

## 二、IP：给每台机器一个地址

### 2.1 一句话定义

**IP（Internet Protocol，网际协议）**：TCP/IP 协议族里的**网络层**协议，负责**寻址、路由和转发**。它是整个互联网的「邮政系统」——不关心信封里装了什么，只负责把信封从一个邮局转到下一个邮局，直到送达。

### 2.2 IP 干两件事：寻址 + 路由转发

- **寻址**：给每台联网设备一个逻辑地址（IP 地址），让数据知道「发给谁」。
- **路由与转发**：让数据包跨越无数个网络，从源主机一站站转发到目的主机。

补充两个原文没提、但排障必用的字段：

| 字段 | 作用 | 排障时怎么看 |
| --- | --- | --- |
| **TTL**（生存时间） | 每过一个路由器减 1，减到 0 就丢弃并回 ICMP 超时 | `ping` 看返回 TTL 可粗略推对方系统；`traceroute` 就是靠逐级加 TTL 实现的 |
| **MTU**（最大传输单元） | 一个包最大能多大，以太网默认 1500 字节 | 超了要分片；VPN/隧道场景常见「MTU 黑洞」，见 [[#12.3 MTU 黑洞]] |

> 「逻辑地址」这个词是重点：IP 是**逻辑**的，可以变（换网络就换 IP）；MAC 是**物理**的，烧在网卡上。所以「IP 地址」不等于「这台机器」，只等于「这台机器此刻在这个网络里的位置」。

### 2.3 地址从哪来：IANA → RIR → ISP → 你

IP 地址不是天上掉的，是一条严格的分配链：

```
IANA（互联网号码分配局，总部在美国）
  └─ 五大区域注册机构 RIR
       ├─ APNIC      亚太（含中国、日韩、东南亚、大洋洲）
       ├─ ARIN       北美
       ├─ RIPE NCC   欧洲、中东、中亚
       ├─ LACNIC     拉美与加勒比
       └─ AFRINIC    非洲
            └─ ISP / IDC / 云厂商
                 └─ 企业用户 / 你
```

| 角色 | 干什么 | 你要打交道吗 |
| --- | --- | --- |
| IANA | 全球总池，把大段分给 RIR | 不会 |
| RIR | 把段分给各国 ISP、云厂商 | 不会（但查 IP 归属地看的就是它） |
| ISP / 云厂商 | 把 IP 分给用户、绑到你的服务器上 | **会**，你的公网 IP 是从这来的 |
| CNNIC 等 | 中国大陆的 IP 与域名资源参与管理 | 备案时会遇到 |

> 中国大陆的公网 IP 与域名资源由 CNNIC 等机构参与管理，这也是「国内服务器要备案」这套体系的底层原因之一。

### 2.4 IPv4：32 位与 43 亿的误会

**IPv4**：32 位二进制，写成 4 段十进制（每段 0~255），如 `192.168.1.1`。总数 2³² = 4,294,967,296 ≈ **43 亿**。

原文说得对：IP 诞生时（1981 年，RFC 791）没人觉得 43 亿会用完，于是按「class A/B/C」大手大脚地切，一个机构能直接拿一个 /8（1677 万个地址）。结果：

| 时间 | 事件 |
| --- | --- |
| 1981 | IPv4 标准化，地址分类制，浪费严重 |
| 1993 | CIDR 引入（无类域间路由），救了一次 |
| 1994 | NAT 普及，再救一次 |
| 2011-02 | IANA 把最后 5 个 /8 分完 |
| 2011-04 | APNIC 池耗尽（亚太最先） |
| 2015-09 | ARIN 耗尽 |
| 2019-11 | RIPE NCC 耗尽 |
| 现在 | 新地址只能靠回收与**二手交易市场**买，一个 IPv4 地址几美元到几十美元 |

### 2.5 地址不够用了怎么办

| 手段 | 原理 | 代价 |
| --- | --- | --- |
| **CIDR** | 不再按 A/B/C 类切，按需给 /24、/22 | 需要路由聚合，配置复杂些 |
| **NAT** | 一堆内网设备共用一个公网 IP | 破坏端到端，P2P 困难，溯源难 |
| **私有地址复用** | 每家公司内部都用 10.x，互不冲突 | 合并网络时会撞段 |
| **IPv6** | 128 位，理论上用不完 | 改造成本，兼容性 |
| **回收与交易** | 老机构退还、市场买卖 | 贵 |

## 三、子网与掩码：一个地址怎么切成两半

### 3.1 网络号 + 主机号

**一个 IPv4 地址 = 网络号 + 主机号**，靠子网掩码划分：

```
IP:      192.168.1.130
掩码:    255.255.255.0   →  也可写 /24
网络号:  192.168.1.0
主机号:  .130            （可用主机 1~254，.0 是网络地址，.255 是广播地址）
```

**掩码的作用**：区分一个 IPv4 地址里，哪部分是【网络号】，哪部分是【主机号】。

怎么算的：掩码写成二进制就是一串 1 后跟一串 0。**1 的位数 = /n 里的 n**，1 覆盖的位是网络号，0 覆盖的位是主机号。

```
255.255.255.0  = 11111111.11111111.11111111.00000000
                  └────── 24 个 1 ──────┘└─ 8 个 0 ─┘
```

### 3.2 掩码的两种写法：点分十进制与 CIDR

| 写法 | 例子 | 说明 |
| --- | --- | --- |
| 点分十进制 | `255.255.255.0` | 老写法，配置界面常见 |
| CIDR 前缀 | `/24` | 新写法，云上基本都用这个 |

云服务器控制台里填的「子网掩码」、安全组里填的「源地址」，用的都是 CIDR。**`0.0.0.0/0` 就是「所有地址」，等价于「不限制来源」——这是最危险的一条规则。**

### 3.3 ⚠️ 最常错的一处：/8 不是 256 个地址

> **原文写的是**：「IPv4 的一个 /8 网络指的是一个由 256 个 IP 地址组成的网络段。」
>
> **这是错的，而且错得很有代表性。** 256 个地址是 **/24**。`/8` 指的是**前 8 位是网络号**，剩下 24 位全给主机，所以是 2²⁴ = **16,777,216 个地址**（1677 万个）。

搞混的根源通常是这个思维跳步：「255.255.255.0 → 最后一段是 256 个」。**256 只来自最后那个 0 段，而 /n 表示的是「前面有多少位是 1」**。前缀越短，网络越大：

```
/8  ⟶ 255.0.0.0        ⟶ 2^24 = 16,777,216 个地址
/16 ⟶ 255.255.0.0      ⟶ 2^16 =     65,536 个地址
/24 ⟶ 255.255.255.0    ⟶ 2^8  =        256 个地址
```

记忆口诀：**前缀数字越小，管的地盘越大。** `/8` 是「一个国家」，`/24` 是「一个小区」。

### 3.4 常用掩码速查表

| CIDR | 掩码 | 总地址数 | 可用主机数 | 典型用途 |
| --- | --- | --- | --- | --- |
| /8 | 255.0.0.0 | 16,777,216 | 16,777,214 | 超大机构、私有网 A 段 |
| /12 | 255.240.0.0 | 1,048,576 | 1,048,574 | 私有网 172.16/12 |
| /16 | 255.255.0.0 | 65,536 | 65,534 | 一个 VPC 常用 |
| /20 | 255.255.240.0 | 4,096 | 4,094 | 中型子网 |
| /22 | 255.255.252.0 | 1,024 | 1,022 | 小型子网 |
| /24 | 255.255.255.0 | 256 | 254 | **最常见**，一个子网 |
| /25 | 255.255.255.128 | 128 | 126 | 对半切 |
| /26 | 255.255.255.192 | 64 | 62 | |
| /27 | 255.255.255.224 | 32 | 30 | |
| /28 | 255.255.255.240 | 16 | 14 | 小集群 |
| /29 | 255.255.255.248 | 8 | 6 | |
| /30 | 255.255.255.252 | 4 | **2** | 点对点链路 |
| /31 | 255.255.255.254 | 2 | **2**（特例） | RFC 3021 点对点，无网络/广播地址 |
| /32 | 255.255.255.255 | 1 | **1**（特例） | 单个主机，常用于白名单 |

### 3.5 可用主机数的公式与两个例外

**通用公式：可用主机数 = 2^(32−n) − 2**

减掉的 2 个是**网络地址**（主机位全 0）和**广播地址**（主机位全 1），这两个不能分给设备。

两个例外必须记住：

- **/31**：按 RFC 3021，点对点链路两端各一个地址，两个都能用，不减 2。
- **/32**：只有一个地址，就是它自己，常用于安全组白名单、单机路由。

> **云上还有一个隐藏扣减**：阿里云、腾讯云、AWS 的 VPC 子网都会额外保留几个 IP 给系统用（网关、DNS、预留）。例如 AWS 每个子网固定保留 5 个，阿里云保留 1、2、3、253、254 等。所以「/24 有 254 个可用」在云上实际常常只有 249~251 个。规划子网时别卡着上限算。

### 3.6 网络地址、广播地址、网关

| 名词 | 是什么 | 例子（192.168.1.130/24） | 能否配给设备 |
| --- | --- | --- | --- |
| 网络地址 | 主机位全 0，代表「这个网段本身」 | 192.168.1.0 | 不能 |
| 广播地址 | 主机位全 1，发给全网段所有设备 | 192.168.1.255 | 不能 |
| 网关 | 一般是网段第一个可用地址，出网段必经之路 | 192.168.1.1 | 能（但那台设备是路由器） |
| 可用主机 | 剩下的 | 192.168.1.2 ~ .254 | 能 |

> 「网关错了」是云服务器上非常常见的故障：机器能 ping 通同网段，但出不了公网。表现是「内网通、公网不通」——先查网关和路由表。

## 四、特殊地址与私有地址

### 4.1 私有地址（三段）

这三段**只在内网用，不会被路由到公网**。全球每家公司都可以重复使用，互不冲突——这正是 NAT 能省地址的原因。

| 段 | 掩码 | 地址数 | 说明 |
| --- | --- | --- | --- |
| `10.0.0.0/8` | 255.0.0.0 | 1677 万 | A 类私有，大企业/云 VPC 最爱 |
| `172.16.0.0/12` | 255.240.0.0 | 104 万 | 即 172.16.0.0 ~ 172.31.255.255，**不是只有 172.16** |
| `192.168.0.0/16` | 255.255.0.0 | 6.5 万 | 家用路由器默认 |

> **`172.16.0.0/12` 的范围是最容易记错的**：它覆盖 172.16 到 172.31 共 16 个 /16，不是只有 172.16.x.x。看到 `172.20.1.1` 也是私有地址。

### 4.2 环回、链路本地、CGNAT、组播、广播

| 段 | 名字 | 干什么 | 补充 |
| --- | --- | --- | --- |
| `127.0.0.0/8` | 环回 Loopback | 指自己，`127.0.0.1` = 本机 | 整段都是环回，不只是 127.0.0.1；`ping 127.0.0.1` 通只证明**本机协议栈正常**，不证明网卡/网络正常 |
| `169.254.0.0/16` | 链路本地 | DHCP 失败时自动配一个 | Windows 叫 **APIPA**，看到 `169.254.x.x` 就是「没拿到 IP」，网络基本是坏的 |
| `100.64.0.0/10` | CGNAT 专用 | 运营商级 NAT 用 | 你家宽带「公网 IP」如果是这段，说明你在大内网里，做不了端口映射 |
| `224.0.0.0/4` | 组播 Multicast | 一对多发 | `224.0.0.1` 所有主机、`224.0.0.2` 所有路由器；直播、路由协议在用 |
| `255.255.255.255` | 受限广播 | 只在本网段广播 | 不会跨路由器转发 |
| `0.0.0.0/8` | 「本网络」 | 见下一节 | 作为**目标**地址时含义特殊 |

### 4.3 其他保留段（容易漏）

| 段 | 用途 | 为什么值得知道 |
| --- | --- | --- |
| `192.0.2.0/24` | 文档示例（TEST-NET-1） | 教程里出现的「假 IP」，别照抄配置 |
| `198.51.100.0/24` | 文档示例（TEST-NET-2） | 同上 |
| `203.0.113.0/24` | 文档示例（TEST-NET-3） | 同上 |
| `198.18.0.0/15` | 网络设备基准测试 | 见到说明是测试环境 |
| `192.88.99.0/24` | 6to4 中继 | 已废弃（RFC 7526） |
| `240.0.0.0/4` | 保留（原 E 类） | 不可用于公网 |
| `192.0.0.0/24` | IETF 协议分配 | |

### 4.4 0.0.0.0 与 127.0.0.1 到底差在哪（云上高频坑）

这两个在配置文件里长得像，含义完全不同：

| 写法 | 作为**监听地址**的含义 | 作为**目标地址**的含义 |
| --- | --- | --- |
| `127.0.0.1` | **只有本机能连**，外部一律连不上 | 指本机 |
| `0.0.0.0` | **监听所有网卡**，任何来源都能连（只要防火墙放行） | 「本网络」/ 默认路由 |

> **云服务器上的经典事故**：应用配置写成 `bind 127.0.0.1:8080`，然后在前端 Nginx 里反代 `127.0.0.1:8080` —— 这是对的。但如果把数据库也写成 `127.0.0.1` 却又想从外部连，就连不上；反过来写成 `0.0.0.0` 且安全组放行 3306，就是**把数据库暴露到公网**，几小时内必被挖矿脚本扫到。
>
> 记住这条：**监听地址决定「谁能连」，安全组决定「能不能到」，两层都要对。**

## 五、NAT：为什么全家设备只有一个公网 IP

### 5.1 一句话定义

**NAT（Network Address Translation，网络地址转换）**：在数据包经过路由器/网关时，**改写 IP 地址（通常还改端口）**的技术。它允许内部网络的多个设备共享一个或多个公共 IP，从而节省 IP 资源。

原文说「并增强网络安全」——这半句要打折，见 5.3。

### 5.2 SNAT / DNAT / PAT 对照

| 类型 | 改什么 | 方向 | 典型场景 |
| --- | --- | --- | --- |
| **SNAT**（源地址转换） | 改**源** IP | 内网 → 公网 | 家里所有设备上网；云上 NAT 网关让无公网 IP 的机器出网 |
| **DNAT**（目的地址转换） | 改**目的** IP | 公网 → 内网 | 端口映射/端口转发，把公网 `IP:8080` 转到内网 `192.168.1.10:80` |
| **PAT / NAPT**（端口复用） | 改源 IP **+ 源端口** | 内网 → 公网 | 真正的「一个公网 IP 带全家」：靠不同源端口区分不同内网连接 |

> 家里的路由器做的是 **PAT**：你手机访问 A 站、电脑访问 B 站，出去都是同一个公网 IP，但源端口不同，路由器靠一张转换表记住谁是谁。

### 5.3 纠正一句：NAT 不是安全机制

原文说 NAT「增强网络安全」，这个说法常见但不严谨：

- NAT 的**副作用**是外部无法主动连进来（因为没有映射），看起来像防火墙；
- 但它**不是**防火墙：它不做访问控制、不做入侵检测、不做日志审计；
- 一旦你做了端口映射（DNAT），那台内网机器就**直接暴露**了；
- 而且 NAT 让**溯源变难**——出了事，日志里只有公网 IP，要知道是谁得翻运营商的转换表。

正确表述：**NAT 省地址，顺带挡住了「非主动的外部入站」，安全要靠防火墙/安全组，不靠 NAT。**

### 5.4 CGNAT：你家的公网 IP 其实也不是你的

运营商也在缺地址，于是搞了**运营商级 NAT（CGNAT）**，专用段 `100.64.0.0/10`。

```
你家路由器 WAN 口：100.64.23.45   ← 这是运营商内网地址，不是真公网
运营商 CGNAT 出口：  36.152.x.x    ← 几十上百户共用这一个
```

后果：

- 你在路由器上做端口映射**没用**，外面进不来；
- 想自建服务对外提供，只能靠**内网穿透 / 反向代理 / 打洞**；
- 玩游戏提示「NAT 类型严格/受限」就是这个原因。

> 排查方法：看路由器 WAN 口拿到的 IP，如果是 `100.64~100.127` 开头，或者和「查 IP」网站显示的公网 IP 不一致，就是 CGNAT。

### 5.5 NAT 的代价

| 代价 | 具体表现 |
| --- | --- |
| 破坏端到端 | 外部无法主动连内网设备，P2P/BT/游戏联机/远程桌面都受影响 |
| 状态表会满 | 连接数太多时路由器/NAT 网关会丢包、变慢 |
| 日志与溯源困难 | 出事只能查转换表，且很多设备不存 |
| 协议不友好 | FTP、SIP、IPsec 等携带 IP 的协议需要 ALG 特殊处理 |
| 打洞有失败率 | STUN/TURN/UPnP 能缓解，但不是 100% |

## 六、IPv6

### 6.1 128 位与正确写法

原文说「IPv6 是最近几年提出的」——**不对**。IPv6 在 **1998 年**就标准化了（RFC 2460，2017 年更新为 RFC 8200），比很多人以为的早得多；只是部署一直很慢，2012 年才有「世界 IPv6 启动日」，中国大规模推进是 2017 年之后的事。

| 项目 | 数值 |
| --- | --- |
| 位数 | 128 位 |
| 写法 | 8 组，每组 4 位十六进制，冒号分隔 |
| 例子 | `2001:0db8:0000:0000:0000:ff00:0042:8329` |
| 总量 | 2¹²⁸ ≈ 3.4 × 10³⁸（340 万亿亿亿个） |
| 形象说法 | 地球上每一粒沙子都能分到一个 IP，还绰绰有余 |

### 6.2 缩写规则（两条，都要会）

| 规则 | 做法 | 例子 |
| --- | --- | --- |
| ① 省略前导零 | 每组前面的 0 可以删 | `0db8` → `db8`，`0000` → `0`，`0042` → `42` |
| ② 连续全零用 `::` | 一整段连续的 `:0:0:0:` 可缩成 `::`，**全地址只能用一次** | `2001:db8:0:0:0:0:0:1` → `2001:db8::1` |

上面的例子两步合起来：

```
2001:0db8:0000:0000:0000:ff00:0042:8329
   ↓ 去前导零
2001:db8:0:0:0:ff00:42:8329
   ↓ 连续零组用 ::
2001:db8::ff00:42:8329
```

> **为什么 `::` 只能用一次**：否则解析器无法确定每一段该补几个 0，地址就有歧义了。这也是为什么 `2001::1::2` 是非法地址。

### 6.3 地址类型表

| 前缀 | 类型 | 类比 IPv4 | 说明 |
| --- | --- | --- | --- |
| `2000::/3` | 全球单播 Global Unicast | 公网 IP | 现在实际分配的都在这一段（2001、2400 开头常见） |
| `fe80::/10` | 链路本地 Link-Local | 169.254.x.x | 每块网卡自动有，只在同一链路内有效，**必须带 `%网卡名`** 才能用 |
| `fc00::/7` | 唯一本地 ULA | 10.x / 192.168.x | 内网用，实际多用 `fd00::/8` |
| `ff00::/8` | 组播 Multicast | 224.0.0.0/4 | IPv6 **没有广播**，全用组播代替 |
| `::1` | 环回 | 127.0.0.1 | 只有一个地址，不是一整段 |
| `::` | 未指定 | 0.0.0.0 | 监听所有地址 / 表示「还没有地址」 |
| `64:ff9b::/96` | NAT64 | — | 让 IPv6-only 网络访问 IPv4 |
| `2001:db8::/32` | 文档示例 | 192.0.2.0/24 | 教程里的假地址 |
| `2002::/16` | 6to4 | — | **已废弃**（RFC 7526） |

### 6.4 和 IPv4 的关键差异

| 维度 | IPv4 | IPv6 |
| --- | --- | --- |
| NAT | 到处都是 | **设计上不需要**，地址管够，端到端回来了 |
| 地址配置 | DHCP 为主 | **SLAAC**（无状态自动配置）为主，也可 DHCPv6 |
| 邻居发现 | ARP | **NDP**（用 ICMPv6 实现，替代 ARP） |
| 广播 | 有 | **没有广播**，只有组播 |
| 分片 | 路由器可帮分片 | **路由器不分片**，只有源端分，必须靠 PMTUD |
| 首部 | 20 字节起，带校验和 | 固定 40 字节，**无校验和**（靠上下层） |
| 最小 MTU | 576 | **1280** |
| 隐私 | 无 | **临时地址**（RFC 4941），避免用 MAC 生成地址被追踪 |

> **IPv6 没有 NAT 是双刃剑**：好处是端到端直连、P2P 复活；坏处是**每台机器都直接暴露在公网**，防火墙不再是「可选项」而是「必需品」。云上开 IPv6 却不配安全组，等于把机器挂在互联网上裸奔。

### 6.5 云服务器上的 IPv6 要注意什么

- **安全组要单独配 IPv6 规则**：很多云厂商的默认安全组只写了 IPv4 的 `0.0.0.0/0`，IPv6 是 `::/0` 另一条，不开就连不上、开了就全开——**别只改一半**。
- **双栈不等于通**：控制台开了 IPv6，系统里还要有地址、有默认路由、DNS 能解析 AAAA，三层都对才通。
- **AAAA 记录一加，流量就换道**：域名同时有 A 和 AAAA 时，客户端优先走 IPv6。如果 IPv6 链路质量差，你会看到「有的人能开、有的人打不开」。
- **别用 IPv6 做「免备案」的侥幸**：大陆节点的 IPv6 同样在监管范围内。

### 6.6 过渡技术

| 技术 | 做什么 | 现状 |
| --- | --- | --- |
| 双栈 Dual Stack | 同时跑 v4 和 v6 | **主流方案** |
| NAT64 + DNS64 | v6-only 网络访问 v4 资源 | 运营商移动网络常用 |
| 6to4 | 用 2002::/16 隧道 | **已废弃** |
| Teredo | 把 v6 封在 v4 UDP 里 | 基本淘汰 |
| ISATAP | 内网 v6 过渡 | 淘汰 |

## 七、域名：给人用的名字

### 7.1 为什么需要域名

IP 地址是给机器用的，人记不住 `142.250.66.36` 这种数字；就算记住了，常用的地址有几十个，不可能全记对。域名（如 `google.com`）是 IP 的**人类友好别名**，通过 DNS 映射到 IP。

| 对比 | IP | 域名 |
| --- | --- | --- |
| 给谁用 | 机器 | 人 |
| 会不会变 | 会（换机房/换服务商就变） | 一般不变 |
| 谁分配 | IANA → RIR → ISP | 注册局 → 注册商 → 你（**要花钱租**） |
| 能否记住 | 难 | 易 |

> 关键认知：**域名是「租」的，不是「买」的**。你买的是「一定期限内的使用权」，到期不续费会被收回，然后被别人抢注——这是最常见的资产损失。

### 7.2 层级结构：从右往左读

以 `https://www.bilibili.com/` 为例：

```
        www  .  bilibili  .  com  .        ← 末尾其实还有一个点（根）
        │        │          │      │
        │        │          │      └─ 根域  "."，全球 13 组根服务器
        │        │          └──────── 顶级域 TLD "com"，由注册局管理
        │        └─────────────────── 二级域 "bilibili"，品牌 + 数字资产
        └──────────────────────────── 子域/主机名 "www"，业务与调度维度
```

| 层级 | 例子 | 谁管 | 说明 |
| --- | --- | --- | --- |
| 根域 | `.` | ICANN / 根服务器运营方 | 全球 13 组根服务器（有大量镜像），DNS 查询的起点 |
| 顶级域 TLD | `.com` `.cn` `.org` | 各注册局 Registry | 由 ICANN 授权 |
| 二级域 | `bilibili` | 你（通过注册商） | 你真正「拥有」的那一层 |
| 子域 | `www` `api` `cdn` | 你自己随便建 | 不用额外付费，数量不限 |
| 主机名/FQDN | `www.bilibili.com.` | — | 完整写法末尾带根点，配置文件里偶尔会见到 |

> **FQDN 末尾那个点**：`www.example.com.` 表示「这是完整名称，不要再帮我补后缀」。在 DNS 配置文件（BIND zone file）里几乎必须写；在浏览器里可以不写。少写一个点，解析器可能会把本地搜索域拼上去，导致解析到奇怪的地方。

### 7.3 顶级域的三类

| 类型 | 例子 | 特点 |
| --- | --- | --- |
| **gTLD**（通用顶级域） | `.com` `.net` `.org` `.info` | 全球通用，`.com` 最保值 |
| **ccTLD**（国家/地区） | `.cn` `.jp` `.uk` `.io` `.ai` | 由各国管理；`.cn` 需实名 + 备案；`.io`/`.ai` 因含义被科技圈炒贵 |
| **新 gTLD**（New gTLD） | `.app` `.dev` `.shop` `.xyz` | 2012 年后批量开放，便宜但认知度低 |

> `.app` 和 `.dev` 有个特殊点：它们被写进了浏览器**HSTS 预加载列表**，只能走 HTTPS，HTTP 一律拒绝。买之前要想清楚。

### 7.4 注册局、注册商、你：三个角色

| 角色 | 干什么 | 例子 |
| --- | --- | --- |
| 注册局 Registry | 管理某个 TLD 的中央数据库 | Verisign 管 `.com`，CNNIC 管 `.cn` |
| 注册商 Registrar | 零售，帮你下单、续费、改 DNS | 阿里云、腾讯云、Namecheap、Cloudflare |
| 注册人 Registrant | 你，持有使用权 | — |

补充两个概念：

- **WHOIS / RDAP**：查域名归属的公开数据库。现在因隐私法规，个人信息多被隐藏。
- **域名解析服务器 NS**：注册商那里填的「这个域交给谁解析」。可以放在注册商，也可以改成 Cloudflare 等第三方——**改 NS 是接管域名的关键操作，也是劫持的常见手法**。

### 7.5 域名的生命周期（钱最容易丢在这里）

| 阶段 | 时间 | 状态 | 能不能救 |
| --- | --- | --- | --- |
| 正常期 | 注册后 1~10 年 | 正常解析 | — |
| **到期未续费** | 到期当天 | 停止解析，网站立刻挂 | 马上续费，通常原价 |
| **宽限期 Grace Period** | 到期后约 0~45 天（各注册局不同） | 仍归你，可正常续费 | 能，原价 |
| **赎回期 Redemption** | 约 30 天 | 高价赎回 | 能，但要付**赎回费**（几百到上千元） |
| **待删除 Pending Delete** | 约 5 天 | 无法操作 | 不能 |
| **释放** | 之后 | 任何人可注册 | 只能抢注 |

> **必须做的事**：开启**自动续费**、绑定一张不会过期的卡、在日历里设备忘。域名过期导致业务中断 + 被抢注的案例，在中小公司里年年都有。
>
> **还要做**：开启**域名锁（Registrar Lock / 转移锁）**，防止被人用转移码把域名转走。

### 7.6 域名安全

| 风险 | 表现 | 防护 |
| --- | --- | --- |
| 过期被抢注 | 忘记续费 | 自动续费 + 多年注册 + 提醒 |
| 域名劫持/转移 | 域名突然解析到别处 | 开转移锁、注册商账号开 MFA |
| DNS 账号被盗 | 攻击者改 NS 或 A 记录 | DNS 服务商账号单独强密码 + MFA，别和邮箱同密码 |
| 仿冒域名 | `app1e.com`、`bilibiIi.com` | 注册防御性域名；品牌监控 |
| 实名不合规 | `.cn` 未实名被暂停解析 | 按注册商要求提交证件 |

---

### 7.7 域名 ≠ 服务器（最容易搞混的一层）

| 说法 | 对不对 | 说明 |
| --- | --- | --- |
| 域名就是一台服务器 | ✗ | 域名只是个名字，本身不指向任何机器 |
| 注册域名就等于拥有服务器 | ✗ | 注册只是在**注册局"占住"这个名字**，服务器要另买 |
| 域名指向哪台机器由 DNS 决定 | ✓ | 改一条 A 记录，域名就"搬"到别处，服务器一台没动 |
| 域名是资产 | ✓ | 是法律意义上的数字资产，可以交易、可以打官司，但**是租的不是买的** |

打一个比方：**域名是门牌号，DNS 是街道办事处登记簿，服务器是房子**。

- 你可以只买门牌号不盖房（解析到空 IP）→ 访问失败但域名是你的
- 你可以一栋楼挂一百个门牌号（虚拟主机 / SNI）→ 一个 IP 承载上百个站点
- 你可以今天把门牌号登记到 A 栋、明天改到 B 栋（换 IP 不换域名）→ 迁移时用户无感
- 但如果登记簿被人改了（DNS 被劫持），门牌号还在你手里，人却全被导到别人家去了


## 八、DNS：把名字翻译成地址

### 8.1 递归查询与迭代查询

原文写的「从右往左逐级问下来」是对的，但要补一个关键区分：

| 类型 | 谁在做 | 做什么 |
| --- | --- | --- |
| **递归查询** | 你的电脑 → 本地 DNS 服务器 | 「你帮我查到底，给我最终答案」 |
| **迭代查询** | 本地 DNS 服务器 → 各级权威服务器 | 「你不知道？那告诉我该去问谁」 |

原文那段对话，其实描述的是**递归服务器在替你做的迭代过程**：

```
你的电脑 ──递归──▶ 本地 DNS（如 223.5.5.5）
                     │
                     ├─迭代─▶ 根服务器        "."  ：com 归谁管？→ 返回 .com 的 TLD 服务器
                     ├─迭代─▶ .com TLD 服务器  ：bilibili.com 归谁管？→ 返回 ns3/ns4.dnsv5.com
                     └─迭代─▶ bilibili.com 权威：www.bilibili.com 的 A 记录？→ 返回 IP
                     │
你的电脑 ◀──答案────┘（并缓存一段时间，时长由 TTL 决定）
```

### 8.2 一次完整解析的全过程

1. **浏览器缓存**：Chrome 自己存一份（`chrome://net-internals/#dns` 可清）。
2. **操作系统缓存**：Windows `ipconfig /displaydns`，Linux 看 `systemd-resolved`。
3. **hosts 文件**：优先级最高，`C:\Windows\System32\drivers\etc\hosts` 或 `/etc/hosts`。**改了不生效，先怀疑这里。**
4. **本地 DNS 服务器**（运营商 DNS / 你配的 223.5.5.5 / 路由器）。
5. **递归 + 迭代**，拿到结果。
6. **写回各级缓存**，按 TTL 计时。

### 8.3 记录类型表

| 类型 | 作用 | 例子 | 注意 |
| --- | --- | --- | --- |
| **A** | 域名 → IPv4 | `www A 1.2.3.4` | 最常用 |
| **AAAA** | 域名 → IPv6 | `www AAAA 2001:db8::1` | 和 A 共存时客户端优先 v6 |
| **CNAME** | 别名，指向另一个域名 | `blog CNAME www.example.com` | **不能与其它记录同名共存**；**根域（apex）不能用** |
| **MX** | 邮件服务器 | `@ MX 10 mail.example.com` | 数字越小优先级越高 |
| **TXT** | 任意文本 | SPF、DKIM、DMARC、域名所有权验证 | 长度有限，超长要拆段 |
| **NS** | 这个域交给谁解析 | `@ NS ns1.aliyun.com` | 改 NS = 换解析商 |
| **SOA** | 区文件的起始授权 | 含序列号、刷新/重试/过期时间 | 主从同步靠序列号 |
| **SRV** | 服务的位置（主机+端口） | `_sip._tcp SRV 10 5 5060 sip.example.com` | 微软域控、SIP 常见 |
| **CAA** | 允许哪些 CA 给这个域签证书 | `@ CAA 0 issue "letsencrypt.org"` | 防误签/防劫持，**建议都加** |
| **PTR** | 反查：IP → 域名 | 在 `in-addr.arpa` 下 | 邮件服务器反解很重要，否则易被判垃圾邮件 |
| **DS / DNSKEY** | DNSSEC 签名 | — | 防篡改，但配置复杂 |

> **CNAME 的两个硬限制最常踩**：① 同一个名字上不能既有 CNAME 又有 A/MX/TXT（DNS 协议不允许）；② 根域（如 `example.com` 本身）不能设 CNAME，因为根域必须同时有 SOA 和 NS。所以「把根域 CNAME 到 CDN」做不到——云厂商用 **ALIAS / ANAME** 这种私有记录类型来变通，或者干脆用 A 记录。

### 8.4 TTL 与「解析生效要 24 小时」的真相

**TTL（Time To Live）**：这条记录允许被缓存多久，单位秒。

| TTL | 适用场景 |
| --- | --- |
| 60~300 秒 | 正在迁移、做灰度、可能要快速回滚 |
| 600 秒（10 分钟） | 常规业务，平衡灵活与查询量 |
| 3600 秒（1 小时） | 稳定业务 |
| 86400 秒（1 天） | 极少变的记录 |

> **「改了解析要等 24~48 小时」是历史遗留说法**。真实生效时间 = **旧记录在各处缓存里剩余的 TTL**，通常就是几分钟到一小时。如果 TTL 设的是 86400，那确实可能等一天——**所以迁移前一定要先把 TTL 调小，等一个旧 TTL 周期，再改记录。** 这是标准操作顺序，很多人反着做，结果「改完立刻切、用户大面积打不开」。

### 8.5 公共 DNS 与加密 DNS

| 服务商 | IPv4 | 备注 |
| --- | --- | --- |
| 阿里 | `223.5.5.5` / `223.6.6.6` | 国内快，支持 DoH |
| 腾讯 | `119.29.29.29` | 国内快 |
| 114（南京信风） | `114.114.114.114` | 老牌，部分网络有劫持投诉 |
| 百度 | `180.76.76.76` | |
| Google | `8.8.8.8` / `8.8.4.4` | 国内常被干扰 |
| Cloudflare | `1.1.1.1` | 隐私好，国内延迟高 |
| Quad9 | `9.9.9.9` | 拦恶意域名 |

**加密 DNS**：普通 DNS 是明文的，路上能被看、能被改。

| 方式 | 端口 | 说明 |
| --- | --- | --- |
| DoH（DNS over HTTPS） | 443 | 混在 HTTPS 里，最难被封，浏览器已内置 |
| DoT（DNS over TLS） | 853 | 独立端口，企业常见 |
| DoQ（DNS over QUIC） | 853/UDP | 较新 |

### 8.6 DNS 安全：污染、劫持、DNSSEC

| 问题 | 现象 | 应对 |
| --- | --- | --- |
| DNS 污染 | 特定域名返回错误 IP | 换加密 DNS；这是链路层干预，不是你的配置问题 |
| DNS 劫持 | 域名被解析到广告页 | 查 NS 是否被改、查注册商账号是否被盗 |
| 缓存投毒 | 递归服务器缓存了假记录 | 用可信递归服务器；DNSSEC |
| 误签证书 | 别人给你的域名签了证书 | 加 **CAA 记录** |
| 泛解析滥用 | `*.example.com` 指向同一 IP，任意子域都能访问 | 谨慎开泛解析；配合 Host 校验 |

> **DNSSEC 值得知道但不必急着上**：它给 DNS 记录加签名，能防篡改；但配置错会让整个域直接解析失败，且国内支持度参差。中小站点优先级低于「把 CAA 加上、把账号 MFA 开上」。

### 8.7 CDN 与 CNAME

用 CDN 时，流程变成：

```
用户 → DNS 查 www.example.com
     → CNAME 到 example.com.w.cdngslb.com（CDN 厂商的调度域名）
     → CDN 的 DNS 按用户地理位置/运营商返回最近的边缘节点 IP
     → 用户连边缘节点，边缘节点回源到你的服务器
```

所以：**用了 CDN 之后，域名解析里看到的不是你的服务器 IP**，这是正常的。要排查「源站是否正常」，得绕过 CDN 直接测源站 IP。

### 8.8 常见 DNS 故障对照表

| 现象 | 最可能的原因 | 验证方法 | 处理 |
| --- | --- | --- | --- |
| 网站打不开，但 ping IP 通 | DNS 解析失败，或被劫持 | `dig +short 域名`；换 `8.8.8.8` 再查一遍对比 | 查解析记录；改用 DoH/DoT |
| 改了记录很久不生效 | 旧 TTL 还没过期 | `dig 域名` 看返回的 TTL 倒数 | 迁移前先把 TTL 调到 60 秒，改完再调回 |
| 部分地区能访问，部分地区不能 | 权威 NS 不一致 / CNAME 链断裂 / CDN 调度异常 | 用多个异地公共 DNS 分别 dig | 对齐 NS；逐级验 CNAME 指向 |
| 邮件进垃圾箱 | 缺 SPF/DKIM/DMARC，或 PTR 反解不匹配 | `dig TXT 域名`、`dig -x IP` | 补三条 TXT；向 ISP 申请 PTR |
| 域名被指到别处 | 注册商账号被盗 / DNS 控制台被改 | 对比权威 NS 与历史快照 | 双因素 + 域名锁（clientHold / transferLock） |
| 解析结果时对时不对 | 多条 A 记录轮询，其中一条挂了 | 反复 dig 看是否只有某个 IP 失败 | 摘掉坏 IP；上健康检查 |
| 解析被篡改（投毒） | 应答被替换成攻击者 IP | 多个 DNS 对比结果 | DNSSEC + DoH/DoT + 换可信递归 |

> **排查顺序永远是「从根往下逐级问」**：先确认权威 NS 是谁 → 再确认权威服务器返回什么 → 最后才怀疑本地缓存。跳过前两步先清缓存，基本是白忙。

### 8.9 DNS 不是"电话簿"，它是互联网的控制面

原文说「DNS 是互联网的分布式数据库 + 电话簿」——这个比喻对，但会让人**严重低估**它：电话簿只查电话号码，而 DNS 手里握着的是**整个互联网的调度权**。

| 用途 | 记录类型 | 谁在用 |
| --- | --- | --- |
| 域名 → IP（正向解析） | A / AAAA | 浏览器 |
| IP → 域名（反向解析） | PTR | 邮件服务器做反垃圾 |
| 邮件收件路由 | MX | 邮件系统 |
| 服务发现 | SRV | SIP、LDAP、K8s 等 |
| 域名所有权验证 | TXT | 证书签发、搜索引擎、各类 SaaS 接入 |
| 反垃圾邮件 | SPF / DKIM / DMARC（都是 TXT） | 邮件网关 |
| 指定谁能给你签证书 | CAA | CA 机构 |
| 声明只能走 HTTPS | HTTPS / SVCB | 浏览器 |

> **推论**：**谁能改你的 DNS，谁就能接管你的域名**——包括收你的邮件、签你的证书、把用户导去钓鱼站。域名和 DNS 的账号安全等级，应该按"最高敏感资产"对待，而不是"IT 顺手管一下"。

### 8.10 更正一句：不是"一个域名对应一个 IP"

原文第 108 行写「一个域名对应一个 IP」，但它在后面的高频误解里又写「域名和 IP 是多对多」——**后一句才对**，前面那句要改。

| 方向 | 实际情况 | 为什么 |
| --- | --- | --- |
| 一个域名 → 多个 IP | 非常常见 | 负载均衡、CDN、多机房容灾；DNS 轮询或按地域返回 |
| 一个 IP → 多个域名 | 极其常见 | 虚拟主机 / SNI，一台 Nginx 挂几百个站点是常态 |
| 一个域名 → 0 个 IP | 也会发生 | 记录被删、域名过期、DNSSEC 校验失败，解析直接失败 |

> 这也解释了两件事：**为什么"封 IP"遏制不住一个站**（换个 IP 就复活），以及**为什么"封域名"才是有效的**。


## 九、网址（URL）：一个链接拆成七段

### 9.1 完整结构

以 `https://www.bilibili.com/` 为例，完整语法（RFC 3986）是：

```
  https://user:pass@www.bilibili.com:443/video/BV1xx?p=2&t=30#comments
  └─┬─┘   └──┬──┘ └──────┬───────┘└┬┘└─────┬────┘└────┬────┘└───┬───┘
  协议    用户信息      主机 host   端口   路径 path   查询串  片段
 scheme  userinfo                 port              query   fragment
```

| 段 | 例子 | 作用 | 原文覆盖 |
| --- | --- | --- | --- |
| 协议 scheme | `https` | 用什么规则通信，决定默认端口 | ✅ |
| 分隔符 | `://` | 纯语法分隔，告诉解析器「协议名到此结束」 | ✅ |
| 用户信息 userinfo | `user:pass@` | 老式 FTP/HTTP 认证，**现在几乎不用，且是钓鱼重灾区** | ➕ 新增 |
| 主机 host | `www.bilibili.com` | 域名或 IP | ✅ |
| 端口 port | `:443` | 省略则用协议默认端口 | ➕ 新增 |
| 路径 path | `/video/BV1xx` | 服务器上的资源位置 | ➕ 新增 |
| 查询串 query | `?p=2&t=30` | 参数，`&` 分隔，`?` 开头 | ➕ 新增 |
| 片段 fragment | `#comments` | **只在浏览器本地用**，不会发给服务器 | ➕ 新增 |

> **`#` 后面的内容服务器永远看不到**。所以「用 `#` 传参数给后端」是错的；单页应用（SPA）用 `#` 做路由，也是因为它不触发请求。

### 9.2 逐段讲解：以 bilibili 为例

原文的拆解基本正确，这里补齐并标注：

- **`https` 协议**：告诉浏览器「用什么规则和对方说话」，同时决定默认端口 **443**（http 是 80）。
  - **加密**：登录态、观看记录、Cookie 不会被链路中间的路由器/WiFi 看到。
  - **不可降级**：B 站开启了 **HSTS**，浏览器会强制把 `http://www.bilibili.com` 内部升级为 https，不给中间人降级攻击的机会。
  - **身份验证**：服务器必须出示由受信任 CA 签发的证书。
- **`://` 分隔符**：纯语法分隔，让解析器知道「协议名到此结束，后面是主机」。
- **`www` 子域**：在同一个 `bilibili.com` 名下，把不同业务拆到不同主机名上。**它如今的真实含义是路由与调度维度，而不是「一台机器」**——`www` 背后可能是几十台服务器 + CDN 几百个节点。原文这句总结很准。
- **`bilibili` 二级域**：品牌标识 + 法律意义上的数字资产。
- **`.com` 顶级域**：域名层级的最顶层，由注册局（Registry）统一管理。

### 9.3 https 到底做了什么

| 能力 | 具体机制 | 防的是什么 |
| --- | --- | --- |
| **加密** | TLS 握手协商出对称密钥，后续内容全加密 | 被同 WiFi 的人抓包看密码 |
| **完整性** | AEAD（如 AES-GCM）带校验 | 内容被中途篡改（插广告、改下载链接） |
| **身份验证** | 服务器出示证书，浏览器验证证书链到受信根 | 连到假网站（钓鱼站） |
| **防降级** | HSTS 强制 https；TLS 1.3 精简握手 | 中间人把你踹回 http |
| **防重放** | 随机数 + 序列 | 重放攻击 |

**证书链**长这样：

```
根证书（Root CA，预装在系统/浏览器里）
  └─ 中间证书（Intermediate CA）
       └─ 你的服务器证书（example.com）
```

> **最常见的证书事故**：只部署了服务器证书，忘了中间证书，导致「电脑能打开、手机打不开」或「Chrome 能开、某些旧客户端报错」。用 `openssl s_client -connect example.com:443 -showcerts` 或在线 SSL 检测工具检查链是否完整。

**SNI（Server Name Indication）**：TLS 握手时客户端先告诉服务器「我要访问哪个域名」，这样一台服务器一个 IP 也能挂多个 HTTPS 站点。**SNI 在 TLS 1.3 之前是明文的**，所以「你访问了哪个网站」在链路上仍可见——这正是 ECH（Encrypted Client Hello）想解决的问题。

**HSTS 的三个参数**：

```
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
```

| 参数 | 作用 | 坑 |
| --- | --- | --- |
| `max-age` | 浏览器记住「这个域只能 https」多久 | 设太长（如 1 年）后想退回 http 就退不回来 |
| `includeSubDomains` | 所有子域一并强制 | 有子域还没上证书就会被锁死 |
| `preload` | 申请进浏览器内置列表 | 一旦进去，**移除要好几个月**，务必最后再加 |

> 还有 **混合内容（Mixed Content）**：https 页面里加载了 http 的图片/脚本，浏览器会警告甚至拦掉。上线前用开发者工具 Console 搜一遍 `Mixed Content`。

### 9.4 证书：三种验证级别

| 类型 | 验证什么 | 签发时间 | 浏览器表现 | 适合 |
| --- | --- | --- | --- | --- |
| **DV**（域名验证） | 只验证你控制这个域名 | 分钟级 | 小锁 | 绝大多数站点，**免费 Let's Encrypt 就是 DV** |
| **OV**（组织验证） | 额外验证公司真实存在 | 1~3 天 | 小锁（点开看详情有公司名） | 企业站、需要展示资质 |
| **EV**（扩展验证） | 更严格的人工审核 | 数天 | **地址栏绿色公司名已被主流浏览器取消** | 现在性价比低 |

**免费证书**：Let's Encrypt（90 天，自动续期）、ZeroSSL、云厂商免费 DV 证书（通常 1 年，单域名）。

> **证书透明（CT, Certificate Transparency）**：所有公开 CA 签发的证书都会记录进公开日志。好处是「别人偷偷给你的域名签证书」会被发现；坏处是**你的子域名会被人从 CT 日志里扒出来**做资产测绘。所以「内部域名用公网 CA 签证书」等于主动公开资产清单。

### 9.5 网址里的陷阱

| 陷阱 | 例子 | 怎么防 |
| --- | --- | --- |
| **@ 符号欺骗** | `https://www.bank.com@evil.com/` 实际访问 evil.com | 看 `@` 后面那一段才是真域名；现代浏览器已明显提示 |
| **同形字（homograph）** | `аpple.com` 里的 `а` 是西里尔字母 | 看 punycode（`xn--` 开头）；别点陌生链接 |
| **子域伪装** | `bilibili.com.evil.com` 真域名是 evil.com | **从右往左读**，倒数第二个点前才是你的域 |
| **超长域名** | 前面塞一堆看似正规的词 | 同上 |
| **短链** | `t.cn/xxx` 看不出目标 | 先展开再点 |
| **开放重定向** | `you.com/jump?url=evil.com` | 站点侧要校验白名单 |

### 9.6 为什么大站要把资源拆到很多个域名上（bilibili 实例）

打开 B 站首页，浏览器实际会碰到至少 **6 类域名**：

| 类别 | 例子 | 装什么 |
| --- | --- | --- |
| 主站 | `www.bilibili.com` | HTML 骨架 |
| 静态资源 | `s1.hdslb.com` | JS / CSS |
| 图片 | `i0.hdslb.com` | 封面、头像 |
| 接口 | `api.bilibili.com` | XHR / JSON |
| 视频流 | `mcdn.bilivideo.com`、`upos-*.bilivideo.com` | DASH 分片 |
| 实时长连接 | `wss://broadcastlv.chat.bilibili.com` | 弹幕 |

**四条原因，依次是性能、安全、可用性、成本：**

| 原因 | 具体机制 | 不这么做的后果 |
| --- | --- | --- |
| **并行加载** | HTTP/1.1 下浏览器对单域名只开 6 条并发连接；拆域名直接突破这个上限 | 首屏资源排队，页面"一片一片"地长出来 |
| **Cookie 隔离** | 主站 Cookie（`SESSDATA`、`bili_jct`）有几 KB；静态资源域不带 Cookie | 每个图片请求白背几 KB；还多一个 XSS 偷 Cookie 的面 |
| **故障隔离** | 图片 CDN 挂了，页面框架和播放器照常 | 一个环节挂 = 整页白屏 |
| **CDN 分工** | 图片可缓存一年（`max-age=31536000`），HTML 一秒都不能缓存 | 一套缓存策略套所有资源，要么慢要么脏 |

> **代价别忽略**：每换一个域名就要重走一遍 **DNS + TCP + TLS**，而 HTTP/2 多路复用**只在同一个域名内**省连接。所以拆域名是"用建连开销换并发和隔离"——拆到 6~10 个是甜点，拆到几十个反而更慢。这正是 `dns-prefetch` / `preconnect` 存在的理由。


## 十、端口与 HTTP

### 10.1 端口的三个区间

端口号 16 位，范围 **0~65535**（0 保留）。

| 区间 | 名称 | 说明 |
| --- | --- | --- |
| 0~1023 | 系统端口 / 知名端口 | 绑定需要 root 权限 |
| 1024~49151 | 注册端口 | 应用常用，普通用户可绑 |
| 49152~65535 | 动态/临时端口 | 客户端发起连接时随机用 |

> **「端口被占用」怎么查**：`ss -tunlp | grep 8080`（Linux）或 `netstat -ano | findstr 8080`（Windows）。
>
> **「改了端口还是连不上」**：三处都要放行——① 服务监听地址（别写成 127.0.0.1）、② 系统防火墙（firewalld/ufw/iptables）、③ **云安全组**。第三处最容易被忘。

### 10.2 常见端口表

| 端口 | 服务 | 云上要不要对公网开 |
| --- | --- | --- |
| 20/21 | FTP 控制/数据 | ❌ 用 SFTP 代替 |
| 22 | SSH | ⚠️ 只对自己 IP 开 |
| 23 | Telnet | ❌ 明文，禁用 |
| 25 | SMTP | ⚠️ 云厂商多默认封禁，需申请解封 |
| 53 | DNS | ⚠️ 只对必要来源 |
| 80 | HTTP | ✅ |
| 443 | HTTPS | ✅ |
| 3306 | MySQL | ❌ **绝不**对公网 |
| 5432 | PostgreSQL | ❌ |
| 6379 | Redis | ❌ **绝不**（未授权访问重灾区） |
| 27017 | MongoDB | ❌ |
| 3389 | RDP | ❌ 或只对自己 IP |
| 9200 | Elasticsearch | ❌ |
| 2375 | Docker API（未加密） | ❌ **开了等于把服务器 root 给人** |
| 6443 | Kubernetes API | ⚠️ 限来源 |

### 10.3 HTTP 版本演进

| 版本 | 年份 | 关键变化 | 解决的问题 |
| --- | --- | --- | --- |
| HTTP/1.0 | 1996 | 每个请求一个连接 | — |
| HTTP/1.1 | 1997 | **keep-alive** 长连接、**Host 头**（一个 IP 挂多站）、管道化 | 连接复用 |
| HTTP/2 | 2015 | 二进制分帧、**多路复用**、HPACK 头压缩、（服务端推送已弃用） | 队头阻塞（应用层） |
| HTTP/3 | 2022（RFC 9114） | 基于 **QUIC（UDP 443）**，0-RTT 建连 | TCP 层队头阻塞、弱网切换 |

### 10.4 TLS 版本

| 版本 | 年份 | 说明 |
| --- | --- | --- |
| SSL 3.0 | 1996 | **已废弃**，禁用 |
| TLS 1.0 / 1.1 | 1999 / 2006 | **已废弃**（RFC 8996），主流浏览器不再支持 |
| TLS 1.2 | 2008 | 目前最低要求 |
| TLS 1.3 | 2018（RFC 8446） | 1-RTT 建连、0-RTT 恢复、精简套件、**默认前向保密** |

> 云上配 HTTPS 时，把「TLS 最低版本」设成 **1.2**。设 1.0/1.1 会过不了等保/合规扫描；设 1.3-only 又会挡掉一批老客户端。

## 十一、接回云服务器：这些概念在云上长什么样

### 11.1 四种「IP」别搞混

| 名字 | 是什么 | 能不能换 | 计费 |
| --- | --- | --- | --- |
| **私网 IP** | VPC 内的地址，机器之间用它通信 | 一般固定，改要停机或迁移 | 免费 |
| **固定公网 IP** | 买机器时分配，和实例绑定 | 释放实例就没了 | 含在带宽里 |
| **EIP（弹性公网 IP）** | 独立持有的公网 IP，可解绑再绑到别的机器 | **能**，可秒级漂移 | 按持有时间+流量/带宽 |
| **虚拟 IP（VIP）** | 用于高可用漂移的逻辑地址 | 能 | 免费 |

> **EIP 的核心价值是「IP 不跟着机器死」**：机器坏了，把 EIP 解绑、绑到备用机上，域名不用改。这是做容灾最便宜的一招。

### 11.2 VPC 与子网规划

```
VPC: 10.0.0.0/16（6.5 万个地址）
 ├─ 子网 A: 10.0.1.0/24   可用区 1   ← Web
 ├─ 子网 B: 10.0.2.0/24   可用区 2   ← Web（跨 AZ 高可用）
 ├─ 子网 C: 10.0.10.0/24  可用区 1   ← 数据库（不开公网）
 └─ 子网 D: 10.0.20.0/24  可用区 1   ← 缓存/中间件
```

三条规划经验：

1. **别用 `192.168.0.0/16` 做 VPC**——和家里/公司网络撞段，以后连 VPN 或做混合云会非常痛苦。用 `10.x` 或 `172.16.x`。
2. **按角色划子网**，不要所有机器挤一个 /24。数据库单独一个子网，天然就能用 ACL 隔离。
3. **预留扩展空间**：别一上来就把 /16 切成 256 个 /24 用完，留一半。

### 11.3 安全组 vs 网络 ACL

| 维度 | 安全组 | 网络 ACL |
| --- | --- | --- |
| 作用对象 | 实例/网卡级别 | 子网级别 |
| 是否有状态 | **有状态**（出去的回包自动放行） | **无状态**（进出要分别写规则） |
| 规则顺序 | 全匹配，**没有优先级，拒绝优先** | **按序号从上到下，先匹配先生效** |
| 默认行为 | 默认拒绝入站、放行出站 | 默认放行全部 |
| 典型误配 | 只开了入站 80，忘了出站 | 放行了入站却忘了出站回包 |

> 记住这个差异：**安全组「有状态」，所以只管进不管出；ACL「无状态」，进出都要写。** 只配 ACL 不配出站规则，现象是「请求能进来、响应出不去」。

### 11.4 NAT 网关与端口映射

| 需求 | 用什么 | 说明 |
| --- | --- | --- |
| 内网机器要能访问公网（下载依赖、调外部 API） | **NAT 网关（SNAT）** | 机器不需要公网 IP，出口 IP 固定，对方做 IP 白名单很方便 |
| 公网要访问内网某台机器的某端口 | **DNAT / 端口映射 / 负载均衡监听** | 尽量用 LB，不要直接把数据库端口映射出去 |
| 内网和另一个 VPC 互通 | 对等连接 / 云企业网 | 注意网段不能重叠 |

### 11.5 域名上线顺序：备案 → 解析 → 证书

大陆节点的正确顺序，别搞反：

1. **买域名 + 实名认证**（`.cn` 必须实名，否则解析会被暂停）
2. **买服务器**（大陆节点需要备案；香港/海外免备案）
3. **提交 ICP 备案**（需要服务器实例、幕布拍照或人脸核验），管局审核 7~20 个工作日
4. **备案通过后**才把域名解析到大陆服务器 —— 没备案就解析，80/443 会被拦截
5. **申请/上传证书**，配 HTTPS，开 HSTS
6. **30 日内做公安联网备案**

> **最容易翻车的一步**：先解析了、站也能开了，过几天被拦——因为没备案。备案是「先审批后解析」，顺序不能反。

### 11.6 IP 被封与被 DDoS

| 情况 | 表现 | 处理 |
| --- | --- | --- |
| 被 DDoS 打到黑洞 | 全站不通，控制台提示「清洗/黑洞」 | 等解封，或换 EIP + 上高防 |
| IP 被墙 | 国内访问不了，海外正常 | 换 IP（EIP 解绑重绑）；域名套 CDN |
| IP 被列黑名单 | 邮件发不出、部分网站拒绝 | 查 MXToolbox 等黑名单库，申请移除 |
| 被扫描爆破 | 日志里大量 SSH 失败登录 | 换端口 + 密钥登录 + fail2ban + 只放行自己 IP |

> **DDoS 期间的应急操作**：把 EIP 解绑（流量就打不到你），换一个新 EIP 绑上，改 DNS。这是最土但最快的止血法——前提是你的 TTL 设得够短。

## 十二、排障工具箱

### 12.1 命令表

| 目的 | Linux | Windows | 看什么 |
| --- | --- | --- | --- |
| 通不通 | `ping host` | `ping host` | 延迟、丢包、TTL |
| 路径 | `traceroute host` / `mtr host` | `tracert host` | 哪一跳开始不通 |
| 解析 | `dig host` / `nslookup host` | `nslookup host` | 返回的 IP 对不对、TTL 多少 |
| 指定 DNS 查 | `dig @223.5.5.5 host` | `nslookup host 223.5.5.5` | 排除本地 DNS 问题 |
| HTTP 细节 | `curl -v https://host` | `curl.exe -v` | 状态码、证书、重定向 |
| 端口通不通 | `nc -vz host 443` / `telnet host 443` | `Test-NetConnection host -Port 443` | 拒绝 vs 超时含义不同 |
| 谁在监听 | `ss -tunlp` | `netstat -ano` | 监听地址是 0.0.0.0 还是 127.0.0.1 |
| 本机地址 | `ip addr` / `ip route` | `ipconfig /all` | IP、掩码、网关、DNS |
| ARP 表 | `arp -a` / `ip neigh` | `arp -a` | 同网段有没有冲突 |
| 抓包 | `tcpdump -i any port 443` | Wireshark | 到底发出去没有、有没有回 |
| 带宽测速 | `iperf3 -c host` | 同 | 是带宽问题还是程序问题 |

> **「拒绝」和「超时」要分清**：`Connection refused` = 端口没人监听或被拒绝（服务没起/防火墙 reject）；`Connection timed out` = 包被丢了（安全组没放行/路由不通/机器挂了）。这一条能省掉一半排查时间。

### 12.2 十类典型故障

| 现象 | 最可能的原因 | 先查什么 |
| --- | --- | --- |
| 域名打不开，IP 能开 | DNS 没配/配错/没生效 | `dig 域名`，看返回 IP |
| 解析到旧 IP | TTL 缓存未过期 | `dig` 看 TTL，等或换 DNS 测 |
| 内网通、公网不通 | 网关/路由表错，或没绑公网 IP | `ip route`、控制台看 EIP |
| 本机能连、外面连不上 | 监听 127.0.0.1 / 防火墙 / 安全组 | `ss -tunlp` 三处逐一放行 |
| 时通时不通 | 多台后端其中一台坏 / 带宽打满 | 查 LB 健康检查、看带宽监控 |
| HTTPS 报证书错 | 证书过期 / 链不全 / 域名不匹配 | `openssl s_client -showcerts` |
| 有的地方能开、有的不能 | AAAA 记录指向了坏掉的 IPv6 | 临时删 AAAA 验证 |
| 上传大文件失败 | MTU 黑洞 | 见 12.3 |
| 访问慢但能开 | 跨地域/跨境、没上 CDN | `mtr` 看哪一跳慢 |
| 突然全站 502 | 后端进程挂了 / 端口变了 | 查后端进程与 Nginx 日志 |

### 12.3 MTU 黑洞

**现象**：小文件能传、小页面能开，但**一旦传大文件或访问大响应就卡死**。

**原因**：路径上某一段 MTU 更小（VPN/隧道常见 1400 甚至 1280），包被要求分片，但分片所需的 ICMP 消息被防火墙拦了（PMTUD 失效），于是大包直接黑洞。

**排查**：

```bash
# Linux：带「不分片」标志试探最大可通包大小
ping -M do -s 1472 example.com
# 逐步减小 1472，直到通为止；通的数值 + 28 = 实际 MTU
```

**处理**：调小网卡 MTU（`ip link set dev eth0 mtu 1400`），或让应用层减小包大小。

## 十三、纠错与常见误解（原文修正 + 补充）

### 13.1 原文两处必须改正

| 原文 | 问题 | 正确说法 |
| --- | --- | --- |
| 「IPv4 的一个 /8 网络指的是一个由 256 个 IP 地址组成的网络段」 | **数值错了一个量级** | `/8` = 2²⁴ = **16,777,216** 个地址；**256 个是 `/24`** |
| 「IPv6：最近几年提出的」 | **时间错** | **1998 年**标准化（RFC 2460），2017 年修订为 RFC 8200；部署慢不等于提出晚 |
| 「一个域名对应一个 IP」（第 108 行） | **与自己后文矛盾** | **多对多**：一个域名可指向多个 IP（LB/CDN），一个 IP 可承载上百个域名（虚拟主机/SNI） |

### 13.2 其他高频误解

| 误解 | 真相 |
| --- | --- |
| 「NAT 能增强安全」 | NAT 只省地址、顺带挡住非主动入站；安全靠防火墙/安全组 |
| 「127.0.0.1 和 0.0.0.0 差不多」 | 前者只本机可连，后者对所有网卡开放；**配错就是把服务暴露或锁死** |
| 「ping 通就说明网络没问题」 | ping 走 ICMP，业务走 TCP/UDP，很多环境单独封 ICMP |
| 「域名解析改完要等 24 小时」 | 真实等待 = 旧 TTL 剩余时间；迁移前应先调小 TTL |
| 「HTTPS 就是加密」 | 还有身份验证、完整性、防降级；证书链不全一样会报错 |
| 「有公网 IP 就能被访问」 | 还要：安全组放行 + 系统防火墙放行 + 服务监听 0.0.0.0 |
| 「IPv6 开了就通」 | 地址、路由、DNS(AAAA)、安全组 v6 规则，四样都要对 |
| 「CNAME 可以随便指」 | 根域不能 CNAME；同一名字不能和其他记录共存 |
| 「私有地址就是安全的」 | 私有只代表不可路由；一旦做了端口映射就完全暴露 |
| 「端口改了别人就扫不到」 | 能降低噪音，但全端口扫描照样能找到；安全靠密钥+限制来源 |
| 「域名买了就永久是我的」 | 是租用；到期有宽限期→赎回期→释放，恢复要花钱甚至抢不回 |
| 「备案是服务器的事」 | 备案绑的是「域名 + 主体 + 接入服务商」，换服务商要变更接入 |
| 「IP 地址就是设备的唯一编号」 | 不是。IP 是**逻辑**地址，换个网络就变；MAC 才是硬件地址，**而 MAC 也能伪造** |
| 「IPv6 就是地址更长」 | 远不止。报头简化、SLAAC 无状态自动配置、取消广播、端到端直连、NDP 替代 ARP，都是**架构级变化** |
| 「有了 IPv6 就不需要防火墙」 | 恰恰相反。没有 NAT 挡着，防火墙规则必须**显式配置**，否则内网设备直接暴露在公网 |
| 「域名和 IP 是一一对应」 | **多对多**：一个域名 → 多个 IP 做 LB/CDN；一个 IP → 上百个域名靠虚拟主机/SNI |
| 「DNS 只是查 IP」 | 它还管邮件路由（MX）、服务发现（SRV）、反垃圾（SPF/DKIM/DMARC）、证书签发授权（CAA） |

## 十四、全链路串讲：从敲下回车到页面出现

```
【你】输入 https://www.bilibili.com/video/BV1xx
   │
   ├─ 1. 浏览器拆 URL
   │      scheme=https  host=www.bilibili.com  path=/video/BV1xx
   │      端口未写 → 用 https 默认 443
   │
   ├─ 2. 查缓存 → 没有 → 发 DNS 查询（UDP 53，可能走 DoH 443）
   │      本地DNS 递归 → 根 → .com → bilibili 的 NS → A/AAAA 记录
   │      拿到 1.2.3.4，缓存 TTL 秒
   │
   ├─ 3. TCP 三次握手 到你 1.2.3.4:443
   │      SYN → SYN+ACK → ACK
   │
   ├─ 4. TLS 握手
   │      ClientHello（带 SNI=www.bilibili.com）
   │      服务器返回证书链 → 浏览器验证到根 CA + 查吊销 + 查域名匹配
   │      协商密钥 → 之后全加密
   │
   ├─ 5. HTTP 请求 GET /video/BV1xx
   │      经过 CDN 边缘节点 → 回源到源站
   │      可能经过：LB（四层/七层）→ Nginx → 应用 → 数据库
   │
   ├─ 6. 返回 HTML（200 OK，Content-Type，Cache-Control）
   │
   ├─ 7. 浏览器解析 HTML → 对 JS/CSS/图片再走 2~6（可能复用连接，HTTP/2 多路复用）
   │
   └─ 8. 渲染 → 页面出现
```

**每一环出问题，现象都不一样**——这就是为什么排障要按链路顺序查，而不是乱试：

| 断在哪 | 现象 |
| --- | --- |
| DNS | 「域名找不到」，IP 能开 |
| TCP | 「连接超时」或「连接被拒绝」 |
| TLS | 「证书错误」「不安全」 |
| HTTP | 4xx/5xx 状态码 |
| 应用 | 502/504，或页面空白 |
| 前端 | 页面错乱、白屏、Console 报错 |

### 14.2 用 bilibili 走一遍完整七步（实测版）

**第 1 步 · DNS 解析**

浏览器缓存 → 系统 DNS 缓存 → `hosts` → 本地递归解析器（如 `223.5.5.5`）→ 问根「`.com` 归谁」→ 问 `.com`「`bilibili.com` 的 NS 是 `ns3/ns4.dnsv5.com`」→ 问 `dnsv5.com`「`www` 的 A / AAAA 记录」→ 拿到 IP。

这个 IP 很可能是 **CDN 边缘节点**，按你的运营商和地理位置调度。实测 `bilibili.com` 曾解析到 `47.103.24.173`、`8.134.50.24`、`139.159.241.37`，**分属不同云厂商网段，且会随调度变化**——这就是"同一个域名在两个人手里解析出不同结果"的直接证据。

**第 2 步 · TCP 握手**，目标是 443 端口。

**第 3 步 · TLS 握手**

- `ClientHello` 里带 **SNI = www.bilibili.com**（一个 IP 挂多个站点时，靠它选证书）
- 服务器返回 **GlobalSign** 签发的证书，浏览器逐项校验：域名匹配 `*.bilibili.com` ✔ 有效期 ✔ 证书链可信 ✔ 未被吊销 ✔
- 协商出 **HTTP/2**，或 **HTTP/3（QUIC —— B 站已大面积启用）**

**第 4 步 · 发 HTTP 请求**（注意：路径和查询串会发出去，`#fragment` 不会）

```
GET /video/BV1xx411c7mD/?spm_id_from=... HTTP/2
Host: www.bilibili.com
Cookie: SESSDATA=...; bili_jct=...      // 登录态，所以必须 HTTPS
Referer: https://www.bilibili.com/
User-Agent: ...
```

**第 5 步 · 服务器处理**

网关按 `/video/` 路由到视频服务 → 查视频元数据 → 校验登录态与地区版权 → 返回 HTML 骨架。B 站是**服务端渲染 + 前端 hydration**：先给你一个能看的骨架，JS 到了再"接管"成可交互页面。

**第 6 步 · 浏览器解析 HTML，并发拉子资源**

| 资源 | 地址 | 说明 |
| --- | --- | --- |
| 静态资源 | `https://s1.hdslb.com/bfs/static/...js` | 另一域名，免带 Cookie |
| 封面图 | `https://i0.hdslb.com/bfs/archive/xxx.jpg` | 另一域名，走 CDN |
| 接口 | `https://api.bilibili.com/x/web-interface/view?bvid=BV1xx...` | XHR |
| 弹幕 | `wss://broadcastlv.chat.bilibili.com/...` | WebSocket 长连接 |

**第 7 步 · 点播放 → 请求视频流**

`mcdn.bilivideo.com` / `upos-*.bilivideo.com` 等，**又是另一套 CDN 域名**，按线路就近分发，**分段（DASH）拉取**——不是下一个整 mp4，而是一片一片要，边下边播、按清晰度切换。

### 14.3 这个例子里藏着的四条通用规律

| 规律 | 含义 | 你会撞上的场景 |
| --- | --- | --- |
| 域名分层 = 调度分层 | 页面/接口/图片/视频各一套域名，各自独立调度 | 自建站也常把 `static.` `img.` `api.` 拆开 |
| 换一个域名就重来一遍建连 | DNS + TCP + TLS 全套 | 首屏慢常因为"域名太多"或"没做 DNS 预取" |
| 静态可长缓存，HTML 不能 | 缓存策略按资源类型定 | 上线后用户看到旧页面 = HTML 被缓存了 |
| 大型站没有"整包下载" | 一切皆分片 | 断点续传、拖进度条、切清晰度都靠分段 |

> **回到云服务器**：你买一台 ECS 建站，默认就是"一个域名 + 一个 IP + 一台机器"。上面这套是**规模化之后才不得不做的优化**——先跑通，再拆。拆早了只是给自己加维护成本。
