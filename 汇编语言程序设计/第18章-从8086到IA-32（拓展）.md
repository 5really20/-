## 18.1 为什么必须走出实模式

**前面 17 章我们一直在 8086 的「实模式」下工作。但现代计算机早就不用实模式了——原因有四大硬伤。**

**实模式的四大局限：**

| 局限 | 具体表现 | 后果 |
|---|---|---|
| **① 内存太小** | 地址总线 20 位 → 只能寻址 **1MB** | 现代机器内存以 GB 计，1MB 连操作系统都装不下 |
| **② 段太小** | 段最大 **64KB**，且段边界必须落在 16 字节边界上 | 写大程序必须频繁切换段寄存器 |
| **③ 没有保护** | 任何程序都能改写任何内存、执行特权指令 | **一个程序出错会拖垮整个系统**；无法实现多任务 |
| **④ 地址不独立** | `物理地址 = 段地址 × 16 + 偏移地址` | 程序直接面对物理内存，**无法实现虚拟内存** |

**第 ③ 条是最致命的：**

```
   实模式下：你在 DOS 里写一句
        mov ax, 0
        mov es, ax
        mov word ptr es:[0], 1234h
   
   —— 就把中断向量表的 0 号表项改了！没有任何机制阻止你。
   
   同样，任何程序都能执行 cli（关中断）、hlt（停机）、out（直接操作端口）。
   ★ 这在现代操作系统里是不可想象的：一个用户程序就能让整机停摆。
```

**保护模式（Protected Mode）的解决之道：**

| 实模式的问题 | 保护模式的机制 |
|---|---|
| 1MB 限制 | **32 位地址总线 → 4GB** 线性地址空间（80386 起） |
| 64KB 段限制 | 段界限可以到 **4GB**（描述符里有 20 位界限 + 粒度位） |
| 无权限检查 | **特权级（0~3）**：用户程序（级 3）不能碰内核数据（级 0），**执行特权指令会触发异常** |
| 地址不独立 | **分页机制**：线性地址经页表映射到物理地址，**每个进程有独立地址空间** |

**从实模式到保护模式的切换（了解即可）：**

```
   ① 建立 GDT（全局描述符表），用 lgdt 指令把它加载到 GDTR 寄存器
   ② 把 CR0 寄存器的 bit0（PE，Protection Enable）置 1
   ③ 执行一条远跳转，刷新 CS，正式进入保护模式
   ④ （可选）再置 CR0 的 bit31（PG，Paging Enable）开启分页
```

**现代操作系统的启动流程（把前面 17 章串起来）：**

```
   加电 → CPU 处于【实模式】，从 FFFF:0000 开始执行 BIOS
        ↓
   BIOS 检测硬件、建立中断向量表（第 12、13 章）
        ↓
   int 19h 读引导扇区（第 17 章的 int 13h！）
        ↓
   引导程序（bootloader，如 GRUB）在实模式下运行，
   把操作系统内核读入内存
        ↓
   bootloader【切到保护模式】，跳到内核入口
        ↓
   内核建立完整的分页表，启动各子系统
        ↓
   （64 位机器还要再切到【长模式 Long Mode】）
```

> **重点**：**你在第 12、13、17 章学的 BIOS 中断、中断向量表、`int 13h` 读扇区——它们全都真实地存在于现代计算机的启动过程中，只是在你看到登录界面之前就完成了使命。** 实模式是「历史起点」，保护模式是「当下现实」，而**两者的接口就是那段 bootloader 代码**。

> **★ 教材延伸**：Intel 处理器一共有**三种工作模式**——**实模式**（8086 模式，我们学了 17 章的那个）、**保护模式**（本节起要讲的）、**虚拟 8086 模式**（在保护模式之上「假装」出多个 8086，让老的 DOS 程序能同时跑；Windows 的 DOS 窗口就靠它）。教材王爽《汇编语言》（第 4 版）把这三种模式收在**「附注 1 Intel 系列微处理器的 3 种工作模式」**（教材第 327 页），是本节最好的补充读物。

## 18.2 保护模式的核心概念

### 段选择子（Segment Selector）

**保护模式下，段寄存器里装的不再是「段地址」，而是一个 16 位的「段选择子」。**

```
   段选择子（16 位）
   ┌──────────────────────────┬────┬──────────┐
   │      索引 Index（13 位）  │ TI │ RPL(2位) │
   └──────────────────────────┴────┴──────────┘
   15                        3    2  1       0
```

| 位域 | 名称 | 含义 |
|---|---|---|
| **bit 15~3** | **索引（Index）** | 描述符在描述符表中的**序号** |
| **bit 2** | **TI** | Table Indicator：**`0` = 查 GDT，`1` = 查 LDT** |
| **bit 1~0** | **RPL** | Requested Privilege Level：**请求特权级（0~3）** |

**★ 为什么「索引 × 8」才是描述符在表中的偏移？**

```
   因为每个段描述符固定占 8 个字节。
   
   索引 = 3  →  偏移 = 3 × 8 = 24
   
   ★ 处理器内部把「索引」先左移 3 位（相当于 ×8），再加上描述符表基址，
     就得到了描述符的地址。这也是为什么索引占 13 位：
     13 位索引 × 8 字节 = 最多 8192 个描述符。
```

**8086 与保护模式的段寄存器语义对比：**

| 对比项 | 实模式（8086） | 保护模式（80386 起） |
|---|---|---|
| 段寄存器内容 | **段地址**（物理地址的高 16 位） | **段选择子**（索引 + TI + RPL） |
| 段寄存器宽度 | 16 位 | **仍然是 16 位**（内容含义变了） |
| 隐藏部分 | 无 | **有 64 位描述符高速缓存**（加载选择子时从描述符填充） |
| 段基址 | 段地址 × 16（固定） | **从描述符里读出（可以是任意 32 位值）** |
| 段长度 | 固定 64KB | **由描述符的段界限决定（可到 4GB）** |

**★ 关键点：段寄存器还是 16 位宽，但处理器内部给它配了一份「隐藏的描述符缓存」。所以 `mov ds, ax` 这条指令在保护模式下要做很多事（查表、检查特权级、填缓存），而不只是改一个数字。**

### 全局描述符表 GDT

**GDT（Global Descriptor Table，全局描述符表）是一个「段描述符数组」，全局唯一。**

**每个段描述符 8 字节（64 位），按位划分如下：**

```
   位编号   63      56 55   52 51      48 47      40 39      32 31              16 15              0
          ┌─────────┬────────┬───────────┬───────────┬───────────┬─────────────────┬─────────────────┐
          │ 基址    │ 标志   │ 界限      │ 访问      │ 基址      │ 基址            │ 界限            │
          │ 24~31   │ G D/B L│ 16~19     │ 权限字节  │ 16~23     │ 0~15            │ 0~15            │
          │ (8 位)  │  AVL   │ (4 位)    │ (8 位)    │ (8 位)    │ (16 位)         │ (16 位)         │
          └─────────┴────────┴───────────┴───────────┴───────────┴─────────────────┴─────────────────┘
            bit 56~63  bit 52~55  bit 48~51   bit 40~47   bit 32~39   bit 16~31        bit 0~15
```

**更清晰的字段划分（按字节顺序）：**

```
   ┌────────────┬───────────────────────────────────────────────┐
   │ bit 0~15   │ 段界限低 16 位                                │
   │ bit 16~31  │ 段基址低 16 位                                │
   │ bit 32~39  │ 段基址 bit 16~23                              │
   │ bit 40~47  │ ★ 访问权限字节：P | DPL(2) | S | Type(4)      │
   │ bit 48~51  │ 段界限 bit 16~19                              │
   │ bit 52~55  │ 标志：G | D/B | L | AVL                       │
   │ bit 56~63  │ 段基址 bit 24~31                              │
   └────────────┴───────────────────────────────────────────────┘
```

> **★ 记忆要点：描述符里「段基址」被拆成三段（bit16~31、bit32~39、bit56~63）、「段界限」被拆成两段（bit0~15、bit48~51）**——这是 Intel 为了和 80286 的描述符格式兼容而留下的历史包袱。**你不需要背下这张图，只要记住：8 字节、里面有 32 位基址、20 位界限、粒度位 `G`、特权级 `DPL`。**

**关键字段解释：**

| 字段 | 含义 |
|---|---|
| **段基址（32 位）** | 段的起始线性地址（**不再需要 ×16**） |
| **段界限（20 位）** | 段的长度上限 |
| **G（粒度位）** | **`G = 0`**：界限单位是**字节**；**`G = 1`**：界限单位是**4KB 页**（此时 20 位界限最大可表示 `FFFFF × 4KB = 4GB`） |
| **P（存在位）** | `P = 1` 表示该段在内存中 |
| **DPL（2 位）** | **描述符特权级（0~3）**，决定谁能访问这个段 |
| **S** | `S = 1` 表示代码段/数据段；`S = 0` 表示系统段（如任务门） |
| **Type（4 位）** | 段的类型（可读/可写/可执行/是否已访问等） |

**GDTR 寄存器：**

```
   GDTR（48 位）
   ┌──────────────────────┬──────────────────────┐
   │  GDT 基址（32 位）     │  GDT 界限（16 位）    │
   └──────────────────────┴──────────────────────┘
   
   ★ 用 lgdt 指令加载：「lgdt [gdt_ptr]」
   ★ GDT 的第 0 个描述符必须全 0（称为「空描述符」），
     这样「选择子 = 0」就代表「空段」，一旦使用就立刻异常 —— 便于抓错。
```

### 特权级

**保护模式有 4 个特权级：**

```
   级 0  ──  最高（内核态）：操作系统内核
   级 1  ──  （很少用）
   级 2  ──  （很少用）
   级 3  ──  最低（用户态）：应用程序
```

**三个容易混淆的术语：**

| 术语 | 全称 | 含义 |
|---|---|---|
| **CPL** | Current Privilege Level | **当前特权级** = `CS` 的 bit 1~0，即「现在正在执行的代码」的级别 |
| **DPL** | Descriptor Privilege Level | **描述符特权级** = 段描述符里写的「这个段允许谁来访问」 |
| **RPL** | Requested Privilege Level | **请求特权级** = 段选择子的 bit 1~0，「我以什么身份请求访问」 |

**访问规则（不必背细节，理解思想即可）：**

```
   ★ 要访问一个数据段：要求 MAX(CPL, RPL) ≤ DPL
   ★ 要跳进一个代码段：要求 CPL = DPL（同级转移）
   ★ 特权级只能通过「门」（调用门、中断门）受控地提升
```

**为什么需要特权级？**

```
   ★ 让「用户程序」和「操作系统」隔离：
        · 用户程序不能直接读写内核数据和内核代码
        ★ 用户程序执行特权指令（cli、hlt、out、lgdt、mov cr0, ...）
          会触发「通用保护异常 #GP」，被操作系统捕获
   
   ★ 这就是「一个程序崩溃不会拖垮整个系统」的实现基础 ——
     也是「蓝屏 / 段错误」这类现象的来源。
```

## 18.3 32位寄存器与32位寻址方式

### 寄存器的扩展

**80386 把 8086 的 16 位寄存器扩展成了 32 位，命名规则是加前缀 `E`（Extended，扩展）。**

| 16 位 | 32 位 | 传统用途 |
|---|---|---|
| `AX` | **`EAX`** | 累加器（乘除、函数返回值） |
| `BX` | **`EBX`** | 基址寄存器 |
| `CX` | **`ECX`** | 计数（循环、串操作） |
| `DX` | **`EDX`** | 数据（乘除的高位、I/O） |
| `SP` | **`ESP`** | 栈指针 |
| `BP` | **`EBP`** | 栈帧基址指针 |
| `SI` | **`ESI`** | 源变址 |
| `DI` | **`EDI`** | 目的变址 |
| `IP` | **`EIP`** | 指令指针 |
| `FLAGS` | **`EFLAGS`** | 标志寄存器（32 位） |

**关键理解：16 位寄存器是 32 位寄存器的「低半部分」。**

```
        EAX（32 位）
   ┌──────────────────────┬──────────────┐
   │       高 16 位        │   AX（16 位）│
   │                      ├──────┬───────┤
   │                      │  AH  │  AL   │
   └──────────────────────┴──────┴───────┘
    31                   16  15   8   7  0
   
   ★ 修改 AX 会改变 EAX 的低 16 位，高 16 位保持原值。
   ★ 8086 上 AX 拆成 AH/AL 的技巧在 32 位下依然有效。
```

**新增的段寄存器：`FS` 和 `GS`。**

```
   8086：CS、DS、SS、ES（4 个）
   80386：CS、DS、SS、ES、FS、GS（6 个）

   ★★ 注意：这 6 个段寄存器全都是【16 位】的！★
      —— 它们装的是「段选择子」（16 位），不是 32 位地址。
      80386 里变宽的是通用寄存器和 EIP，段寄存器本身没变宽。
      （这正是「平坦模型」的思路：段寄存器只用来做权限检查和选描述符，
        真正的 32 位地址由 EIP 和通用寄存器给出。）
```

**`FS`/`GS` 在现代操作系统里的用途（32 位与 64 位正好相反，别记混）：**

| 系统 | 32 位模式 | 64 位模式 | 指向什么 |
|---|---|---|---|
| Windows | **`FS`** | **`GS`** | **TEB**（Thread Environment Block，线程环境块）——32 位下 `FS:[0]` 是 SEH 异常处理链的头 |
| Linux | **`GS`** | **`FS`** | **TLS / TCB**（线程局部存储 / 线程控制块）——glibc 靠它找到 `errno`、线程栈等每线程数据 |

> **★ 一句话记忆：Windows 和 Linux 对 `FS`/`GS` 的分工是反的，而且 32 位与 64 位也是反的。** 你不用背，只要知道「**段寄存器在现代系统里主要不是用来寻址，而是用来快速找到『当前线程的私有数据』**」——因为换线程时只要改一个段寄存器基址，比改一堆全局变量快得多。

### 32 位寻址方式（本章最实用的部分）

**8086 的寻址方式受限严重（第 7、8 章讲过）：**

```
   [bx+si]、[bx+di]、[bp+si]、[bp+di]、[bx+idata]、[bx+si+idata]……
   ★ 只有 4 种合法配对
   ★ 没有比例因子（无法直接寻址「元素大小为 4 的数组」）
   ★ 参与寻址的只能是 bx/bp/si/di
```

**32 位寻址方式完全解放了这些限制：**

```
   ★★★ 有效地址 = 基址寄存器 + (变址寄存器 × 比例) + 位移 ★★★
   
   ★ 基址寄存器：EAX、EBX、ECX、EDX、ESI、EDI、EBP、ESP（8 个都行！）
   ★ 变址寄存器：EAX、EBX、ECX、EDX、ESI、EDI、EBP（ESP 不能做变址）
   ★ 比例（Scale）：1、2、4、8
   ★ 位移（Displacement）：8 位或 32 位常量
```

**这正好对应高级语言里的三种数据结构：**

| 数据结构 | 寻址方式 | 例子 |
|---|---|---|
| **普通变量 / 结构体成员** | `[基址 + 位移]` | `mov eax, [ebx+8]` |
| **数组元素** | `[基址 + 变址 × 比例]` | `mov eax, [ebx+esi*4]` |
| **结构体数组的元素成员** | `[基址 + 变址 × 比例 + 位移]` | `mov eax, [ebx+esi*4+12]` |

**★ 第三行正是 8086 的 `[bx+si+idata]` 的 32 位升级版！**

**对比表（8086 vs IA-32）：**

| 对比项 | 8086（16 位） | IA-32（32 位） |
|---|---|---|
| 可用基址寄存器 | `BX`、`BP` | **8 个通用寄存器都行** |
| 可用变址寄存器 | `SI`、`DI` | **除 `ESP` 外都行** |
| 合法配对 | **只有 4 种**（`bx+si`/`bx+di`/`bp+si`/`bp+di`） | **任意组合** |
| 比例因子 | **无** | **1、2、4、8** |
| 位移 | 8 位或 16 位 | 8 位或 32 位 |
| 一次寻址范围 | 64KB（段内） | **4GB（平坦模型下）** |

**示例：访问一个 `int` 数组 `a[10]` 的 `a[i]`（`i` 在 `ESI` 中，`a` 的地址在 `EBX` 中）**

```asm
    mov eax, [ebx + esi*4]      ; ★★ 一条指令完成！
                                ;   ebx = 数组首地址
                                ;   esi = 下标 i
                                ;   4   = sizeof(int)
```

**对比 8086 上要做同样的事（第 7、8 章）：**

```asm
    ; 8086：a[i]，每个 int 占 2 字节（16 位下 int 通常是 2 字节）
    mov ax, si                  ; i
    mov cl, 2
    shl ax, cl                  ; ★ 手工乘 2（或 mul）
    mov bx, ax                  ; bx = i × 2
    mov ax, [bx + a]            ; 再从数组基址 + 偏移取值
                                ;   ★ 而且 a 的基址必须在一个段内（≤64KB）
```

> **重点**：**32 位寻址方式把「乘元素大小」这件事交给了硬件。** 从 8086 的「手工移位 + 加法」到 IA-32 的「一条 `[ebx+esi*4]`」，这就是「编译器生成的代码越来越短、CPU 要做的越来越多」的缩影。**理解了 `[基址+变址×比例+位移]`，你就理解了 C 语言数组和结构体访问的编译结果。**

## 18.4 平坦内存模型与分页

### 平坦内存模型

**保护模式虽然把段基址变成了 32 位任意值，但现代操作系统几乎都采用「平坦内存模型（Flat Memory Model）」：**

```
   ★ 把所有段的基址都设为 0，界限都设为 4GB（0xFFFFF，G=1）
   
   于是：  线性地址 = 段基址 + 偏移 = 0 + 32 位偏移 = 32 位偏移
   
   ★★ 「段」实际上被「架空」了 —— 只剩下一个 32 位的偏移量在寻址。
```

**平坦模型下段寄存器的角色：**

| 段寄存器 | 平坦模型下的值 | 作用 |
|---|---|---|
| `CS` | 指向「代码段描述符」（基址 0、可执行） | 只为配合硬件，实际不起偏移作用 |
| `DS`、`ES` | 指向「数据段描述符」（基址 0、可读写） | 同上，**任何数据都能用任意段寄存器访问** |
| `SS` | 指向「数据段描述符」（基址 0、可读写） | 栈也用同一片 4GB 空间 |
| `FS`、`GS` | 指向特殊数据段（**基址不为 0**） | **Windows 的 TEB / Linux 的 TLS**——这是平坦模型下**唯一还在真正用「段基址」的地方**（32 位 Windows 用 `FS`、64 位 Windows 用 `GS`；32 位 Linux 用 `GS`、64 位 Linux 用 `FS`） |

**平坦模型带来的最大简化：**

```
   ★ 不再需要关心「数据在哪个段」「段会不会超过 64KB」
   ★ C 语言的「指针」就等价于一个 32 位偏移（= 32 位线性地址）
   ★ mov eax, [ebx] 永远是「从 ebx 指向的地址取 4 字节」
```

### 分页机制

**分页（Paging）负责把「线性地址」翻译成「物理地址」。**

**三级地址转换的完整流程（这一节的核心图）：**

```
   程序里的地址
   ┌──────────────┐
   │ 逻辑地址      │   「段选择子 : 偏移」
   │ (CS:EAX 之类) │
   └──────┬───────┘
          │  ① 分段（Segmentation）
          │     查 GDT/LDT 中的描述符，段基址 + 偏移
          ▼
   ┌──────────────┐
   │ 线性地址      │   32 位（0 ~ FFFFFFFF）
   │ (Linear)     │
   └──────┬───────┘
          │  ② 分页（Paging）
          │     查页目录 + 页表
          ▼
   ┌──────────────┐
   │ 物理地址      │   送到内存总线上
   │ (Physical)   │
   └──────────────┘
   
   ★★ 平坦模型下第 ① 步「段基址 = 0」，所以线性地址 = 偏移。
      真正起作用的是第 ② 步分页。★★
```

**两级页表的索引结构：**

```
   线性地址（32 位）
   ┌────────────┬────────────┬──────────────────┐
   │ 目录项 10 位│ 页表项 10 位│  页内偏移 12 位   │
   └─────┬──────┴─────┬──────┴────────┬─────────┘
         │            │               │
         ▼            ▼               │
   ┌──────────┐  ┌──────────┐         │
   │ 页目录    │  │ 页表      │         │
   │ (CR3 指向)│─►│          │         │
   └──────────┘  └────┬─────┘         │
                      │               │
                      ▼               ▼
                 ┌─────────────────────────┐
                 │  物理页框（4KB）          │
                 │  物理地址 = 页框基址+偏移  │
                 └─────────────────────────┘
   
   ★ 页大小 = 4KB = 2^12 → 所以页内偏移占 12 位
   ★ 10 位目录项 → 最多 1024 个页目录项
   ★ 10 位页表项 → 每个页表最多 1024 项
   ★ 一个页目录可覆盖 1024 × 1024 × 4KB = 4GB（正好整个 32 位空间）
```

**分页的三大作用：**

| 作用 | 说明 |
|---|---|
| **虚拟内存** | 页不在物理内存时触发「缺页异常（#PF）」，操作系统把页从磁盘调入——**程序可以用比物理内存更大的地址空间** |
| **进程隔离** | **每个进程有独立的页目录（`CR3` 不同）**，同一个线性地址在不同进程里映射到不同物理页——**一个进程无法访问另一个进程的内存** |
| **内存共享与保护** | 页表项里有「只读/可写/用户/内核」权限位；共享库的代码页可以被多个进程共享映射 |

**相关控制寄存器：**

| 寄存器 | 作用 |
|---|---|
| **`CR0`** | **bit0 = PE**（保护模式使能）、**bit31 = PG**（分页使能） |
| **`CR2`** | **发生缺页异常时的线性地址** |
| **`CR3`** | **页目录的物理基址**（进程切换时切换它） |
| **`CR4`** | 各种扩展功能开关（如 PAE、PSE） |

> **重点**：**「段」解决的是「访问权限与段的边界」，「页」解决的是「地址映射与隔离」。** 在平坦模型下，**分段基本退化成「权限检查」**（CS 的 DPL 决定你能执行哪些指令），**而分页承担了虚拟内存的全部工作。** 这也解释了为什么现代操作系统一开就是保护模式 + 分页，而实模式那套「段×16+偏移」彻底成了历史。

## 18.5 汇编与C语言混合编程

**为什么要混合编程？三个真实理由：**

| 理由 | 例子 |
|---|---|
| **性能热点** | 视频编解码、加密算法、图像处理的内层循环 |
| **访问硬件 / 特殊指令** | `in`/`out` 端口操作、`rdtsc` 读时间戳、`cpuid` 取 CPU 信息、`cli`/`sti` |
| **调用操作系统未公开的接口** | 直接 `syscall` / `int 0x80` |

**两种混合方式：**

### 方式一：嵌入汇编（Inline Assembly）

**直接在 C 代码里写汇编，编译器和 C 语句一起处理。**

**MSVC（Microsoft Visual C++）语法：`__asm { ... }`**

```c
#include <stdio.h>

// ===== 例 1：用汇编实现两数相加 =====
int asm_add(int a, int b)
{
    __asm {
        mov eax, a          // 把参数 a 装入 EAX
        add eax, b          // EAX = EAX + b
        // ★ 函数返回值默认就是 EAX，不用显式 return
    }
}

// ===== 例 2：读 CPU 时间戳计数器（只有汇编能做）=====
unsigned long long rdtsc(void)
{
    __asm {
        rdtsc               // ★ EDX:EAX = 时间戳（64 位）
        // 返回值是 64 位 → 约定放在 EDX:EAX，正好匹配
    }
}

// ===== 例 3：关中断（只在内核态有效）=====
void disable_interrupts(void)
{
    __asm cli               // 单条指令也可以这样写
}

int main(void)
{
    printf("3 + 4 = %d\n", asm_add(3, 4));
    printf("TSC = %llu\n", rdtsc());
    return 0;
}
```

**GCC 语法（AT&T 格式，操作数顺序相反、寄存器带 `%`、立即数带 `$`）：**

```c
// GCC：把 a 和 b 相加
int asm_add(int a, int b)
{
    int result;
    __asm__ __volatile__ (
        "movl %1, %%eax\n\t"    // 把 a（第 1 个输入）送入 EAX
        "addl %2, %%eax\n\t"    // EAX += b（第 2 个输入）
        "movl %%eax, %0"        // 把 EAX 写入输出
        : "=r"(result)          // 输出
        : "r"(a), "r"(b)        // 输入
        : "%eax"                // 被破坏的寄存器
    );
    return result;
}
```

**两种汇编语法的差异对照（很重要，看 Linux 内核源码必备）：**

| 对比项 | Intel 语法（MASM / MSVC） | AT&T 语法（GCC / GAS） |
|---|---|---|
| 操作数顺序 | **目的, 源** | **源, 目的** |
| 寄存器 | `eax` | `%eax` |
| 立即数 | `10` | `$10` |
| 内存操作数 | `[ebx+4]` | `4(%ebx)` |
| 数据宽度后缀 | `mov dword ptr [ebx], 1` | `movl $1, (%ebx)` |

### 方式二：独立汇编模块

**把汇编写成单独的文件，编译成 `.obj`，再和 C 的 `.obj` 一起链接。**

**汇编模块（`asmfunc.asm`）：**

```asm
.386
.model flat, c                 ; ★ flat = 平坦模型；c = 使用 C 调用约定
.code

; ===== 导出符号（让链接器能被 C 找到）=====
public asm_add
public asm_max

; ===== int asm_add(int a, int b) =====
; 参数：[ebp+8] = a，[ebp+12] = b
; 返回：EAX
asm_add proc
    push ebp
    mov  ebp, esp               ; ★ 建立栈帧
    mov  eax, [ebp+8]           ; EAX = a
    add  eax, [ebp+12]          ; EAX = a + b
    pop  ebp
    ret                         ; ★ cdecl：直接 ret，由调用者清栈
asm_add endp

; ===== int asm_max(int a, int b) =====
asm_max proc
    push ebp
    mov  ebp, esp
    mov  eax, [ebp+8]           ; EAX = a
    mov  ecx, [ebp+12]          ; ECX = b
    cmp  eax, ecx
    jge  done                   ; ★ 有符号比较：a >= b 就保持 a
    mov  eax, ecx               ; 否则取 b
done:
    pop  ebp
    ret
asm_max endp

end
```

**C 模块（`main.c`）：**

```c
#include <stdio.h>

// ★ 声明汇编里实现的函数
extern int asm_add(int a, int b);
extern int asm_max(int a, int b);

int main(void)
{
    printf("asm_add(3, 4)  = %d\n", asm_add(3, 4));
    printf("asm_max(10, 7)  = %d\n", asm_max(10, 7));
    return 0;
}
```

**编译与链接（命令行）：**

```
   ml /c /coff asmfunc.asm        ; ★ 汇编成 asmfunc.obj（/coff 生成 COFF 格式）
   cl /c main.c                   ; 编译成 main.obj
   link main.obj asmfunc.obj      ; 链接成可执行文件
   
   运行结果：
       asm_add(3, 4)  = 7
       asm_max(10, 7) = 10
```

**命名修饰（Name Mangling）——混合编程最容易踩的坑：**

| 语言 / 约定 | C 符号 `foo` 的目标文件符号名 |
|---|---|
| C，cdecl | **`_foo`** |
| C，stdcall | **`_foo@8`**（8 = 参数字节数） |
| C++（未加 `extern "C"`） | `?foo@@YAHHH@Z` 之类的乱码串 |
| MASM `.model flat, c` | 生成 **`_foo`**（匹配 C） |
| MASM `option casemap:none` | **区分大小写**（默认为不区分） |

> **重点**：**`.model flat, c` 里的 `c` 不起眼，但它决定了「MASM 生成的符号名是 `_asm_add` 还是 `asm_add`」——写错了就会在链接时报 `unresolved external symbol _asm_add`。** 这个错误在混合编程里出现频率极高，**看到 `unresolved external` 第一件事就是检查命名修饰。**

## 18.6 调用约定cdecl/stdcall/fastcall

**调用约定（Calling Convention）是「函数调用」的一套合同，规定了四件事：**

```
   ① 参数怎么传（顺序 + 用栈还是用寄存器）
   ② 谁负责清理栈上的参数（调用者还是被调用者）
   ③ 返回值放在哪里
   ④ 哪些寄存器必须由被调用者保护（不能破坏）
```

**★★ 三种主要调用约定对照表（必背）★★**

| 对比项 | **cdecl** | **stdcall** | **fastcall** |
|---|---|---|---|
| **参数传递** | **从右到左压栈** | **从右到左压栈** | **前 2 个放 `ECX`、`EDX`，其余从右到左压栈** |
| **栈清理者** | **调用者（caller）** | **被调用者（callee）** | **被调用者（callee）** |
| **清理方式** | `add esp, n` | **`ret n`** | **`ret n`**（n 只算栈上的参数） |
| **返回值** | `EAX`（64 位在 `EDX:EAX`） | `EAX` | `EAX` |
| **必须保护的寄存器** | `EBX`、`ESI`、`EDI`、`EBP` | 同左 | 同左 |
| **`EAX`/`ECX`/`EDX`** | 可自由破坏 | 可自由破坏 | 可自由破坏 |
| **名字修饰** | `_name` | **`_name@n`**（n = 参数字节数） | `@name@n` |
| **典型用途** | **C/C++ 默认（32 位）** | **Win32 API（`WINAPI`/`__stdcall`）** | 性能优化（少用） |
| **支持可变参数** | **✓（`printf` 必须用它）** | ✗ | ✗ |

**为什么 cdecl 能支持可变参数，stdcall 不能？**

```
   ★ 因为「清理栈」需要知道「一共压了几个参数、共占多少字节」。
   
   cdecl：调用者清栈 → 调用者当然知道自己压了几个参数
          → 所以 printf("...", a, b, c) 这种「参数个数不定」的调用可行
   
   stdcall：被调用者清栈 → 被调用者必须写死 ret n
          → 参数个数必须固定，无法支持可变参数
```

### 栈帧（Stack Frame）的标准结构

**理解调用约定的关键，是理解「函数执行时栈上有什么」。**

```
        高地址
   ┌──────────────────────┐
   │      参数 n           │ ← [ebp + 8 + 4×(n−1)]
   ├──────────────────────┤
   │        ……            │
   ├──────────────────────┤
   │      参数 2           │ ← [ebp + 12]
   ├──────────────────────┤
   │      参数 1           │ ← [ebp + 8]     ★ 第一个参数离 EBP 最近
   ├──────────────────────┤
   │     返回地址          │ ← [ebp + 4]     ★ call 指令压入
   ├──────────────────────┤
   │   旧的 EBP            │ ← [ebp + 0]     ★ EBP 指向这里
   ├──────────────────────┤
   │   局部变量 1          │ ← [ebp − 4]
   ├──────────────────────┤
   │   局部变量 2          │ ← [ebp − 8]
   ├──────────────────────┤
   │        ……            │
   └──────────────────────┘ ← ESP（随着 push/pop 上下移动）
        低地址
```

**建立和拆除栈帧的两条固定指令对：**

```asm
    ; ===== 进入函数（序言 Prologue）=====
    push ebp                ; 保存调用者的 EBP
    mov  ebp, esp           ; ★ 让 EBP 指向「保存的旧 EBP」，作为访问参数的基准

    sub  esp, 8             ; （可选）为局部变量在栈上开辟空间

    ; …… 函数体 ……

    ; ===== 离开函数（尾声 Epilogue）=====
    mov  esp, ebp           ; （可选）释放局部变量空间
    pop  ebp                ; 恢复调用者的 EBP
    ret                     ; 返回（cdecl）
```

**★ `[ebp+8]` 为什么是第一个参数？**

```
   call 指令压入返回地址（4 字节）→ [ebp+4]
   push ebp 压入旧 EBP（4 字节）  → [ebp+0]
   然后调用者在此之前压的参数，就依次在 [ebp+8]、[ebp+12]、……
   
   ★ 从右到左压栈 + 栈向低地址生长 → 第一个参数离 EBP 最近。
```

### 三种约定的汇编框架

**cdecl 版本（`ret`，被调用者不清理参数）：**

```asm
; ===== int myfunc_cdecl(int a, int b) =====
myfunc_cdecl proc
    push ebp
    mov  ebp, esp
    mov  eax, [ebp+8]           ; EAX = a
    add  eax, [ebp+12]          ; EAX += b
    pop  ebp
    ret                         ; ★★ 直接 ret，参数由【调用者】清理
myfunc_cdecl endp
```

**调用者的代码：**

```asm
    ; ===== 调用 myfunc_cdecl(1, 2) =====
    push 2                      ; ★ 从右到左：先压第 2 个参数
    push 1                      ;             再压第 1 个参数
    call myfunc_cdecl
    add  esp, 8                 ; ★★ 调用者清理 8 字节（2 个参数 × 4）
```

**stdcall 版本（`ret n`，被调用者清理参数）：**

```asm
; ===== int myfunc_stdcall(int a, int b) =====
myfunc_stdcall proc
    push ebp
    mov  ebp, esp
    mov  eax, [ebp+8]           ; EAX = a
    add  eax, [ebp+12]          ; EAX += b
    pop  ebp
    ret 8                       ; ★★ ret 8：先弹出返回地址，再把 ESP 加 8
                                ;     → 跳过了 2 个参数，由【被调用者】清理
myfunc_stdcall endp
```

**调用者的代码：**

```asm
    ; ===== 调用 myfunc_stdcall(1, 2) =====
    push 2
    push 1
    call myfunc_stdcall
    ; ★★ 不需要 add esp, 8 —— 被调用者的 ret 8 已经清理了
```

**`ret n` 的执行过程（对比 `ret`）：**

```
   ret 8 等价于：
        pop  eip                ; 弹出返回地址
        add  esp, 8             ; ★ 再多弹 8 字节（跳过参数）
   
   而 ret 等价于：
        pop  eip                ; 只弹出返回地址
```

**栈的变化对比（调用 `f(1, 2)` 之后）：**

```
   【cdecl】调用者清理                       【stdcall】被调用者清理
   
   调用前：ESP ──► (空闲)                    调用前：ESP ──► (空闲)
                                                    push 2
   调用前：push 2  push 1                     调用中：ESP ──► [2][1][返回地址]
           ESP ──► [2][1]                             （call 后 ESP 指向返回地址）
           call f  → 压入返回地址                      函数体内 pop ebp
           ESP ──► [2][1][返回地址]                    ret 8：
           函数体内 pop ebp                                 弹出返回地址 → EIP
           ret：                                            ESP += 8
                 弹出返回地址 → EIP                 返回后：ESP ──► (空闲) ✓
                 返回后：ESP ──► [2][1] ← 垃圾！
           调用者 add esp, 8
                 ESP ──► (空闲) ✓
   
   ★ 结论：stdcall 省掉了调用点的 add esp, n —— 每个调用点少一条指令。
     这就是为什么 Win32 API 全用 stdcall（成千上万个调用点，积少成多）。
```

**fastcall 版本（前两个参数用寄存器，其余压栈）：**

```asm
; ===== int myfunc_fastcall(int a, int b) =====
; ★ 入口：ECX = a，EDX = b（32 位 Windows 的 fastcall）
myfunc_fastcall proc
    push ebp
    mov  ebp, esp
    mov  eax, ecx               ; ★ 第 1 个参数在 ECX
    add  eax, edx               ; ★ 第 2 个参数在 EDX
    pop  ebp
    ret                         ; ★ 本例没有压栈参数，所以 ret 后面不带数字
                                ;   （若还有第 3 个参数，则要 ret 4）
myfunc_fastcall endp
```

**为什么 `fastcall` 没有流行起来？**

```
   ★ 优点：省掉了压栈/出栈的内存访问，速度快。
   ★ 缺点：
        · 各编译器实现不一致（Borland 和 Microsoft 的 fastcall 就不同）
        · 只有前 2 个参数受益，参数多时优势消失
        · 破坏了「函数可以只看原型就知道怎么调用」的简单性
   
   ★ 到了 64 位时代，微软统一采用「x64 调用约定」：
        前 4 个整型参数放 RCX、RDX、R8、R9
        浮点参数放 XMM0~XMM3
        调用者负责清理栈
        ★★ 64 位 Windows 上【只有一种调用约定】，不再有 cdecl/stdcall 之分。
```

**三种约定的名字修饰对照（链接错误排查必备）：**

| C 声明（32 位 Windows） | 汇编里要写的名字 |
|---|---|
| `int __cdecl foo(int a, int b)` | **`_foo`** |
| `int __stdcall foo(int a, int b)` | **`_foo@8`** |
| `int __fastcall foo(int a, int b)` | `@foo@8` |

> **重点**：**调用约定不是「可选的风格」——它是 ABI（应用二进制接口）的一部分。** 调用者和被调用者**必须约定一致**，否则会出现「栈失衡」「参数取错」「返回地址错乱」这类极难排查的崩溃。**混合编程时的规则很简单：汇编模块用 `.model flat, c` 匹配 C 的 cdecl；要写 Win32 API 风格的函数就用 `stdcall` 并在 `.model` 里写 `stdcall`。**

## 18.7 Win32汇编入门

**Win32 汇编 = 用汇编语言写 32 位 Windows 程序。开发包通常用 MASM32。**

**与 DOS 汇编的整体差异（这张表是本节的总纲）：**

| 对比项 | DOS 16 位汇编（第 1~17 章） | **Win32 汇编** |
|---|---|---|
| 内存模型 | `.model small`、多个 segment | **`.model flat, stdcall`，只有一个平坦空间** |
| 段结构 | `code segment` / `data segment` / `stack segment` | **`.code` / `.data` / `.data?`（无栈段）** |
| 调用系统功能 | **`int 21h` + `AH` 功能号** | **`invoke` 调用动态库（DLL）中的 API 函数** |
| 程序入口 | `end start`，由 DOS 装入执行 | **`WinMain`（窗口程序）或 `start`（控制台）** |
| 退出方式 | `mov ax,4c00h` / `int 21h` | **`invoke ExitProcess, 0`** |
| 字符串 | `db 'text', '$'`（`$` 结尾） | **`db 'text', 0`（0 结尾，C 风格）** |
| 显示输出 | `int 21h` 9 号 / 写显存 `B800H` | **`invoke MessageBox` / `invoke WriteConsole`** |
| 输入 | `int 16h` / `int 21h` 1 号 | **窗口消息 `WM_KEYDOWN` / `invoke ReadConsole`** |
| 执行模型 | **顺序执行**（从头跑到尾） | **消息驱动**（等消息 → 处理 → 再等） |
| 地址 | `段:偏移`（16 位） | **32 位平坦地址** |
| 库 | 直接用 BIOS/DOS | **需要 `.lib` + `includelib`** |

### 例一：最小的 Win32 程序（弹出一个消息框）

```asm
.386                            ; ★ 使用 80386 指令集
.model flat, stdcall            ; ★ 平坦模型 + stdcall 调用约定
option casemap:none             ; ★ 区分大小写（API 函数名大小写敏感）

; ===== 包含头文件与库 =====
include windows.inc
include user32.inc
includelib user32.lib
include kernel32.inc
includelib kernel32.lib

; ===== 数据段 =====
.data
    szCaption db 'Hello', 0                     ; ★ 以 0 结尾
    szText    db 'Hello, Win32 Assembly!', 0

; ===== 代码段 =====
.code
start:
    ; ★ invoke 伪指令：自动压参数（stdcall 从右到左）、检查参数个数、调用
    invoke MessageBox, NULL, addr szText, addr szCaption, MB_OK

    invoke ExitProcess, 0       ; ★ 退出进程（相当于 DOS 的 int 21h 4CH）
end start
```

**`invoke` 伪指令到底做了什么？**

```asm
    invoke MessageBox, NULL, addr szText, addr szCaption, MB_OK
```

**等价于手工写：**

```asm
    push MB_OK                  ; 第 4 个参数（最右）
    push offset szCaption       ; 第 3 个参数
    push offset szText          ; 第 2 个参数
    push NULL                   ; 第 1 个参数（最左）
    call MessageBox             ; ★ stdcall：被调用者用 ret 16 清理这 4 个参数
```

> **★ 数清楚有几个参数：`MessageBoxA` 的原型是 4 个参数。**
> ```
> int MessageBoxA(HWND hWnd, LPCSTR lpText, LPCSTR lpCaption, UINT uType);
>                    ①            ②              ③            ④
> ```
> 对照 `invoke MessageBox, NULL, addr szText, addr szCaption, MB_OK`：**`NULL`=①、`addr szText`=②、`addr szCaption`=③、`MB_OK`=④**——**一共 4 个，所以只有 4 条 `push`**。
> **常见错误**：看到 `NULL` 就以为「`NULL` 是空、不算参数」，于是写成 5 条 `push`（多压一个 `NULL`）并配 `ret 20`。**那样栈会被多清 4 字节，`ret` 弹回的返回地址就是错的，程序立刻崩。**
> **`ret 16` 里的 16 是怎么来的**：**4 个参数 × 4 字节 = 16**（32 位程序里每个参数占 4 字节，`NULL`/`MB_OK` 这类常量也被 `invoke` 按 32 位压栈）。**口诀：`ret n` 的 `n` = 参数个数 × 4。**

**`invoke` 的三个好处：**

| 好处 | 说明 |
|---|---|
| **自动按调用约定压栈** | 不用手写一堆 `push` |
| **自动参数个数检查** | 参数个数写错会在汇编期报错 |
| **自动选择 `call` 还是 `call [xxx]`** | 对 DLL 导入函数会自动生成间接调用 |

### 例二：Win32 窗口程序的结构（消息驱动）

**Win32 窗口程序有一个固定骨架——`WinMain` 负责「创建窗口 + 消息循环」，`WndProc` 负责「处理消息」。**

```
   WinMain（主流程）                          WndProc（窗口过程，被系统反复调用）
   ─────────────────────────────             ────────────────────────────────
   ① invoke GetModuleHandle  → hInstance
   ② invoke RegisterClassEx  （注册窗口类）
   ③ invoke CreateWindowEx   （创建窗口）
   ④ invoke ShowWindow       （显示窗口）
   ⑤ invoke UpdateWindow     （刷新窗口）
   ⑥ ★ 消息循环：
        .while TRUE
            invoke GetMessage, addr msg, NULL, 0, 0
            .break .if eax == 0
            invoke TranslateMessage, addr msg
            invoke DispatchMessage, addr msg
        .endw
   ⑦ invoke ExitProcess, msg.wParam
                                              ┌──► invoke WndProc, hWnd, uMsg, wParam, lParam
                                              │        .if uMsg == WM_CREATE
                                              │            …… 初始化 ……
                                              │        .elseif uMsg == WM_PAINT
                                              │            …… 绘制 ……
                                              │        .elseif uMsg == WM_LBUTTONDOWN
                                              │            …… 响应鼠标点击 ……
                                              │        .elseif uMsg == WM_DESTROY
                                              │            invoke PostQuitMessage, 0
                                              │        .else
                                              │            invoke DefWindowProc, ...
                                              │        .endif
                                              │        xor eax, eax
                                              │        ret
                                              └──────── 返回系统
```

**关键理解：`WndProc` 不是你调用的，是「操作系统在消息到来时调用你」。**

```
   DOS 模型：                     Win32 模型：
   ────────────                   ──────────────
   我的程序从头跑到尾               我的程序注册一个「窗口过程」
   ↓                              ↓
   我主动问「有键吗」（int 16h）    系统在事件发生时【主动调用】我的 WndProc
   ↓                              ↓
   我主动做每一件事                 我只负责「响应消息」
   
   ★★ 从「我控制流程」变成「系统控制流程、我响应事件」——
      这是思维方式的根本转变，也是所有现代 GUI / 事件驱动编程的基础。
```

**常用窗口消息（了解即可）：**

| 消息 | 触发时机 |
|---|---|
| `WM_CREATE` | 窗口创建时 |
| `WM_PAINT` | 窗口需要重绘时 |
| `WM_LBUTTONDOWN` / `WM_LBUTTONUP` | 鼠标左键按下 / 抬起 |
| `WM_KEYDOWN` / `WM_KEYUP` | 键盘按键按下 / 抬起 |
| `WM_MOUSEMOVE` | 鼠标移动 |
| `WM_SIZE` | 窗口大小改变 |
| `WM_TIMER` | 定时器到期 |
| `WM_COMMAND` | 菜单 / 按钮被点击 |
| **`WM_DESTROY`** | **窗口被销毁（一般在这里 `PostQuitMessage` 结束程序）** |

> **重点**：**从 DOS 到 Win32，最大的变化不是「指令变多了」，而是「谁在控制程序流程」。** 在 DOS 下你是主宰（顺序执行、主动查询）；在 Win32 下你是**响应者**（等待消息、处理消息、返回）。**这个转变，就是「面向过程」到「事件驱动」的转变——你写的每一个现代 GUI 程序、Web 前端程序，底层都是这个模型。** 而你学的 `int 9` 中断例程的写法（保护现场 → 处理 → 恢复 → `iret`），本质上和 `WndProc` 的写法（处理 → 返回）是同一个思想：**「被动响应」比「主动轮询」更高效。**

## 18.8 从汇编视角看C语言

**学了汇编，你对 C 语言的理解应该发生一次质变——不再是「语法」，而是「CPU 要做什么」。**

**常见 C 语句与汇编实现的对照表（`-O0` 未优化，最能看清结构）：**

| C 语句 | 典型汇编实现 | 涉及的知识 |
|---|---|---|
| `int a = 10;` | `mov dword ptr [ebp-4], 10` | **局部变量在栈上** |
| `a = b + c;` | `mov eax,[ebp-8]`<br>`add eax,[ebp-12]`<br>`mov [ebp-4],eax` | 双操作数指令、中间寄存器 |
| `if (a > b) x=1;` | `mov eax,[a]`<br>`cmp eax,[b]`<br>`jle L1`<br>`mov dword ptr [x],1`<br>`L1:` | **有符号比较用 `jg`/`jl`** |
| `if ((unsigned)a > b)` | `cmp` + **`jbe`** | **无符号比较用 `ja`/`jb`** |
| `for (i=0; i<10; i++)` | `mov dword ptr [i],0`<br>`jmp L2`<br>`L1: inc dword ptr [i]`<br>`L2: cmp dword ptr [i],10`<br>`jl L1` | **循环 = 条件转移 + 计数变量** |
| `a[i]`（`int` 数组） | `mov eax,[ebp+8]`<br>`mov ecx,[ebp+12]`<br>`mov eax,[eax+ecx*4]` | **`[基址 + 变址 × 比例]`** |
| `p->field` | `mov eax,[ebp+8]`<br>`mov eax,[eax+4]` | **结构体成员 = 固定偏移** |
| `arr[i].field` | `mov eax,[ebp+8]`<br>`mov ecx,[ebp+12]`<br>`mov eax,[eax+ecx*8+4]` | **`[基址+变址×比例+位移]`** |
| `f(1, 2)` | `push 2` / `push 1` / `call f` / `add esp,8` | **cdecl 调用约定** |
| `return x;` | `mov eax,[ebp-4]` | **返回值放 `EAX`** |
| `{ int t; ... }` | `sub esp, 4`（进入时）<br>`mov esp, ebp`（离开时） | **局部变量靠移动 ESP 批量分配** |
| `switch (x)` 多分支 | **跳转表 + `jmp [table+eax*4]`** | **第 16 章的直接定址表！** |
| `static inline` 函数 | **不生成 `call`/`ret`，直接展开** | 省掉调用开销 |

**完整例子：把一段 C 翻译成汇编。**

```c
int sum_array(int *a, int n)
{
    int s = 0;
    for (int i = 0; i < n; i++) {
        s += a[i];
    }
    return s;
}
```

**对应的汇编（cdecl，未优化）：**

```asm
; ===== int sum_array(int *a, int n) =====
; 参数：[ebp+8] = a（指针），[ebp+12] = n
; 局部：[ebp-4] = s，[ebp-8] = i
sum_array proc
    push ebp
    mov  ebp, esp
    sub  esp, 8                 ; ★ 为 s 和 i 两个局部变量开辟 8 字节

    mov  dword ptr [ebp-4], 0   ; s = 0
    mov  dword ptr [ebp-8], 0   ; i = 0

    jmp  L_cond                 ; ★ 先跳到条件判断（对应 for 的语义）

L_body:
    mov  eax, [ebp-8]           ; eax = i
    mov  ecx, [ebp+8]           ; ecx = a（数组首地址）
    mov  eax, [ecx + eax*4]     ; ★★ eax = a[i]（基址 + 变址 × 比例）
    add  [ebp-4], eax           ; s += a[i]

    inc  dword ptr [ebp-8]      ; i++

L_cond:
    mov  eax, [ebp-8]           ; eax = i
    cmp  eax, [ebp+12]          ; 比较 i 和 n
    jl   L_body                 ; ★ 有符号小于则继续循环

    mov  eax, [ebp-4]           ; ★ 返回值放 EAX
    mov  esp, ebp               ; 释放局部变量
    pop  ebp
    ret                         ; cdecl：调用者清栈
sum_array endp
```

**这段对照揭示的六个「为什么」：**

| 疑问 | 汇编给出的答案 |
|---|---|
| **为什么局部变量在栈上？** | 因为**递归和嵌套调用需要「每次调用一份独立副本」**，栈的自动分配/回收正好满足；而且 `sub esp, n` 一条指令就批量分配 |
| **为什么递归必须有栈？** | 每次递归调用都要**保存参数、返回地址、局部变量**，这些只能放在栈上 |
| **为什么数组下标从 0 开始？** | 因为 `[基址 + 变址 × 比例]` 里**下标 0 正好对应第一个元素**。若从 1 开始，每次访问都要多减 1 |
| **为什么 `a[i]` 比 `p->f` 慢？** | 不是慢，而是**寻址方式不同**：数组要算「变址 × 比例」，结构体成员是固定位移（编译期就是常量） |
| **为什么 `switch` 有时比 `if-else` 快？** | 多分支 `switch` 会被编译成**跳转表**（第 16 章的直接定址表），`O(1)`；而 `if-else` 链是 `O(n)` |
| **为什么内联函数能提升性能？** | 因为它**省掉了 `push` 参数、`call`、`ret`、`add esp,n` 这一整套调用开销**（见 18.6 的调用约定） |

**再看一个「数组 vs 结构体数组」的寻址对比（呼应第 7、8 章）：**

| 访问形式 | 寻址方式 | 8086 对应写法 |
|---|---|---|
| `a[i]`（`int` 数组） | `[base + i*4]` | `[bx+si]` + 手工乘 2 ✓ |
| `s.field` | `[base + const]` | `[bx+idata]` ✓ |
| `arr[i].field` | `[base + i*8 + const]` | **`[bx+si+idata]` ✓** |

> **重点**：**第 7 章学的 `[bx+si+idata]`、第 8 章学的「结构化数据访问」、第 16 章学的「直接定址表」——它们不是「8086 时代的老古董」，而是现代编译器生成代码时用的同一种寻址逻辑，只不过 32 位下多了「比例因子」这个便利。** 换句话说：**你前面 17 章学的东西，就是 C 语言编译器每天在做的事。** 理解了它，你看任何一行 C 代码都能在脑子里看到对应的汇编。

## 典型例题

**例 18.1**（题型：实模式与保护模式对比）
说明实模式的四大局限，以及保护模式分别用什么机制解决。
**解**：

| 实模式局限 | 保护模式的解决机制 |
|---|---|
| **只能寻址 1MB**（20 位地址总线） | **32 位地址总线 → 4GB 线性地址空间**（80386 起） |
| **段最大 64KB**、段边界固定在 16 字节倍数 | **段描述符里 32 位段基址 + 20 位段界限（配合粒度位 `G`，最大 4GB）**，段可以任意起始 |
| **没有权限检查**，任何程序能改任何内存、执行特权指令 | **特权级（0~3）**：用户程序（级 3）访问内核段（级 0）会触发异常；执行特权指令触发 `#GP` |
| **无虚拟内存**，程序直接面对物理地址 | **分页机制**：线性地址经页表映射，配合缺页异常实现虚拟内存和进程隔离 |

**答案**：见上。

**例 18.2**（题型：段选择子解析）
保护模式下 `DS = 0x0023`。请说明这个选择子的含义，并算出它指向的描述符在 GDT 中的偏移。
**解**：
- 把 `0x0023` 展开成二进制：

```
   0x0023 = 0000 0000 0010 0011 B
   
   索引(13位)      TI  RPL
   ┌───────────┬───┬───┐
   │ 0000000000100│ 0 │ 11│
   └───────────┴───┴───┘
   
   ★ 索引 = 二进制 100 = 十进制 4
   ★ TI = 0 → 查 GDT（不是 LDT）
   ★ RPL = 11B = 3 → 请求特权级为 3（用户态）
```

- **描述符在 GDT 中的偏移** = **索引 × 8 = 4 × 8 = 32**。
- **含义**：这是 GDT 中第 4 个描述符（从 0 开始编号），**以用户态（级 3）身份请求访问**。

**答案**：索引 4、查 GDT、RPL = 3；描述符偏移为 **32**。

**例 18.3**（题型：32 位寻址方式）
在 IA-32 上，`EBX` 中是一个 `struct` 数组的首地址，每个元素占 8 字节，`ESI` 中是下标 `i`。要访问第 `i` 个元素中偏移为 4 的字段，写出寻址表达式和指令。
**解**：
- **元素大小 8 字节 → 比例因子为 8**；**字段偏移 4 是常量位移**。
- **寻址表达式**：`[EBX + ESI*8 + 4]`
```asm
    mov eax, [ebx + esi*8 + 4]      ; ★ 一条指令完成
```
**答案**：`[EBX + ESI*8 + 4]`；指令 `mov eax, [ebx+esi*8+4]`。
**关键**：**这正是 8086 的 `[bx+si+idata]` 的 32 位升级版**——多了「比例因子 8」，省掉了手工乘法。

**例 18.4**（题型：调用约定辨析）
下列函数分别应采用哪种调用约定？为什么？
（1）`int printf(const char *fmt, ...);`
（2）`int MessageBoxA(HWND, LPCSTR, LPCSTR, UINT);`（Windows API）
**解**：
- （1）**必须是 `cdecl`**。因为它是**可变参数函数**——参数个数由格式串 `fmt` 决定。**只有「调用者清理栈」的 cdecl 才能支持可变参数**（调用者清楚自己压了几个参数；被调用者无法写死 `ret n`）。
- （2）**采用 `stdcall`**（Windows API 的 `WINAPI` 就是 `__stdcall`）。**理由**：参数个数固定，由**被调用者用 `ret n` 清理栈**，可以让**每一个调用点省掉一条 `add esp, n`**——Windows API 被成千上万次调用，积少成多。

**答案**：见上。
**对比**：cdecl 用 `ret` + 调用者的 `add esp,n`；stdcall 用 `ret n` + 调用者不清理。

**例 18.5**（题型：栈帧分析）
某函数用 cdecl 约定，签名是 `int f(int a, int b, int c)`。函数体内 `EBP = 0x0012FF00`。请写出 `a`、`b`、`c`、返回地址、旧 `EBP` 各自的内存地址。
**解**：
- `push ebp` / `mov ebp, esp` 之后，栈帧布局固定：

| 内容 | 地址 | 说明 |
|---|---|---|
| `c` | **`EBP + 16` = 0x0012FF10** | 最后一个参数（最先压栈） |
| `b` | **`EBP + 12` = 0x0012FF0C** | |
| `a` | **`EBP + 8` = 0x0012FF08** | 第一个参数（最后压栈，离 EBP 最近） |
| 返回地址 | **`EBP + 4` = 0x0012FF04** | `call` 指令压入 |
| 旧 `EBP` | **`EBP + 0` = 0x0012FF00** | `push ebp` 压入；`EBP` 指向这里 |
| （局部变量） | `EBP − 4`、`EBP − 8`…… | 由 `sub esp, n` 分配 |

**答案**：`a` 在 `EBP+8`、`b` 在 `EBP+12`、`c` 在 `EBP+16`；返回地址在 `EBP+4`；旧 `EBP` 在 `EBP+0`。
**关键**：**「从右到左压栈」+「栈向低地址生长」⇒ 第一个参数离 `EBP` 最近（偏移最小）。**

**例 18.6**（题型：C 到汇编的翻译）
把下面的 C 代码翻译成 IA-32 汇编（不要求最优）。
```c
int find_max(int *a, int n)
{
    int m = a[0];
    for (int i = 1; i < n; i++) {
        if (a[i] > m) m = a[i];
    }
    return m;
}
```
**解**：
```asm
; ===== int find_max(int *a, int n) =====
; 参数：[ebp+8] = a，[ebp+12] = n
; 局部：[ebp-4] = m，[ebp-8] = i
find_max proc
    push ebp
    mov  ebp, esp
    sub  esp, 8

    ; ---- m = a[0] ----
    mov  eax, [ebp+8]           ; eax = a
    mov  eax, [eax]             ; ★ eax = a[0]（变址为 0，比例无所谓）
    mov  [ebp-4], eax           ; m = a[0]

    ; ---- i = 1 ----
    mov  dword ptr [ebp-8], 1

    jmp  L_cond

L_body:
    ; ---- 取 a[i] ----
    mov  eax, [ebp-8]           ; eax = i
    mov  ecx, [ebp+8]           ; ecx = a
    mov  eax, [ecx + eax*4]     ; ★★ eax = a[i]（基址 + 变址 × 比例）

    ; ---- if (a[i] > m) m = a[i] ----
    cmp  eax, [ebp-4]           ; 比较 a[i] 与 m
    jle  L_next                 ; ★ 有符号：不大于则跳过
    mov  [ebp-4], eax           ; m = a[i]
L_next:
    inc  dword ptr [ebp-8]      ; i++

L_cond:
    mov  eax, [ebp-8]
    cmp  eax, [ebp+12]          ; i < n ?
    jl   L_body

    mov  eax, [ebp-4]           ; ★ 返回值放 EAX
    mov  esp, ebp
    pop  ebp
    ret
find_max endp
```
**答案**：见上。
**关键**：① **局部变量用 `sub esp, 8` 在栈上分配，用 `[ebp-4]`/`[ebp-8]` 访问**；② **`a[i]` 用 `[ecx+eax*4]` 一次完成**；③ **返回值放 `EAX`**；④ **有符号比较用 `jl`/`jle`**（若 `n` 是 `unsigned`，则要改用 `jb`/`jbe`）。

## 易错点提醒

1. **错**：以为保护模式下的段寄存器里装的是「段地址」。**对**：**保护模式下段寄存器装的是「段选择子」（索引 13 位 + TI 1 位 + RPL 2 位）**，真正的段基址存放在**描述符**里（由处理器读进隐藏的描述符缓存）。
2. **错**：把段选择子的偏移算成「索引 × 2」或「索引 × 4」。**对**：**每个段描述符固定 8 字节，所以偏移 = 索引 × 8**。这也是索引只占 13 位的原因（`2^13 × 8 = 64KB` 的描述符表空间）。
3. **错**：把选择子的 bit 位置记错。**对**：**bit 15~3 是索引、bit 2 是 TI、bit 1~0 是 RPL。** `TI = 0` 查 GDT、`TI = 1` 查 LDT。
4. **错**：以为 `CPL`、`DPL`、`RPL` 是同一个东西。**对**：**`CPL`（当前特权级）= `CS` 的低 2 位；`DPL`（描述符特权级）= 段描述符里写的「谁能访问我」；`RPL`（请求特权级）= 选择子的低 2 位「我以什么身份请求」。**
5. **错**：以为保护模式下段寄存器变成 32 位了。**对**：**段寄存器仍然只有 16 位（装选择子）**；变宽的是**通用寄存器**（`EAX` 等）和**隐藏的描述符缓存（64 位）**。
6. **错**：`G`（粒度位）的作用搞不清。**对**：**`G = 0` 时段界限单位是字节；`G = 1` 时单位是 4KB 页。** 所以 20 位界限在 `G = 1` 时最大可表示 `FFFFF × 4KB = 4GB`。
7. **错**：把 32 位寻址的比例因子写成任意数。**对**：**比例因子只能是 1、2、4、8**（对应 `char`/`short`/`int`/`double` 或指针的大小），**没有 3、5、16**。
8. **错**：用 `ESP` 做变址寄存器。**对**：**`ESP` 可以作基址，但不能作变址**（`[esp+eax*4]` 非法）。这是编码格式的限制。
9. **错**：以为平坦模型下「段」完全不存在了。**对**：**段机制仍在使用**——`CS` 的 `DPL`/`CPL` 决定了你能执行哪些指令、`SS` 的权限决定了栈操作是否合法。**只是「段基址 = 0、界限 = 4GB」使分段不再造成地址偏移**，看起来像「没有段」。
10. **错**：以为 `cdecl` 和 `stdcall` 只是「风格差异」。**对**：**它们是 ABI 的一部分，调用者和被调用者必须一致。** 混用会导致**栈失衡、参数取错、返回地址错乱**，表现为莫名其妙的崩溃。
11. **错**：把 `ret` 和 `ret n` 用反。**对**：**cdecl 用 `ret`（被调用者不清理，调用者写 `add esp, n`）**；**stdcall 用 `ret n`（被调用者清理，n 是参数字节总数）**。写反了栈指针就错了。
12. **错**：忘了「从右到左压栈」。**对**：**cdecl/stdcall 都是先压最右边的参数，最后压最左边的参数。** 所以 **[ebp+8] 是第一个参数**（离 `EBP` 最近）。
13. **错**：以为 `[ebp+4]` 是第一个参数。**对**：**`[ebp+4]` 是返回地址**（`call` 压入的），**[ebp+0] 是旧的 `EBP`**，**参数从 `[ebp+8]` 开始**。
14. **错**：汇编模块和 C 链接时报 `unresolved external symbol _foo`，以为是函数没实现。**对**：**这是「名字修饰」不匹配**——C 的 cdecl 会在函数名前加下划线。**解决：汇编模块里写 `.model flat, c`**（让 MASM 也加下划线），或检查 `stdcall` 的 `_foo@n` 形式是否对上了参数字节数。
15. **错**：在 Win32 汇编里写 `int 21h` 或 `mov ax,4c00h`。**对**：**Win32 是保护模式下的 32 位程序，不能调用 DOS 中断。** 退出要用 **`invoke ExitProcess, 0`**，显示输出要用 **`invoke MessageBox`/`WriteConsole`** 等 Windows API。
16. **错**：以为 Win32 窗口程序里 `WndProc` 会自己调用一次。**对**：**`WndProc` 是「回调函数」——由操作系统在消息到来时反复调用**，你只负责「收到某消息时做什么」。**这就是「事件驱动」与 DOS「顺序执行」的根本区别。**

## 本章小结

- **实模式的四大局限**：只能寻址 **1MB**、段最大 **64KB**、**没有权限检查**、**程序直接面对物理内存（无虚拟内存）**。
- **保护模式的解决之道**：**32 位地址总线（4GB）**、**描述符里 32 位段基址 + 20 位界限（`G=1` 时可达 4GB）**、**特权级（0~3）**、**分页（虚拟内存 + 进程隔离）**。
- **切换方法**：建 GDT → `lgdt` → 置 `CR0` 的 `PE` 位 → 远跳转刷新 `CS` →（可选）置 `PG` 位开分页。
- **段选择子（16 位）**：**bit 15~3 索引、bit 2 TI（0=GDT/1=LDT）、bit 1~0 RPL**；**描述符偏移 = 索引 × 8**（每个描述符 8 字节）。
- **段描述符关键字段**：**32 位段基址、20 位段界限、`G` 粒度位（0=字节/1=4KB 页）、`DPL`、`P`、`S`、`Type`**；`GDTR` 用 `lgdt` 加载；**第 0 个描述符必须全 0**。
- **三个特权级术语**：**`CPL`（当前，= `CS` 低 2 位）、`DPL`（描述符声明）、`RPL`（请求）**；级 0 是内核、级 3 是用户。
- **寄存器扩展**：`AX→EAX`、`BX→EBX`、`CX→ECX`、`DX→EDX`、`SP→ESP`、`BP→EBP`、`SI→ESI`、`DI→EDI`、`IP→EIP`、`FLAGS→EFLAGS`；**16 位寄存器是 32 位寄存器的低半部分**；新增 **`FS`、`GS`**。
- **★★ 32 位寻址方式：`有效地址 = 基址 + 变址 × 比例 + 位移`；比例只能是 1/2/4/8；8 个通用寄存器都能作基址，除 `ESP` 外都能作变址——彻底摆脱了 8086「只有 4 种配对、没有比例因子」的束缚。★★**
- **三种对应关系**：`[基址+位移]` = 结构体成员；`[基址+变址×比例]` = 数组元素；**`[基址+变址×比例+位移]` = 结构体数组的元素成员（= 8086 的 `[bx+si+idata]`）**。
- **平坦内存模型**：**所有段基址 = 0、界限 = 4GB** ⇒ **线性地址 = 32 位偏移**，分段基本退化为权限检查。
- **★★ 地址转换两阶段：`逻辑地址（段:偏移）──分段──► 线性地址 ──分页──► 物理地址`**；分页两级表：**10 位目录项 + 10 位页表项 + 12 位页内偏移**（页大小 **4KB**）；`CR3` 指向页目录。
- **分页三大作用**：**虚拟内存（缺页异常）、进程隔离（每进程独立页目录）、内存共享与保护**。`CR0` 的 `PE` = 保护模式、`PG` = 分页。
- **混合编程两方式**：**嵌入汇编（MSVC `__asm { }` / GCC `__asm__ __volatile__`，注意 Intel 与 AT&T 语法的差异）** 和 **独立汇编模块（`.model flat, c` + `public` 导出 + 与 C 的 `.obj` 一起链接）**。
- **★★★ 三种调用约定对照（必背）★★★**：

| | **cdecl** | **stdcall** | **fastcall** |
|---|---|---|---|
| 参数 | 从右到左压栈 | 从右到左压栈 | 前 2 个在 `ECX`/`EDX`，其余压栈 |
| 清栈 | **调用者 `add esp,n`** | **被调用者 `ret n`** | **被调用者 `ret n`** |
| 返回值 | `EAX` | `EAX` | `EAX` |
| 名字修饰 | `_name` | `_name@n` | `@name@n` |
| 用途 | **C 默认、支持可变参数（`printf`）** | **Win32 API** | 性能优化 |

- **★★ 栈帧固定布局：`[ebp+8]` 起是参数（第一个参数偏移最小）、`[ebp+4]` 是返回地址、`[ebp+0]` 是旧 `EBP`、局部变量在 `[ebp−4]`、`[ebp−8]`……；序言是 `push ebp` / `mov ebp,esp` / `sub esp,n`，尾声是 `mov esp,ebp` / `pop ebp` / `ret`。★★**
- **`ret n` ≡ `pop eip` + `add esp, n`**；**为什么 cdecl 能支持可变参数：只有调用者知道自己压了几个参数。**
- **Win32 汇编要点**：`.386` / `.model flat, stdcall` / `option casemap:none` / `include` + `includelib` / **`invoke` 自动按调用约定压参并检查参数个数** / 字符串以 **`0`** 结尾 / 退出用 **`invoke ExitProcess, 0`**。
- **Win32 的执行模型是「消息驱动」**：`WinMain` 创建窗口 + 消息循环（`GetMessage` / `TranslateMessage` / `DispatchMessage`），**`WndProc` 由系统在消息到来时回调**（`WM_CREATE`、`WM_PAINT`、`WM_LBUTTONDOWN`、`WM_DESTROY` 等）。**这是「被动响应」取代「主动轮询」的根本转变。**
- **从汇编看 C 的六个「为什么」**：局部变量在栈上（支持递归）、数组下标从 0 开始（`[base+index*size]`）、`switch` 用跳转表（`O(1)`）、内联函数省掉调用开销、结构体成员是固定位移、返回值放 `EAX`。

> **一句话记住本章**：**「保护模式 = 大地址（4GB）+ 特权级（0~3）+ 分页（虚拟内存与隔离），段寄存器装的是选择子（索引×8 找描述符）」；「32 位寻址 = 基址 + 变址×比例 + 位移，比例只会是 1/2/4/8」；「cdecl 调用者清栈、stdcall 被调用者 `ret n` 清栈，`[ebp+8]` 才是第一个参数」；「Win32 程序不问你什么时候按键，只等系统把消息送上门」——而这最后一句，正是你在第 15 章写的 `int 9` 中断例程教给你的同一件事。**

## 自测题

**1.** 实模式有哪四大局限？保护模式分别用什么机制解决？
**答**：① **地址空间只有 1MB**（20 位地址总线）→ 保护模式用 **32 位地址总线扩展到 4GB**；② **段最大 64KB 且边界固定** → 保护模式用**描述符中的 32 位段基址 + 20 位界限（配合粒度位可达 4GB）**，段可任意起始；③ **没有权限检查** → 保护模式引入**特权级（0~3）**，用户程序访问内核段或执行特权指令会触发异常；④ **无虚拟内存、程序直接面对物理地址** → 保护模式用**分页机制**实现虚拟内存与进程隔离。

**2.** 保护模式下 `DS = 0x0010`，请说明它的含义并算出描述符在 GDT 中的偏移。
**解**：`0x0010 = 0000 0000 0001 0000B`。
- **索引 = bit 15~3 = `0000000000010B = 2`**
- **TI = bit 2 = 0**（查 GDT）
- **RPL = bit 1~0 = 00**（特权级 0，内核态）
- **偏移 = 索引 × 8 = 2 × 8 = 16**
**答**：这是 GDT 中第 2 个描述符的选择子，以**内核态（级 0）**身份请求访问，描述符偏移为 **16**。

**3.** 为什么段选择子的索引要「乘以 8」才是描述符偏移？索引为什么是 13 位？
**答**：**因为每个段描述符固定占 8 个字节**，所以「第 n 个描述符」的偏移就是「n × 8」（处理器内部把索引左移 3 位实现）。**索引取 13 位是因为 2^13 = 8192，8192 × 8 字节 = 64KB**——正好是一个描述符表的最大长度。

**4.** `CPL`、`DPL`、`RPL` 分别是什么？各从哪里获得？
**答**：**`CPL`（Current Privilege Level，当前特权级）** = `CS` 寄存器的低 2 位，表示**正在执行的代码**的级别；**`DPL`（Descriptor Privilege Level，描述符特权级）** = 段描述符里的字段，表示**这个段允许哪个级别访问**；**`RPL`（Requested Privilege Level，请求特权级）** = 段选择子的低 2 位，表示**请求者以什么身份访问**。

**5.** 段描述符中的 `G`（粒度位）有什么作用？
**答**：**`G` 决定段界限的单位**：**`G = 0` 时单位是字节；`G = 1` 时单位是 4KB 页。** 因此 20 位的段界限在 `G = 1` 时最大可表示 **`0xFFFFF × 4KB = 4GB`**。这是保护模式能支持「一个段覆盖整个地址空间」（平坦模型）的关键。

**6.** 80386 扩展了哪些寄存器？16 位寄存器和 32 位寄存器是什么关系？
**答**：`AX→EAX`、`BX→EBX`、`CX→ECX`、`DX→EDX`、`SP→ESP`、`BP→EBP`、`SI→ESI`、`DI→EDI`、`IP→EIP`、`FLAGS→EFLAGS`；另外**新增段寄存器 `FS`、`GS`**。**16 位寄存器是 32 位寄存器的低 16 位**——修改 `AX` 只影响 `EAX` 的低半部分，高 16 位保持不变。

**7.** 写出 IA-32 的有效地址公式，并说明各部分有哪些限制。
**答**：**有效地址 = 基址寄存器 + 变址寄存器 × 比例 + 位移**。
- **基址寄存器**：`EAX`、`EBX`、`ECX`、`EDX`、`ESI`、`EDI`、`EBP`、`ESP`（8 个都可以）
- **变址寄存器**：`EAX`、`EBX`、`ECX`、`EDX`、`ESI`、`EDI`、`EBP`（**`ESP` 不能作变址**）
- **比例**：**只能是 1、2、4、8**
- **位移**：8 位或 32 位常量

**8.** 用一个 `int` 数组 `a`（首地址在 `EBX`）和下标 `i`（在 `ESI`），写出取 `a[i]` 的指令。这与 8086 上做同样的事有什么区别？
**答**：**`mov eax, [ebx + esi*4]`**。
**与 8086 的区别**：8086 上没有比例因子，**必须手工把下标乘以元素大小**（`mov ax,si` / `mov cl,2` / `shl ax,cl` / 再 `[bx+ax]`），而且要受「只有 `bx`/`bp`/`si`/`di` 参与寻址、只有 4 种合法配对、段内不超过 64KB」的限制。**IA-32 把「乘元素大小」交给硬件，一条指令完成。**

**9.** 平坦内存模型的含义是什么？为什么说它「架空了分段」？
**答**：**平坦模型把所有段的基址都设为 0、界限都设为 4GB。** 于是**线性地址 = 段基址 + 偏移 = 0 + 32 位偏移 = 32 位偏移**——段基址不再造成任何地址偏移，**分段机制只剩下了「权限检查」的作用**（`CS` 的 `CPL`/`DPL` 仍决定能否执行），所以说是「架空了分段」。

**10.** 画出「逻辑地址 → 线性地址 → 物理地址」的转换流程，并说明分页表的两级结构。
**答**：
```
   逻辑地址（段选择子:偏移）
        │  ① 分段：查 GDT/LDT 取段基址，加上偏移
        ▼
   线性地址（32 位）
        │  ② 分页：查页目录 → 查页表
        ▼
   物理地址
```
**分页两级结构**：**32 位线性地址 = 目录项 10 位 + 页表项 10 位 + 页内偏移 12 位**。`CR3` 指向页目录基址；**页大小 4KB（2^12）**，所以页内偏移占 12 位；一个页目录可覆盖 `1024 × 1024 × 4KB = 4GB`。

**11.** 分页机制有哪三大作用？
**答**：① **虚拟内存**——页不在物理内存时触发缺页异常（`#PF`），操作系统把页从磁盘调入，**程序可以使用比物理内存更大的地址空间**；② **进程隔离**——**每个进程有独立的页目录（`CR3` 不同）**，同一线性地址在不同进程映射到不同物理页，**进程之间不能互相访问内存**；③ **内存共享与保护**——页表项含读写/用户/内核权限位，**共享库的代码页可被多个进程共享映射**。

**12.** 比较 cdecl 和 stdcall 的三个方面：参数传递、栈清理、名字修饰。
**答**：

| 方面 | cdecl | stdcall |
|---|---|---|
| 参数传递 | **从右到左压栈** | **从右到左压栈**（相同） |
| 栈清理 | **调用者**：`call` 后写 `add esp, n` | **被调用者**：`ret n` |
| 名字修饰 | **`_name`** | **`_name@n`**（n = 参数字节数） |
| 代表用途 | C/C++ 默认，支持可变参数 | Win32 API（`WINAPI`） |

**13.** 为什么 `printf` 这样的可变参数函数必须用 cdecl？
**答**：**因为「清理栈」需要知道参数的总字节数。** `printf` 的参数个数由格式串决定，**被调用者无法预先写死 `ret n`**。而 **cdecl 由调用者清理栈**——调用者当然清楚自己压了几个参数、共多少字节，所以能正确执行 `add esp, n`。**这就是 cdecl 能支持可变参数、而 stdcall 不能的根本原因。**

**14.** 一个函数 `int f(int a, int b, int c)`（cdecl），执行到函数体时 `EBP = 0x0012FF00`。请写出 `a`、`b`、`c`、返回地址、旧 `EBP` 的内存地址。
**答**：**`a` 在 `0x0012FF08`（`[ebp+8]`）、`b` 在 `0x0012FF0C`（`[ebp+12]`）、`c` 在 `0x0012FF10`（`[ebp+16]`）、返回地址在 `0x0012FF04`（`[ebp+4]`）、旧 `EBP` 在 `0x0012FF00`（`[ebp+0]`）。** 局部变量在 `[ebp-4]`、`[ebp-8]`……
**理由**：**参数从右到左压栈 + 栈向低地址生长 ⇒ 第一个参数离 `EBP` 最近（偏移最小）。**

**15.** `ret` 和 `ret n` 的执行过程分别是什么？
**答**：**`ret` 等价于 `pop eip`**（只弹出返回地址）。**`ret n` 等价于 `pop eip` + `add esp, n`**——弹出返回地址后，**再把 `ESP` 加上 n，跳过栈上的 n 字节参数**。这就是 stdcall 里「被调用者清理参数」的实现方式。

**16.** 在 Win32 汇编里，`invoke MessageBox, NULL, addr szText, addr szCaption, MB_OK` 展开成什么？`invoke` 有什么好处？
**答**：展开成 **4 条 `push`**（`MessageBoxA` 原型只有 4 个参数）：
```asm
push MB_OK
push offset szCaption
push offset szText
push NULL
call MessageBox          ; stdcall：被调用者会 ret 16 清理 4 个参数（4 × 4 = 16）
```
**★ 别数错**：`invoke MessageBox, NULL, addr szText, addr szCaption, MB_OK` 里的 `NULL` **也是一个实实在在的参数**（`hWnd` = 窗口句柄，这里传「无父窗口」），**总共 4 个参数，不是 5 个**。写成 5 条 `push` + `ret 20` 会让栈多清 4 字节，`ret` 弹回的返回地址就错了。
**`invoke` 的好处**：① **自动按调用约定（这里是 stdcall，从右到左）压参数**，不用手写 `push`；② **自动检查参数个数**，个数不对在汇编期就报错；③ **自动决定用 `call` 还是间接调用**（对 DLL 导入函数）。

**17.** Win32 程序和 DOS 程序在「执行模型」上有什么根本区别？
**答**：**DOS 是「顺序执行」**：程序从头跑到尾，主动用中断查询状态、主动做每件事。**Win32 是「消息驱动」**：`WinMain` 创建窗口后进入消息循环，**操作系统在事件发生时主动调用你的窗口过程 `WndProc`**，你只负责「收到某消息时做什么」。**这是从「我控制流程」到「系统控制流程、我响应事件」的转变**——也就是「被动响应」取代「主动轮询」。**它与第 15 章的中断例程思想一致：中断处理程序也是「被动响应」。**

**18.** 从汇编的角度解释：为什么 C 语言的数组下标从 0 开始？
**答**：因为数组元素的寻址是 **`[基址 + 变址 × 比例]`**。**下标为 0 时偏移正好是 0，也就是数组的第一个元素。** 如果下标从 1 开始，那么每次访问都要额外做一次减法（`[base + (i-1)*size]`），**白白多一条指令**。**从 0 开始让「下标 = 偏移量 / 元素大小」这个关系最简单、最高效，这就是 C 语言数组下标从 0 开始的底层原因。**

**19.** `switch` 语句为什么有时比 `if-else` 链快？用汇编原理说明。
**答**：因为多分支的 `switch` 会被编译器优化成**跳转表**：把各个 `case` 分支的地址存进一张表，用 **`jmp [table + eax*4]`**（或 `call`）直接跳转。**这是一次地址计算 + 一次跳转，复杂度 `O(1)`**。而 `if-else` 链是**一串 `cmp` + 条件转移**，复杂度 `O(n)`——分支越多越慢。**这正是第 16 章「程序入口地址的直接定址表」的原理。**
